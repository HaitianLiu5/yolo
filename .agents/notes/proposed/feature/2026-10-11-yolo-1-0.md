# Agent Note: Yolo 1.0 and the path to it

Status: proposed

English | [中文](2026-10-11-yolo-1-0.zh.md)

## Problem

Yolo works today for one owner: a Cloudflare control plane, a media node on a Mac, Plex and web video as sources, the Tesla client, and agents over MCP. Without a definition of 1.0, the next versions have no shared target, and features that do not belong (multi-user, music, native apps) compete with the ones that do.

## Proposal

Yolo 1.0 is a self-hosted private media service. Like Plex it covers everything from sources and a library to playback on every screen; unlike Plex it is driven by agents and plays in the Tesla browser on a canvas.

| Area | At 1.0 |
|---|---|
| Install | A Cloudflare account, plus a NAS or computer that runs Docker, or a Mac. One command deploys the control plane; the media node is installed, and the owner registers a passkey with the code the node prints |
| Sources | NAS or local folders (the node runs on the NAS, or SMB/NFS shares are mounted on its machine), WebDAV, Plex (optional), web video links (yt-dlp); each one a plugin |
| Library | Films and series with posters and synopses; one progress and watch history shared by every client; one Spotify-style queue; playlists; history |
| Clients | Tesla: Drive-In. Any browser: Yolo Web. iPhone, iPad, Apple TV, Mac: Infuse for manual playback, Swiftfin for agent remote control. Jellyfin clients on Android should work but are not guaranteed |
| Agents | ChatGPT, Claude, and Codex search, play, control, and manage the queue and settings over MCP; whichever protocol a device speaks, it looks the same to them |
| Plugins | A documented plugin API with an example plugin, open to the community |
| Usage model | One owner, several devices, one playing at a time |

Out of scope for 1.0: multi-user households, family profiles, and sharing with friends; music, podcasts, audiobooks, and Spotify; native iOS, tvOS, and Android apps (a native tvOS app only if Swiftfin's remote control proves unreliable, see Risks); [self-hosting without Cloudflare](../architecture/2026-10-07-self-hosting-without-cloudflare.md); offline downloads, live TV and recording, IPTV; an SMB/NFS client inside the node; an official Plex protocol plugin; remote-controlling Infuse; and a plugin permission system.

```
              ChatGPT / Claude / Codex
                       │ MCP + OAuth
                       ▼
 ┌──────────── Control plane (Cloudflare Worker) ────────────┐
 │ Core: MCP, /v1, OAuth, Hub DO (devices/queue/state), D1     │
 │ Plugins (bundled at deploy): protocols (Jellyfin…), devices │
 └──────────┬──────────────────────────────┬──────────────────┘
            │ Workers VPC (nodeFetch)       │ WebSocket / HTTP
            ▼                              ▼
 Media node (Mac, or Docker on a NAS)   Clients
 ├ Core: transcoding, HLS, subtitles,   ├ Drive-In (Tesla canvas)
 │       signed /m/* streams            ├ Yolo Web (browser)
 └ Plugins (loaded at start):           ├ Swiftfin (agent remote)
   sources (folder, WebDAV, Plex,       └ Infuse (manual)
   yt-dlp), metadata (TMDB), device LAN halves
            └── media: through the Worker, LAN-direct at home ──┘
```

### Versions

Every version is usable on its own: if the next one never finishes, the system is still complete. The roadmap rates complexity (low, medium, high) and names the difficulty instead of estimating time.

| Version | Theme | Delivers | Complexity | Difficulty |
|---|---|---|---|---|
| 0.1 (done) | Control plane and MCP | Agents control the car through Yolo; Plex and web URLs as sources | — | — |
| 0.2 (done) | Plugin framework | [Plugins](../../implemented/architecture/2026-10-11-plugin-architecture.md) for Plex and yt-dlp; no `url` source type or yt-dlp in the core | High | One API for two runtimes; bundling at deploy time; untangling Plex and yt-dlp from three layers |
| 0.3 (done) | Drive-In fully on Yolo | The [media pipeline](../../implemented/architecture/2026-10-11-node-media-pipeline.md) in the node; the Tesla client on v1 with [QR pairing](../../implemented/feature/2026-10-07-device-code-pairing.md); [progress owned by Yolo](../../implemented/feature/2026-10-11-yolo-owns-progress-and-resume.md); the old server and CLI removed | High | Much code to move without regressing Tesla behavior; four stream types verified in the car; data migration |
| 0.4 | [Yolo Web](2026-10-11-yolo-web-client.md) | A browser client and the settings page | Medium | Mostly new interface; the engine and realtime channel are reused |
| 0.5 | [Own library and NAS](2026-10-11-own-library-and-nas.md) | Folder, WebDAV, and TMDB plugins; a catalog in D1; a node Docker image | High | Varied NAS setups; file-naming edge cases; transcoding on low-end NAS |
| 0.6 | [Jellyfin protocol plugin](2026-10-11-jellyfin-protocol-plugin.md) | Infuse and Swiftfin connect to Yolo; agents remote-control Swiftfin | Medium-high | About 40–60 endpoints and Infuse's quirks; no prior session-push implementation; real devices required |
| 0.7 → 1.0 | [Distribution to other owners](2026-10-11-distribution-to-other-owners.md) | One-command deploy, installers, setup wizard, `yolo install`, docs and the `useyolo.app` site | Medium | Wide rather than deep: packaging and testing on many platforms |

Phase one is 0.2, 0.3, and 0.4 together (decided 2026-10-11): it lays the architecture and moves development to `HaitianLiu5/yolo`. Its remaining parts are Yolo Web and retiring Drive-In's public pieces ([one repository](../../implemented/process/2026-10-07-one-yolo-repository.md)). Phase one excludes NAS and folder sources, WebDAV, TMDB, the Jellyfin protocol, Apple devices, installers for others, and multi-user.

### Official plugins at 1.0

| Type | Plugin | Runs on |
|---|---|---|
| Source | Folder (local and NAS) | Node |
| Source | WebDAV | Node |
| Source | Plex | Node |
| Source | yt-dlp | Node |
| Metadata | TMDB | Node |
| Protocol | Jellyfin-compatible API | Control plane (API, session push) and node (media) |

Yolo's own realtime channel (Drive-In, Yolo Web) stays in the core; the device-plugin interface waits for the first third-party device.

## Alternatives considered

**Native apps for 1.0.** Apple devices join through the Jellyfin-compatible protocol instead: native apps would have to pass App Review (guidelines 2.1 and 5.2.3) and be maintained every year ([Jellyfin proposal](2026-10-11-jellyfin-protocol-plugin.md)).

**Emulating a Plex server for third-party clients.** [Rejected](../../rejected/architecture/2026-10-11-emulate-a-plex-media-server.md): plex.tv's claim mechanism and Plex's terms do not allow it.

## Acceptance criteria

Every row of the 1.0 table above holds for a new owner who follows the published instructions, and every version in the table has shipped with its own acceptance criteria met. The plugin API is documented with an example plugin, and the `useyolo.app` site and documentation are live.

## Risks

| # | Assumption | If it fails | Who checks, when |
|---|---|---|---|
| 1 | Swiftfin on tvOS executes remote commands reliably | Add a native tvOS app after 0.6 that speaks the same Jellyfin session protocol, so the service and MCP stay unchanged; it brings Swift into the project and needs the owner's separate approval | Before 0.6, on the owner's Apple TV |
| 2 | Cloudflare's terms allow proxying video through a Worker (the 2026-09 terms are unclear) | Serve media LAN-direct through a media origin not proxied by Cloudflare; media URLs have been replaceable since 0.3 ([open question](../process/2026-10-07-cloudflare-video-terms.md)) | The owner, before 1.0 goes public |
| 3 | Self-hosted software may ship a TMDB API key | Each owner registers a key, one more install step | Before 0.5 |
| 4 | An interface designed from two source plugins holds for later plugins | The interface stays experimental until 1.0; 0.5 and 0.6 add four plugins to test it | Continuously from 0.2 to 1.0 |
