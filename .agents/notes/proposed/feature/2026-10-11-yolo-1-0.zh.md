# Agent Note: Yolo 1.0 和通往它的路线

Status: proposed

[English](2026-10-11-yolo-1-0.md) | 中文

## 问题

Yolo 0.4.0 已经能为一位用户本人工作，另一位用户本人的 agent（智能体）也能替他部署。Cloudflare 上的控制面和 Mac 上的媒体节点服务一个播放器：它在车上用 canvas 引擎播放，在其他任何浏览器（包括 iPhone）里用 `<video>` 引擎播放（[两个引擎](../../implemented/architecture/2026-10-12-two-playback-engines.zh.md)）；在家时媒体流直接来自节点（[局域网直连播放](../../implemented/feature/2026-10-12-lan-direct-play.zh.md)）；Plex 和网页视频都是插件；Yolo 在各设备间保存一份带续播的历史记录、一条队列和播放列表（[进度和续播](../../implemented/feature/2026-10-11-yolo-owns-progress-and-resume.zh.md)）；agent 通过 MCP 驱动它（[远程 MCP 服务](../../implemented/feature/2026-10-07-remote-mcp-server.zh.md)）；agent 还能从打了标签的版本部署、升级和回退一个实例（[agent 部署](../../implemented/feature/2026-10-13-agent-deployment.zh.md)、[版本和发布](../../implemented/process/2026-10-13-versions-and-releases.zh.md)）。

截至 2026-10-13，有四个缺口让 Yolo 还不能推荐给别人：

- **离家时媒体流经过 Worker。** 离家时每条流都经 Worker 的中转两次穿过 Cloudflare，受中转 4.8 Mbps 的上限约束，还消耗用户本人的 Workers 请求数；而从节点出发的直连路径到达屏幕更快，也不占用 Cloudflare 的带宽（[媒体流离开 Worker](../../implemented/architecture/2026-10-13-media-off-the-worker.zh.md)）。
- **片源离不开 Plex 或 yt-dlp。** 只有 yt-dlp 插件认领 URL，所以直接的 `.mp4` 或 `.m3u8` 链接仍然需要它，DASH manifest 则无路可走；节点读不了本地文件，所以没有 Plex 时 NAS 上的文件放不了。
- **安全阻断问题。** passkey 登录后的开放重定向、Workers Logs 里的媒体 token 和配对码，以及 canvas 引擎对失败分片的无限重试。
- **仓库还背着历史包袱。** 已经退役的 Drive-In 名字还出现在当前文档和设置里，好几份记录和代码对不上。

没有一个把这些缺口补上的 1.0 定义，接下来的版本就没有共同目标，可以等的工作（推荐、电视和手机 App、多用户家庭）也会和不能等的工作争抢精力。

## 提案

### Yolo 是什么

Yolo 是**面向 agent 时代的娱乐画布**：

- **由 agent 驱动。** ChatGPT、Claude 和 Codex 通过 MCP 替用户搜索、播放和控制播放。
- **一个播放器让用户摆脱各平台的限制。** 它在车上用 canvas 引擎，在网页上用 `<video>` 引擎；电视和手机以后再做。
- **不强制任何片源。** Plex 和 yt-dlp 跟其他插件一样只是插件；Vimeo、任何 CDN 上的直链和 NAS 上的文件都通过片源插件播放。
- **它像 Plex 一样保存用户的状态：** 历史记录、续播、队列和播放列表，所有设备共享。
- **它由插件组成。** 片源、协议服务（例如兼容 Jellyfin 的 API）、代理和推荐订阅源都可以是社区插件。
- **它的 D1 模型健康、可扩展：** 每一行都按用户归属，没有任何东西绑死在某一个片源上，并为片库目录和新的条目类型留有余地。
- **以后，推荐跑在用户自己的订阅上。** Yolo 保存状态（关注列表、收件箱）并提供 MCP 工具；用户自己的 ChatGPT 或 Codex agent 按计划完成思考。

### 决定

- **1.0 时媒体流离开 Worker。** 经 Worker 中转时，离家的每条流都要两次穿过 Cloudflare，受 4.8 Mbps 的上限约束，还消耗用户本人的 Workers 请求数；而从节点出发的直连路径到达屏幕更快，也不占用 Cloudflare 的带宽。因此媒体流走第一条能用的直连路径：局域网直连播放；然后是远程直连播放，即经路由器端口（由节点自己映射）到达一个带正式证书的仅 DNS 名字（覆盖用 LTE 的车）。每个实例都是一个人自己的 Cloudflare 账号，供个人使用，所以中转是一条正常的、受支持的路径，也是回退路径：在默认模式 `auto` 下，只有某块屏幕没有任何直连路径能用时，中转才承载它的媒体流，一条流开始时如此，一条直连流中途失败、在同一位置恢复时也如此；`on` 允许中转作为最后一条路径，`off` 则从不中转。R2 暂存是一条全在 Cloudflare 内、从存储播放的路径，给无法做端口转发的用户本人，推迟再做。设计见[媒体流离开 Worker](../../implemented/architecture/2026-10-13-media-off-the-worker.zh.md)。
- **对外身份是 HaitianLiu5：** 仓库、版权持有人、包的作者和代码所有者都用它。
- **所有包用同一个版本号，从 0.4.0 开始，** 每次发布是一个 `vX.Y.Z` git 标签，并在 [`CHANGELOG.md`](../../../../CHANGELOG.md) 里有一条记录（[版本和发布](../../implemented/process/2026-10-13-versions-and-releases.zh.md)）。下面的每个版本都是这样的一次发布。
- **Drive-In 这个名字退役。** 车上的是播放器的车机 profile，「特斯拉」只指车本身和它的浏览器。

### 版本

每个版本都是一次打了标签、能单独使用的发布：就算下一个版本一直没发布，系统也是完整的。每一项只评估复杂度（低、中、高）并写明主要难点，从不估时间。

#### 朋友预览

朋友预览是第一个让用户本人可以请朋友试用 Yolo 的打标签版本。它需要 0.4 这条线和 0.5 里的一项，别的都不需要：

1. 朋友自己注册并持有 Cloudflare 账号和域名；用户本人从不替他注册，Cloudflare 的协议也禁止这样做（第 2.2.1(a) 节）。
2. 朋友的 agent 在该版本标签的全新克隆里用 [`yolo-deploy`](../../../../skills/yolo-deploy/SKILL.md) 完成部署，只在它列出的检查点停下，`yolo doctor` 通过；之后这个 agent 用 [`yolo-upgrade`](../../../../skills/yolo-upgrade/SKILL.md) 升级实例。
3. 安全阻断问题已修复，未认证路由有限速，因为朋友的实例从第一次部署起就是公开的。
4. 新实例上的中转不需要任何设置：在默认模式 `auto` 下，某块屏幕没有任何直连路径能用时，中转就承载它的媒体流。从 0.5 提前做的那一项是中转开关，它在新实例上关闭，打开时要先确认一段警告；朋友的第一次部署因此什么都放不了，因为他的网关既不响应 NAT-PMP 也不响应 UPnP，中转又是关闭的；三种模式取代了这个开关。在家时朋友通过局域网直连播放；离家时，远程直连播放能用就走它，其他情况走中转。
5. CI 通过，朋友读到或运行的任何东西都不带用户本人的域名、资源 id 或 Drive-In 这个名字。
6. 朋友的片源和 0.4 一样是 Plex 或 yt-dlp；README 写明预览版的局限，并请朋友通过 GitHub issue 反馈问题。

## 曾考虑的替代方案

**Worker 中转继续作为第一条媒体路径。** 它不需要任何设置、在哪里都能用，但即使节点在家里或经路由器就能直达屏幕，每条流也都要两次穿过 Cloudflare，受 4.8 Mbps 的上限约束，并消耗用户本人的 Workers 请求数；作为回退路径，中转只承载没有任何直连路径能承载的流（[媒体流离开 Worker](../../implemented/architecture/2026-10-13-media-off-the-worker.zh.md)）。

**用 Tailscale 作为媒体路径。** 它不用端口转发就能让离家的手机和电脑播放，但每台设备都要安装并登录 Tailscale，而特斯拉的浏览器根本运行不了它；远程直连不用安装任何东西就能到达每块屏幕，包括车（[媒体流离开 Worker](../../implemented/architecture/2026-10-13-media-off-the-worker.zh.md)）。

**给 Apple 设备做 Jellyfin 协议插件。** [已否决](../../rejected/feature/2026-10-11-jellyfin-protocol-plugin.zh.md)：Infuse 不接受遥控命令，Swiftfin 的遥控还没验证，两者都显示不了 Yolo 的弹幕、AI 字幕和 Ask；[Apple TV 客户端](2026-10-19-apple-tv-client.zh.md)讲 Yolo 自己的协议。

**先做自己的片库，再摆脱 yt-dlp。** 节点既读不了本地文件，也做不了 remux，所以文件夹和 WebDAV 片源要建立在 0.6 的本地文件 Input 和 remux 之上；而直接 URL 片源能以很低的代价让 yt-dlp 变成可选。

**先做安装包和设置向导，再做 agent 部署。** Yolo 由 agent 部署，所以先要有可重复执行、带检查点的命令；向导和安装包在 0.9 里包装同样的命令。

**把原生 App 作为 1.0 的标准。** 1.0 覆盖的是车和网页。[Apple TV 客户端](2026-10-19-apple-tv-client.zh.md)只需要[客户端协议](../architecture/2026-10-19-client-protocol.zh.md)的服务端部分，这部分很小，会先于它发布，所以做好了就发布，不拖 1.0 的后腿；它通过 TestFlight 装到用户本人自己的设备上，通过 App Store 分发给其他用户本人要等 App 审核（条款 2.1 和 5.2.3）。

**为第三方客户端模拟 Plex 服务端。** [已否决](../../rejected/architecture/2026-10-11-emulate-a-plex-media-server.zh.md)：plex.tv 的认领机制和 Plex 的条款都不允许。

## 验收标准

1. **朋友的 agent 能部署和升级它。** 在 1.0 标签的全新克隆里，替新用户本人工作的 agent 用随附的 skill、`yolo doctor` 和被忽略的实例文件，把 Yolo 部署到这位用户本人的 Cloudflare 账号和域名上，只在 skill 列出的检查点停下；之后它先展示更新日志里的升级块请对方批准，再升级到下一个版本并回退。没有任何被跟踪的文件保存实例的值。
2. **媒体流不依赖 Worker 中转。** 只要有直连路径能用，就没有流走中转，车在 LTE 上通过远程直连播放四种流类型（`hls`、`direct`、`dash_split`、`plex`）；没有直连路径能用时，中转承载这条流，从它开始时承载，或从一条直连流失败的位置接着承载；[媒体流离开 Worker](../../implemented/architecture/2026-10-13-media-off-the-worker.zh.md) 的验收标准都成立。
3. **yt-dlp 是可选的。** 没有 yt-dlp 插件、也没装 yt-dlp 程序时，任意 CDN 上的 `.mp4`、`.m3u8` 和 `.mpd` 直链都能在两个 profile 里播放，并带有标题和时长。
4. **本地和 NAS 文件能播放。** 没有 Plex 的用户本人在两个 profile 里播放本地文件夹和 NAS 共享里的电影和剧集，带海报和简介，其中包括一个需要 remux 的文件和一个需要转码的文件，拖动、续播和历史记录都正常。
5. **安全阻断问题已修复，** 每个都有回归测试；未认证路由有限速；面向互联网的部分，即 Worker 的路由和节点的远程监听端口，有记录在案的安全审查。
6. **仓库是干净的。** CI 在包支持的每个 Node 版本上通过；每个包都带着这次发布的版本号；Drive-In 这个名字只出现在归档记录和一行来历说明里；没有被跟踪的文件带着用户本人的域名或资源 id；一版本兼容的旧名字已经删掉；贡献者指南能把新人带到浏览器里播放起来。
7. **1.0 表格里的其余各行** 对按公开说明操作的新用户本人都成立：续播和已看状态不受历史长度影响，并跨片源跟随条目；MCP 覆盖队列、播放列表、历史记录和设置；`@useyolo/plugin-api` 1.0 已发布，带文档、示例插件和一致性测试套件。

## 风险

| # | 假设 | 不成立时怎么办 | 谁在什么时候验证 |
|---|---|---|---|
| 1 | 大多数用户本人能把一个端口转发到节点 | 在运营商级 NAT 之后或没有路由器权限时，离家的每块屏幕都经中转播放，受它 4.8 Mbps 的上限约束，并消耗用户本人的 Workers 请求数；R2 暂存提前到其他 1.x 工作之前 | 从 0.5 起最早几位朋友实例的 `edge` 遥测，以及设置和 `doctor` 里的中转流数量 |
| 2 | 车的浏览器在 LTE 上能连到家里地址上被转发的端口 | 转发外部端口 443，或者在车的网络有 IPv6 时依靠 IPv6 | 0.5 期间，由用户本人在车上用 LTE 实测 |
| 3 | 自托管软件可以内置 TMDB 的 API key | 每个用户本人自己申请一个 key，设置时多一步 | 开始 0.7 之前 |
| 4 | 根据片源和元数据插件冻结的插件 API，能撑住协议、设备、订阅源和代理插件 | 它们的接口作为新增的小版本加入；真要破坏性改动就等 2.0 | 第一个协议或设备插件开始时 |
| 5 | Workers VPC 在测试期结束后仍然可用，价格也合适 | `NODE_TRANSPORT=tunnel`，不用改代码；媒体流离开 Worker 之后，只有控制流量依赖它 | Cloudflare 公布价格时 |
| 6 | Cloudflare 的条款保持 2026-10-14 时的内容 | 媒体流那份记录、中转的默认模式和 README 都跟着新条款改 | 每当 Cloudflare 更新条款时，以及 1.0 之前 |
