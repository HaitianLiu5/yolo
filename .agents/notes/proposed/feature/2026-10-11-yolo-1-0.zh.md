# Agent Note: Yolo 1.0 和通往它的路线

Status: proposed

[English](2026-10-11-yolo-1-0.md) | 中文

## 问题

Yolo 0.4.0 已经能为一位用户本人工作，另一位用户本人的 agent（智能体）也能替他部署。Cloudflare 上的控制面和 Mac 上的媒体节点服务一个播放器：它在车上用 canvas 引擎播放，在其他任何浏览器（包括 iPhone）里用 `<video>` 引擎播放（[两个引擎](../../implemented/architecture/2026-10-12-two-playback-engines.zh.md)）；在家时媒体流直接来自节点（[局域网直连播放](../../implemented/feature/2026-10-12-lan-direct-play.zh.md)）；Plex 和网页视频都是插件；Yolo 在各设备间保存一份带续播的历史记录、一条队列和播放列表（[进度和续播](../../implemented/feature/2026-10-11-yolo-owns-progress-and-resume.zh.md)）；agent 通过 MCP 驱动它（[远程 MCP 服务](../../implemented/feature/2026-10-07-remote-mcp-server.zh.md)）；agent 还能从打了标签的版本部署、升级和回退一个实例（[agent 部署](../../implemented/feature/2026-10-13-agent-deployment.zh.md)、[版本和发布](../../implemented/process/2026-10-13-versions-and-releases.zh.md)）。

截至 2026-10-13，有四个缺口让 Yolo 还不能推荐给别人：

- **离家时媒体流经过 Worker。** Cloudflare 的条款很可能限制在被代理的主机名上提供托管在 Cloudflare 之外的视频，而每位用户本人都要在自己的账号上承担这个风险（[媒体流离开 Worker](../architecture/2026-10-13-media-off-the-worker.zh.md)）。
- **片源离不开 Plex 或 yt-dlp。** 只有 yt-dlp 插件认领 URL，所以直接的 `.mp4` 或 `.m3u8` 链接仍然需要它，DASH manifest 则无路可走；节点读不了本地文件，所以没有 Plex 时 NAS 上的文件放不了。
- **安全阻断问题。** passkey 登录后的开放重定向、Workers Logs 里的媒体 token 和配对码，以及 canvas 引擎对失败分片的无限重试。
- **仓库还背着历史包袱。** 已经退役的 Drive-In 名字还出现在当前文档和设置里，好几份记录和代码对不上。

没有一个把这些缺口补上的 1.0 定义，接下来的版本就没有共同目标，可以等的工作（推荐、电视和手机 App、多用户家庭）也会和不能等的工作争抢精力。

## 提案

### Yolo 是什么

Yolo 是**面向 agent 时代的娱乐画布**：

- **由 agent 驱动。** ChatGPT、Claude 和 Codex 通过 MCP 替用户搜索、播放和控制播放。
- **一个播放器让用户摆脱各平台的限制。** 它在车上用 canvas 引擎，在网页上用 `<video>` 引擎；电视和手机以后再做。
- **不强制任何片源。** Plex 和 yt-dlp 跟其他插件一样只是插件；Vimeo、任何 CDN 上的直链和 NAS 上的文件都通过片源插件播放。
- **它像 Plex 一样保存用户的状态：** 历史记录、续播、队列和播放列表，所有设备共享。
- **它由插件组成。** 片源、协议服务（给 Infuse 和 Apple TV 用的兼容 Jellyfin 的 API）、代理和推荐订阅源都可以是社区插件。
- **它的 D1 模型健康、可扩展：** 每一行都按用户归属，没有任何东西绑死在某一个片源上，并为片库目录和新的条目类型留有余地。
- **以后，推荐跑在用户自己的订阅上。** Yolo 保存状态（关注列表、收件箱）并提供 MCP 工具；用户自己的 ChatGPT 或 Codex agent 按计划完成思考。

### 1.0

| 方面 | 1.0 的状态 |
|---|---|
| 部署 | 有 Cloudflare 账号和域名的用户本人，让自己的 agent 用随附的 skill、`yolo doctor` 和被忽略的实例文件，从打了标签的版本部署 Yolo，之后再按更新日志升级和回退。用户本人只在 skill 列出的检查点动手：Cloudflare 登录、域名、passkey 和路由器 |
| 媒体流 | Worker 只承载控制：登录、片库目录、token、Hub 和 MCP。媒体流通过局域网直连播放、经端口转发的远程直连播放或 Tailscale 从节点直达设备；除非用户本人打开，Worker 中转一直关闭 |
| 片源 | 任何 CDN 上的直接 URL（`.mp4`、`.webm`、`.m3u8`、`.mpd`）、本地和 NAS 文件夹、WebDAV，以及可选的 Plex 和 yt-dlp；每一种都是一个插件 |
| 片库 | 电影和剧集带海报和简介；每个条目一个续播位置和已看状态，跨设备、跨片源；完整的历史记录；一条队列；播放列表 |
| 客户端 | 播放器：在特斯拉浏览器里是它的车机 profile（canvas 引擎），在其他任何浏览器（包括 iPhone）里是它的 web profile（`<video>` 引擎） |
| agent | ChatGPT、Claude 和 Codex 通过 MCP 搜索、播放、控制，并管理队列、播放列表、历史记录和设置 |
| 插件 | `@useyolo/plugin-api` 1.0，按 semver 发布，有文档、示例插件和一致性测试套件 |
| 使用模式 | 一个用户本人、多台设备，同一时间只有一台在播 |

1.0 不做：电视和手机 App 以及兼容 Jellyfin 的协议；多用户家庭、家庭成员档案和分享；音乐、播客和有声书；推荐；[不依赖 Cloudflare 的自托管](../architecture/2026-10-07-self-hosting-without-cloudflare.zh.md)；离线下载、直播电视和 IPTV；在节点里实现 SMB 或 NFS 客户端；以及插件隔离。

```
                 │ Workers VPC (nodeFetch)             │ WebSocket / HTTP
                 ▼                                     ▼
 Media node (Mac, or Docker on a NAS)            Player

 │       /m/{token}/* sessions                   └ web profile (<video> engine)
 ├ Plugins: sources (direct URL, folder,                ▲
 │   WebDAV, Plex, yt-dlp), metadata (TMDB)             │ media
 └ Media listeners ─────────────────────────────────────┘
     first path that works: LAN direct, remote direct, Tailscale
```

### 决定

- **1.0 时媒体流离开 Worker。** Cloudflare 的 CDN 条款写道：「除非你是 Enterprise 客户，Cloudflare 提供特定的付费服务（例如 Developer Platform、Images 和 Stream），你必须使用它们才能经 CDN 提供视频和其他大文件」（[服务专属条款：应用服务](https://www.cloudflare.com/service-specific-terms-application-services/)，2026-09-28 更新）。Cloudflare 的解释还说「托管在 Cloudflare 之外的视频和大文件，在我们的 CDN 上仍受限制」（[博客，2023-05-16](https://blog.cloudflare.com/updated-tos/)），它的文档把这条限制用于公开主机名，只豁免私有网络路由（[视频交付](https://developers.cloudflare.com/fundamentals/reference/policies-compliances/delivering-videos-with-cloudflare/)）。Yolo 的视频托管在用户本人的节点上，却在 Worker 的公开主机名上提供。因此 Worker 只保留控制，媒体流走第一条能用的路径：局域网直连播放；然后是远程直连播放，即路由器把端口转发到一个带正式证书的仅 DNS 名字上（覆盖用 LTE 的车）；再然后是给手机和电脑用的 Tailscale。中转保留，但默认关闭，并配有直白的警告；R2 暂存是全在 Cloudflare 内的合规路径，推迟再做；用户本人也可以向 Cloudflare 支持要一份书面答复。设计见[媒体流离开 Worker](../architecture/2026-10-13-media-off-the-worker.zh.md)。
- **对外身份是 HaitianLiu5：** 仓库、版权持有人、包的作者和代码所有者都用它。
- **所有包用同一个版本号，从 0.4.0 开始，** 每次发布是一个 `vX.Y.Z` git 标签，并在 [`CHANGELOG.md`](../../../../CHANGELOG.md) 里有一条记录（[版本和发布](../../implemented/process/2026-10-13-versions-and-releases.zh.md)）。下面的每个版本都是这样的一次发布。
- **Drive-In 这个名字退役。** 车上的是播放器的车机 profile，「特斯拉」只指车本身和它的浏览器。

### 版本

每个版本都是一次打了标签、能单独使用的发布：就算下一个版本一直没发布，系统也是完整的。每一项只评估复杂度（低、中、高）并写明主要难点，从不估时间。

#### 朋友预览

朋友预览是第一个让用户本人可以请朋友试用 Yolo 的打标签版本。它需要 0.4 这条线和 0.5 里的一项，别的都不需要：

1. 朋友自己注册并持有 Cloudflare 账号和域名；用户本人从不替他注册，Cloudflare 的协议也禁止这样做（第 2.2.1(a) 节）。
2. 朋友的 agent 在该版本标签的全新克隆里用 [`yolo-deploy`](../../../../skills/yolo-deploy/SKILL.md) 完成部署，只在它列出的检查点停下，`yolo doctor` 通过；之后这个 agent 用 [`yolo-upgrade`](../../../../skills/yolo-upgrade/SKILL.md) 升级实例。
3. 安全阻断问题已修复，未认证路由有限速，因为朋友的实例从第一次部署起就是公开的。
4. 新实例上中转是关闭的，打开它时会显示那段直白的警告：这是 0.5 里低复杂度的中转开关，提前做。在家时朋友通过局域网直连播放；离家时，在 0.5 发布之前只能经中转，而且只能由朋友自己决定打开。
5. CI 通过，朋友读到或运行的任何东西都不带用户本人的域名、资源 id 或 Drive-In 这个名字。
6. 朋友的片源和 0.4 一样是 Plex 或 yt-dlp；README 写明预览版的局限，并请朋友通过 GitHub issue 反馈问题。

| 项目 | 复杂度 | 主要难点 |

## 曾考虑的替代方案

**Worker 中转继续作为默认的媒体路径。** 它不需要任何设置，但在 Free、Pro 和 Business 区域上很可能不符合 Cloudflare 的条款，在 Workers Free 上则明确不符合，而且每位朋友都要在自己的账号上承担这个风险（[媒体流离开 Worker](../architecture/2026-10-13-media-off-the-worker.zh.md)）。

**1.0 就做 Jellyfin 协议插件。** 这是通往 Apple TV 和 iPhone 播放器最省事的路，但 1.0 覆盖的是车和网页。这个插件需要的宿主功能（控制面路由、插件存储、Hub 里的设备接口）没有一条 1.0 标准用得上，而它的前提，即 Swiftfin 的遥控，还没有验证。这些功能是在插件 API 上新增，不会破坏它，所以可以放到 1.0 之后。

**先做自己的片库，再摆脱 yt-dlp。** 节点既读不了本地文件，也做不了 remux，所以文件夹和 WebDAV 片源要建立在 0.6 的本地文件 Input 和 remux 之上；而直接 URL 片源能以很低的代价让 yt-dlp 变成可选。

**先做安装包和设置向导，再做 agent 部署。** Yolo 由 agent 部署，所以先要有可重复执行、带检查点的命令；向导和安装包在 0.9 里包装同样的命令。

**1.0 就做原生 App。** 原生 App 要通过 App 审核（条款 2.1 和 5.2.3），每年还要维护；电视和手机在 1.0 之后再做，先通过 Jellyfin 协议接入（[Jellyfin 提案](2026-10-11-jellyfin-protocol-plugin.zh.md)）。

**为第三方客户端模拟 Plex 服务端。** [已否决](../../rejected/architecture/2026-10-11-emulate-a-plex-media-server.zh.md)：plex.tv 的认领机制和 Plex 的条款都不允许。

## 验收标准

1. **朋友的 agent 能部署和升级它。** 在 1.0 标签的全新克隆里，替新用户本人工作的 agent 用随附的 skill、`yolo doctor` 和被忽略的实例文件，把 Yolo 部署到这位用户本人的 Cloudflare 账号和域名上，只在 skill 列出的检查点停下；之后它先展示更新日志里的升级块请对方批准，再升级到下一个版本并回退。没有任何被跟踪的文件保存实例的值。
2. **媒体流不依赖 Worker 中转。** 新实例上中转是关闭的；车在 LTE 上通过远程直连播放四种流类型（`hls`、`direct`、`dash_split`、`plex`）；离家的手机通过 Tailscale 播放；[媒体流离开 Worker](../architecture/2026-10-13-media-off-the-worker.zh.md) 的验收标准都成立。
3. **yt-dlp 是可选的。** 没有 yt-dlp 插件、也没装 yt-dlp 程序时，任意 CDN 上的 `.mp4`、`.m3u8` 和 `.mpd` 直链都能在两个 profile 里播放，并带有标题和时长。
4. **本地和 NAS 文件能播放。** 没有 Plex 的用户本人在两个 profile 里播放本地文件夹和 NAS 共享里的电影和剧集，带海报和简介，其中包括一个需要 remux 的文件和一个需要转码的文件，拖动、续播和历史记录都正常。
5. **安全阻断问题已修复，** 每个都有回归测试；未认证路由有限速；面向互联网的部分，即 Worker 的路由和节点的远程监听端口，有记录在案的安全审查。
6. **仓库是干净的。** CI 在包支持的每个 Node 版本上通过；每个包都带着这次发布的版本号；Drive-In 这个名字只出现在归档记录和一行来历说明里；没有被跟踪的文件带着用户本人的域名或资源 id；一版本兼容的旧名字已经删掉；贡献者指南能把新人带到浏览器里播放起来。
7. **1.0 表格里的其余各行** 对按公开说明操作的新用户本人都成立：续播和已看状态不受历史长度影响，并跨片源跟随条目；MCP 覆盖队列、播放列表、历史记录和设置；`@useyolo/plugin-api` 1.0 已发布，带文档、示例插件和一致性测试套件。

## 风险

| # | 假设 | 不成立时怎么办 | 谁在什么时候验证 |
|---|---|---|---|
| 1 | 大多数用户本人能把一个端口转发到节点 | 在运营商级 NAT 之后或没有路由器权限时，手机和电脑用 Tailscale，车只能由用户本人选择是否用中转；R2 暂存提前到其他 1.x 工作之前 | 0.5 期间，看最早几位朋友实例的 `edge` 遥测 |
| 2 | 车的浏览器在 LTE 上能连到家里地址上被转发的端口 | 转发外部端口 443，或者在车的网络有 IPv6 时依靠 IPv6 | 0.5 期间，由用户本人在车上用 LTE 实测 |
| 3 | 自托管软件可以内置 TMDB 的 API key | 每个用户本人自己申请一个 key，设置时多一步 | 开始 0.7 之前 |
| 4 | 根据片源和元数据插件冻结的插件 API，能撑住协议、设备、订阅源和代理插件 | 它们的接口作为新增的小版本加入；真要破坏性改动就等 2.0 | Jellyfin 插件开始时 |
| 5 | Swiftfin 在 tvOS 上能可靠执行遥控命令 | 做一个讲同一套 Jellyfin 会话协议的原生 tvOS App；这会把 Swift 引入项目，需要用户本人另外批准 | 开始 Jellyfin 插件之前，用用户本人的 Apple TV 实测 |
| 6 | Workers VPC 在测试期结束后仍然可用，价格也合适 | `NODE_TRANSPORT=tunnel`，不用改代码；媒体流离开 Worker 之后，只有控制流量依赖它 | Cloudflare 公布价格时 |
| 7 | Cloudflare 的条款在 2026-10-13 的解读保持不变 | 中转的警告、媒体流那份记录和 README 都跟着新条款改 | 每当 Cloudflare 更新条款时，以及 1.0 之前 |
