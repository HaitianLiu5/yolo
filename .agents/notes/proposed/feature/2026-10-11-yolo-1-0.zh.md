# Agent Note: Yolo 1.0 和通往它的路线

Status: proposed

[English](2026-10-11-yolo-1-0.md) | 中文

## 问题

Yolo 现在已经能为一位用户本人工作：Cloudflare 上的控制面、Mac 上的媒体节点、Plex 和网页视频两种片源、特斯拉客户端，以及通过 MCP 接入的 agent（智能体）。没有对 1.0 的定义，接下来的版本就没有共同的目标，不属于它的功能（多用户、音乐、原生 App）也会和真正该做的功能争抢精力。

## 提案

Yolo 1.0 是一套自托管的私人媒体服务。它像 Plex 一样，从片源、片库一直覆盖到各端播放；不同的是，它由 agent 驱动，还能在特斯拉浏览器里用 canvas 播放。

| 方面 | 1.0 的状态 |
|---|---|
| 安装 | 一个 Cloudflare 账号，以及一台能跑 Docker 的 NAS 或电脑，或者一台 Mac。一条命令部署控制面；装好媒体节点后，用户本人用节点打印的码注册 passkey |
| 片源 | NAS 或本地文件夹（节点直接跑在 NAS 上，或者把 SMB/NFS 共享挂载到节点所在的机器）、WebDAV、Plex（可选）、网页视频链接（yt-dlp）；每一种都是一个插件 |
| 片库 | 电影和剧集带海报和简介；所有客户端共享一份进度和观看记录；一条 Spotify 式队列；播放列表；历史记录 |
| 客户端 | 特斯拉：Drive-In。任意浏览器：Yolo Web。iPhone、iPad、Apple TV、Mac：Infuse 用来手动播放，Swiftfin 可以被 agent 遥控。Android 上的 Jellyfin 客户端应该可用，但不做保证 |
| agent | ChatGPT、Claude 和 Codex 通过 MCP 搜索、播放、控制，管理队列和设置；不管设备讲哪种协议，在它们看来都一样 |
| 插件 | 有文档和示例插件、对社区开放的插件 API |
| 使用模式 | 一个用户本人、多台设备，同一时间只有一台在播 |

1.0 不做：多用户家庭、家庭成员档案和分享给朋友；音乐、播客、有声书和 Spotify；原生 iOS、tvOS 和 Android App（只有 Swiftfin 的遥控被证明不可靠时才做原生 tvOS App，见「风险」）；[不依赖 Cloudflare 的自托管](../architecture/2026-10-07-self-hosting-without-cloudflare.zh.md)；离线下载、直播电视和录像、IPTV；在节点里实现 SMB/NFS 客户端；官方的 Plex 协议插件；遥控 Infuse；以及插件权限系统。

```
              ChatGPT / Claude / Codex
                       │ MCP + OAuth
                       ▼
 ┌──────────── Control plane (Cloudflare Worker) ────────────┐
 │ Core: MCP, /v1, OAuth, Hub DO (devices/queue/state), D1     │
 │ Plugins (bundled at deploy): protocols (Jellyfin…), devices │
 └──────────┬──────────────────────────────┬──────────────────┘
            │ Workers VPC (nodeFetch)       │ WebSocket / HTTP
            ▼                              ▼
 Media node (Mac, or Docker on a NAS)   Clients
 ├ Core: transcoding, HLS, subtitles,   ├ Drive-In (Tesla canvas)
 │       signed /m/* streams            ├ Yolo Web (browser)
 └ Plugins (loaded at start):           ├ Swiftfin (agent remote)
   sources (folder, WebDAV, Plex,       └ Infuse (manual)
   yt-dlp), metadata (TMDB), device LAN halves
            └── media: through the Worker, LAN-direct at home ──┘
```

### 版本

每个版本发布后都能单独使用：就算下一个版本一直做不完，系统也是完整的。路线图只评估复杂度（低、中、高）并写明难点，不估时间。

| 版本 | 主题 | 交付什么 | 复杂度 | 难点 |
|---|---|---|---|---|
| 0.1（已完成） | 控制面和 MCP | agent 通过 Yolo 控制车上的播放；片源是 Plex 和网页 URL | — | — |
| 0.2（已完成） | 插件框架 | Plex 和 yt-dlp 改为[插件](../../implemented/architecture/2026-10-11-plugin-architecture.zh.md)；核心里不再有 `url` 片源类型和 yt-dlp | 高 | 两个运行环境共用一套 API；部署时打包；把 Plex 和 yt-dlp 从三层代码里拆干净 |
| 0.3（已完成） | Drive-In 完全迁到 Yolo | [媒体管线](../../implemented/architecture/2026-10-11-node-media-pipeline.zh.md)搬进节点；特斯拉客户端改用 v1 并支持[扫码配对](../../implemented/feature/2026-10-07-device-code-pairing.zh.md)；[进度归 Yolo 管](../../implemented/feature/2026-10-11-yolo-owns-progress-and-resume.zh.md)；删掉旧服务和 CLI | 高 | 要迁的代码多，特斯拉相关行为不能退化；四种流类型要在车上验证；要迁移数据 |
| 0.4 | [Yolo Web](2026-10-11-yolo-web-client.zh.md) | 浏览器客户端和设置页 | 中 | 主要是新界面；播放引擎和实时通道复用 |
| 0.5 | [自己的片库和 NAS](2026-10-11-own-library-and-nas.zh.md) | 文件夹、WebDAV 和 TMDB 插件；D1 里的片库目录；节点的 Docker 镜像 | 高 | NAS 环境各不相同；文件命名的边界情况；低端 NAS 上的转码 |
| 0.6 | [Jellyfin 协议插件](2026-10-11-jellyfin-protocol-plugin.zh.md) | Infuse 和 Swiftfin 连接 Yolo；agent 遥控 Swiftfin | 中高 | 约 40–60 个端点和 Infuse 的各种特殊行为；没有现成的会话推送实现；必须用真机验证 |
| 0.7 → 1.0 | [分发给其他用户](2026-10-11-distribution-to-other-owners.zh.md) | 一条命令部署、安装包、首次设置向导、`yolo install`、文档和 `useyolo.app` 网站 | 中 | 工作面宽但不深：要在多个平台上打包和测试 |

一阶段是 0.2、0.3 和 0.4 合在一起（2026-10-11 定）：打好架构基础，并把开发迁到 `HaitianLiu5/yolo`。它剩下的部分是 Yolo Web 和下线 Drive-In 对外的部分（[一个仓库](../../implemented/process/2026-10-07-one-yolo-repository.zh.md)）。一阶段不做 NAS 和文件夹片源、WebDAV、TMDB、Jellyfin 协议、Apple 设备、给别人用的安装包和多用户。

### 1.0 的官方插件

| 类型 | 插件 | 运行在 |
|---|---|---|
| 片源 | 文件夹（本地和 NAS） | 节点 |
| 片源 | WebDAV | 节点 |
| 片源 | Plex | 节点 |
| 片源 | yt-dlp | 节点 |
| 元数据 | TMDB | 节点 |
| 协议 | 兼容 Jellyfin 的 API | 控制面（API、会话推送）和节点（媒体流） |

Yolo 自己的实时通道（Drive-In、Yolo Web）留在核心里；设备插件的接口等第一个第三方设备出现时再定。

## 曾考虑的替代方案

**1.0 就做原生 App。** Apple 设备改为通过兼容 Jellyfin 的协议接入：原生 App 要通过 App 审核（条款 2.1 和 5.2.3），每年还要维护（[Jellyfin 提案](2026-10-11-jellyfin-protocol-plugin.zh.md)）。

**为第三方客户端模拟 Plex 服务端。** [已否决](../../rejected/architecture/2026-10-11-emulate-a-plex-media-server.zh.md)：plex.tv 的认领机制和 Plex 的条款都不允许。

## 验收标准

新用户按发布的说明操作后，上面 1.0 表格的每一行都成立，并且表中每个版本都已发布、满足各自的验收标准。插件 API 有文档和示例插件，`useyolo.app` 网站和文档已经上线。

## 风险

| # | 假设 | 不成立时怎么办 | 谁在什么时候验证 |
|---|---|---|---|
| 1 | Swiftfin 在 tvOS 上能可靠执行遥控命令 | 0.6 之后加一个讲同一套 Jellyfin 会话协议的原生 tvOS App，服务和 MCP 不用改；这会把 Swift 引入项目，需要用户本人另外批准 | 开始 0.6 之前，用用户本人的 Apple TV 实测 |
| 2 | Cloudflare 的条款允许通过 Worker 代理视频（2026-09 版条款对此没有写清楚） | 媒体流改走局域网直连，使用一个不经 Cloudflare 代理的媒体源；从 0.3 起媒体流地址就是可以替换的（[待定问题](../process/2026-10-07-cloudflare-video-terms.zh.md)） | 1.0 公开前，由用户本人决定 |
| 3 | 自托管软件可以内置 TMDB 的 API key | 每个用户自己申请一个 key，安装时多一步 | 开始 0.5 之前 |
| 4 | 根据两个片源插件设计出来的接口，能撑住之后的插件 | 1.0 之前接口一直标为实验性；0.5 和 0.6 会再加四个插件来检验它 | 从 0.2 到 1.0 持续检验 |
