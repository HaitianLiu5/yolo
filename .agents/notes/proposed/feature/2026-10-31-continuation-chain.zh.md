# Agent Note: 播完总有下一个：每块屏幕上的接续链

Status: proposed

[English](2026-10-31-continuation-chain.md) | 中文

## 问题

一个条目播完时，Hub 先沿历史往前走，再取队列的第一项，最后取片源用 `sequence()` 给出的那一串的下一项（[接着播放](../../implemented/feature/2026-10-23-up-next.zh.md)，[`hub-core.js`](../../../../service/control/src/hub/hub-core.js)）。再往后就什么都不播了。而人看的大部分东西都不属于任何一串：

- **单个网页视频**（一个 YouTube 视频、只有一个分 P 的 B 站视频、一段新闻）没有一串，停在"已播完"。
- **agent 播的东西**也一样停下。agent 对接下来播什么没有发言权：它可以往队列里放条目，但人转去看别的之后这些条目还留在那里；它没法说"播完接着放这个频道的"，也没法说"只播这一个"。
- **剧集停在一季的末尾。** B 站番剧的一串就是它的一季（[`bilibili-bangumi.js`](../../../../plugins/source-ytdlp/src/bilibili-bangumi.js)），所以第一季最后一集播完就停了，第二季还得自己去搜。
- **Apple TV 和 iOS** 会接着播完一串，因为是 Hub 在播，但播完前没有卡片，播完后也没有结束页。

[Yolo 1.0](2026-10-11-yolo-1-0.zh.md) 承诺每个 1.0 客户端上一个条目播完都有下一个，并把顺序和候选交给这份笔记。[账号插件](2026-10-28-site-accounts.zh.md)从用户本人的关注里给出候选，[屏幕会话](../../implemented/architecture/2026-10-31-screen-sessions.zh.md)让每块屏幕有自己的队列和一串；两者都没说它们怎样合成"接下来播什么"。

## 提案

一个条目之后播什么，是一条有序的**接续链**：Hub 按屏幕会话计算，每块屏幕用同样的环节。agent 可以设定它的开头和结尾；其他环节都没有时，由家里的 agent 来挑；屏幕在条目播完前显示接下来是什么，播完后显示结束页。

### 接续链

一个条目播完时，或按"下一个"时，播第一个有条目的环节：

| # | 环节 | `from` | 来自哪里 | 类别 |
|---|---|---|---|---|
| 1 | 沿历史往前 | `history` | "上一个"退回来时经过的条目，和现在一样 | 点名要的 |
| 2 | agent 设定的下一个 | `agent` | agent 设定接在这个条目后面的条目（[见下](#what-an-agent-sets-as-next)） | 点名要的 |
| 3 | 队列 | `queue` | 这块屏幕的队列，从第一项开始 | 点名要的 |
| 4 | 那一串 | `sequence` | 正在播的条目所在的一串：agent 设了 `from` 就用它，否则用条目自己的 `sequence()` | 同一部作品 |
| 5 | 一串之后 | `sequence` | 片源在一串最后一项之后指出的下一季或下一卷（[见下](#the-run-past-its-end)） | 同一部作品 |
| 6 | 同一频道 | `by` | 这个频道或 UP 主在这一个之后发的下一个：用户本人账号里关注的频道给的（`sameBy`），否则来自片源的 `related()` | 发现 |
| 7 | 追的剧 | `continuing` | 用户本人在网站上追的每部剧的下一集，最近看过的在前（账号） | 发现 |
| 8 | 关注的更新 | `updates` | 关注的频道和 UP 主的新视频，最新的在前（账号） | 发现 |
| 9 | 相关推荐 | `related` | 片源自己给这个条目的相关列表 | 发现 |
| 10 | 家里的 agent | `agent_pick` | 家里的 agent 挑的一个条目（[见下](#the-owners-agent-picks-the-last-link)） | 发现 |
| 11 | 什么都没有 | | 结束页，带"重播"和屏幕能提供的东西 | |

队列排在一串前面，和现在一样：队列是用户本人或 agent 点名要的，等它空了再接着播一串，就像音乐播放器播完插进来的歌，再回到原来的专辑。agent 设定的下一个排在队列前面，因为它是针对这个条目、在队列排好之后才提的要求，而且只在这一段观看里有效。环节 1 到 5 是人点名要的，或他正在看的作品；环节 6 到 10 是发现，只在[防护](#autoplay-and-still-watching)允许的范围内自动播。

每个环节都会跳过不受欢迎的条目：

- **看过的。** 环节 6 到 10 跳过会话的档案在 Yolo 里标记为看过的，环节 6 到 9 还跳过账号的行认为看过而略去的（[站点账号](2026-10-28-site-accounts.zh.md#on-the-home-screen)）。
- **这段观看里播过的。** 任何环节都不播这个会话最近 4 小时播过的条目，所以互相指向的相关列表不会兜圈子。
- **播不了的。** `prepare` 失败（`resolve_failed`、`unavailable`、`not_found`）的候选会被跳过，接着播下一个；连续三个失败时，屏幕才显示失败了什么，并提供"重试"（[没有死路](2026-10-11-yolo-1-0.zh.md#five-promises)）。
- **不属于这个档案的。** 环节 6 到 8 遵守账号的档案规则：用户本人以外的档案的会话，拿不到用户本人账号列表里的候选，只拿公开列表里的（[账号和档案](2026-10-28-site-accounts.zh.md#accounts-and-profiles)）。

Hub 获取环节 1 到 5 的方式和现在一样：历史往前和队列是它自己的，一串是在条目被直接播放时在后台向节点要的。环节 6 到 9 只在环节 2 到 5 都为空时才向节点要，一次请求（`GET /internal/v1/next`，[见下](#routes-state-and-versions)），在条目开始后于后台进行，并为这个条目保留 30 分钟。环节 10 只在环节 2 到 9 都为空时才去问。所以一部剧或一个队列的请求数不比现在多。

### 一串之后

<a id="the-run-past-its-end"></a>

片源 `sequence()` 的回答增加 `next: { source, title? }`：这一串之后的第一个条目，比如一部剧的下一季、一个合集的下一卷。当一串离末尾不到 10 项时，Hub 对这个条目调用 `sequence()`，把它的一串接到后面，每一项保留自己的 `label`（"S2 · E1"），卡片写出新一串的标题。没有 `next` 的一串就到此为止，接续链继续到环节 6。

- **Plex** 已经用一次 `allLeaves` 把一部剧所有季的集列成一串，不需要 `next`。
- **B 站番剧：** 给出这一季各集的季 API，也按 B 站的顺序列出这个系列的其他季（`result.seasons`）。这个列表里夹着配音版和衍生作品（一部长篇的列表是"TV版"、"中配版"，然后是两部衍生作品），所以 `next` 是后面第一个标题不表示当前这一季配音版的条目；检查 C1 决定这个规则。
- **合集里的 B 站视频：** 一个只有一个分 P、属于 UP 主某个合集（B 站视频信息里的 `ugc_season`）的视频，以这个合集的各集为一串，按位置标注，就像多 P 视频以各个分 P 为一串。检查 C2 在节点上确认这个字段。
- **播放列表**（`list=`）在最后一个视频处结束，接续链继续往下。

### 单个网页视频

一个没有一串、没有队列、也没有 agent 设定下一个的视频，靠发现接着播：同一频道的下一个视频；开了账号插件时，再是追的剧和关注的更新；然后是片源的相关推荐；最后是家里的 agent。yt-dlp 片源为页面能给出这些的网站实现 `related()`，网站允许时不需要登录：

- **同一频道**（`why: "by"`）：这个频道或 UP 主在这一个之后发布的视频，最早的在前，取自频道视频页的扁平列表（YouTube 用 yt-dlp 的频道 tab，B 站用 UP 主空间），最多 30 个，同一频道的所有视频共用 30 分钟。
- **相关推荐**（`why: "similar"`）：网站自己的相关列表，按它的顺序：B 站的 `x/web-interface/archive/related?bvid=`（2026-10-31 不登录返回 40 个视频），以及 YouTube 观看页的相关视频（检查 C3）。

yt-dlp 能播、但 `related()` 不覆盖的网站，环节 6 和 9 为空；没有账号时，接续链走到家里的 agent，然后是结束页。一个直接的 `.mp4` 链接只有 agent 这一环。

### agent 设定的下一个

<a id="what-an-agent-sets-as-next"></a>

agent 用 `set_next`（MCP）或 `PUT /v1/playback/next` 设定一个会话接续链的开头和结尾，也可以在 `play` 上带同样的 `next` 对象，所以"播这个，然后接着放这个频道的"是一次调用：

| 字段 | 含义 |
|---|---|
| `items` | 最多 30 个条目（条目 id 或 URL），按顺序接在正在播的条目后面：环节 2 |
| `from` | 一个 URL，`items` 播完且队列为空后，接着播它里面的条目：一个播放列表、一个频道的视频页、一部剧的页面。它作为环节 4 替换条目自己的一串，通过片源的 `expand()`（合集）或 `sequence()`（一串里的一项） |
| `then` | `continue`（默认）：接续链在 agent 指定的东西之后继续。`stop`：agent 的条目和 `from` 之后不再自动播任何东西；结束页提供队列的第一项和接续链的头几个候选，都不自动播 |
| `clear` | 清除 agent 设定的内容 |

**它在这段观看里一直有效。** 接续链播放期间，agent 设定的内容留在会话上：它指定的条目、队列里的条目、一串里的条目播放时都保留它，agent 的每个条目播过就离开。有人在这块屏幕上直接播了别的（点一下、结束页的卡片、"上一个"、agent 不带 `next` 的 `play`）、会话停止、`clear`、或会话最后一次播放之后过了 4 小时，它就结束。接手时它跟着一串和队列一起转到继续这个会话的屏幕（[屏幕会话](../../implemented/architecture/2026-10-31-screen-sessions.zh.md#continue-here)）。新的 `set_next` 替换旧的，回答里说明替换了什么。

它有意和队列分开：队列里的条目一直留着，直到播放或被移除，不管人在这期间看了什么；而 agent 设定的下一个属于 agent 被要求播的那个东西，人转去看别的就消失。

状态里写明它（`next: { setBy, items, from?, then, at }`），所以每块屏幕和每个 agent 都能看到是谁设定了接下来播什么。`setBy` 是 MCP 客户端的名字；来自屏幕的请求，则是 agent 插件的名字。

### 家里的 agent 挑最后一环

<a id="the-owners-agent-picks-the-last-link"></a>

当正在播的条目的环节 2 到 9 都为空时，Hub 通过节点的 agent 插件，请家里的 agent 挑一个条目（[屏幕上的 agent](../../implemented/feature/2026-10-18-agent-from-the-screen.zh.md)）：

- **什么时候。** 每个条目一次，在它播到一半和距结束 2 分钟这两个时间点中较晚的一个，好让挑出的条目有时间提前解析；短于 4 分钟的条目立即问。
- **哪个 agent。** 这块屏幕选的那个（[`agent-choice.js`](../../../../clients/player/src/agent-choice.js)），否则是节点加载的第一个 agent 插件。没有 agent 插件时这一环为空：只用 claude.ai 或 ChatGPT 的用户看到结束页，他们的 agent 可以在播放时设定 `next`。
- **请求。** `POST /internal/v1/agents/next`：节点的 [`agents.js`](../../../../service/node/src/agents.js) 自己组装请求，内容是屏幕、档案、快结束的条目及其 URL 和详情、会话最近的五个条目，然后带着 Yolo 的 MCP 工具运行 agent，只有一条指示：挑一个接下来播的东西，用 `set_next` 设定，不要播放任何东西，用一行话说明原因。挑的结果作为 agent 设定的下一个回来，`setBy: "agent_pick"`，`upNext` 里 `from: "agent_pick"`，那一行原因显示在卡片上。
- **优先级。** 它的优先级最低：等正在运行的屏幕 Ask 结束，从不拖延 Ask；最多 60 秒；如果回答时条目已经结束超过 30 秒，就丢弃。
- **设置。** 设置 › 播放 ›"后面什么都没有时，问我的 agent"，按档案：用户本人的档案默认开，其他档案默认关，因为 agent 用的是用户本人的权限。用哪个模型、花多少，由节点的 agent 插件决定，和 Ask 一样。

条目在挑出之前就结束时，结束页显示"正在问 *agent* 接下来播什么…"和"取消"，最多 30 秒，挑出来就播；超过之后，挑的结果作为结束页的第一张卡片出现，不自动播。

### 自动播放和"还在看吗？"

<a id="autoplay-and-still-watching"></a>

每个环节都会自动播，所以车里或房间另一头的屏幕没人碰也能一直播下去。一个防护避免发现环节在没人看时连播几个小时：Hub 按会话计数，从屏幕最后一次有输入以来，环节 6 到 10 自动播了几个条目。到 3 个时，下一个本该来自环节 6 到 10 的条目不再自动播：播完前的卡片问"还在看吗？"，按钮是"继续看"而不是"立即播放"，条目播完停在结束页上，同样问这个问题。环节 1 到 5 从不被拦下：一部剧会一直播完。

输入是屏幕上的任何点按、按键或遥控器按键，屏幕在报告里以 `inputAge`（距最后一次输入的秒数）带上；也包括针对这个会话的任何命令：暂停、跳转、切换音轨字幕、"下一个"、点卡片、从这块屏幕发起的 Ask，或 agent 对它的 `play` 或 `set_next`。接手会让计数重新开始。

设置 › 播放 ›"我选的看完后继续播"，按档案，默认开；关掉后环节 6 到 10 不自动播：条目播完就停，由结束页提供它们。

### 提前准备下一个

接下来播的东西，开始得和提前准备过的历史条目一样快，而屏幕不必加载两条流：

1. **提前解析**，和现在一样：每当 `upNext` 指向另一个条目，Hub 就让节点为正在播的屏幕 `warm` 它，带上屏幕的能力和媒体路径（[节点内部 API](../../implemented/architecture/2026-10-07-node-internal-api.zh.md)）。
2. **最后 60 秒就绪：** Hub 请节点为那块屏幕把第一个候选准备成一个待用的媒体会话（`POST /internal/v1/warm`，带 `ready: true`）：片源的 `prepare` 运行，最前面的分段进入节点的分段缓存。结尾的 `load` 带着这个会话的流，屏幕从缓存开始播。每块屏幕一个待用会话；`upNext` 改变、会话转走，或 2 分钟没用，它就被丢弃。关掉卡片也会丢弃它。
3. **屏幕不提前加载任何东西。** canvas 引擎保持有界的队列和单飞的 HLS 预取（[canvas 引擎](../../implemented/architecture/2026-04-04-canvas-playback-engine.zh.md)），`<video>` 只有一个元素，用 LTE 的车不会为可能不播的条目花流量。按下时立刻显示下一个条目的画面和标题，和现在一样。

环节 6 到 9 的候选在条目开始时获取，agent 的挑选在结束前 2 分钟，所以两者都在就绪这一步之前就已知。

### 屏幕上

卡片在条目最后 20 秒显示，只限至少 90 秒长的条目，和现在一样。它说明下一个条目来自哪里，由客户端根据 `from` 翻译："下一集"、"第 2 季"、"你的 agent 设定的"、"在你的队列里"、"来自 *频道*"、"在追"、"你关注的人的新视频"、"相关"、"*agent* 挑的"并附上它的一行原因。不认识的 `from` 不显示原因这一行。正在问 agent 时，卡片显示"正在问 *agent*…"；防护拦下时，它问"还在看吗？"。

条目在屏幕上播完并停下时显示结束页：最后一帧变暗，"已播完"（防护拦下时是"还在看吗？"，`then: stop` 时是"你的 agent 说播到这里为止"），"重播"，以及一行卡片，按顺序列出接续链本来会播的东西，每张卡片标出它的环节，最多 30 个（`GET /v1/playback/up-next`）。结束页上什么都不会自动播，除了在它那 30 秒内到达的 agent 挑选。

| 屏幕 | 卡片 | 结束页 |
|---|---|---|
| 网页模式 | 画面右下角，和现在一样，加上原因一行 | 在变暗的最后一帧上，和现在一样，加上标签 |
| 车机模式 | 在驾驶员一侧，和现在一样，按钮大小适合车里（[设计原则](../../implemented/architecture/2026-07-13-in-car-design-principles.zh.md)） | 同样，在驾驶员一侧 |
| Apple TV | 播放器上下文操作（`AVPlayerViewController.contextualActions`）里的"播放下一个"按钮，也就是 tvOS 显示下一集的位置，旁边是标题和原因；传输栏菜单里的"播完这个就停"发送 `advance: false` | 播放器之后的全屏页面：变暗的画面、"重播"和那一行卡片，焦点在第一张；按选择键播它，按返回回首页 |
| iOS | 播放控件上方右下角的浮层卡片；只要有 `upNext`，锁屏和控制中心的"下一首"命令就播下一个 | 播放器之后 app 自己的页面，和 Apple TV 一样；画中画或锁屏时，接续链继续播，不显示卡片，遇到"还在看吗？"时不提示，直接停下 |

Apple TV 和 iOS 从状态读 `upNext`，从 `GET /v1/playback/up-next` 读那一行，两者都已存在；YoloKit 增加它们的类型，一致性测试套件为每一项增加场景。

### 档案和屏幕会话

接续链是屏幕会话的一部分：会话的历史往前、队列和一串已经是（[屏幕会话](../../implemented/architecture/2026-10-31-screen-sessions.zh.md#sessions-in-the-hub)），agent 设定的下一个、防护的计数、环节 6 到 10 的候选也放进去，存在 `chain:<deviceId>` 下。两块屏幕从不共用一条接续链，即使是同一个档案。接手时，agent 设定的下一个和一串随其他上下文一起复制过去，队列移过去，防护的计数重新开始。

档案决定接续链可以用什么：用它自己的看过标记来跳过，用账号的行来生成环节 6 到 8（用户本人的会话用他本人的列表，其他会话用公开列表），用它自己的设置决定 agent 挑选和发现环节的自动播放。所以客厅电视上的 Family 会话会播 Family 的下一集和片源的相关推荐，但永远不会播用户本人的关注，也不会问 agent，除非用户本人为 Family 打开了它。

### 插件提供什么

<a id="what-plugins-provide"></a>

片源插件（[片源插件 API](../../implemented/architecture/2026-10-11-source-plugin-api.zh.md#methods)），每项都是可选的：

| 新增 | 用途 | 返回 |
|---|---|---|
| `sequence()` 的 `next` | 一串之后是什么 | 回答里的 `{ source, title? }`，或没有 |
| `related(source, { limit, signal })` | 条目之后同一频道的视频和网站的相关条目，给环节 6 和 9；只在环节 2 到 5 为空时调用，节点保留 30 分钟 | `{ items: [{ source, title?, thumbnail?, duration?, by?, why }] }`，`why` 是 `by`（同一频道在这一个之后的视频，最早的在前）或 `similar`（网站的相关列表，按它的顺序），最多 `limit`（30）个 |
| `describe()` 的 `by` | 条目的频道或 UP 主 `{ title, url? }`，给账号的 `sameBy` 和卡片用 | 在 `Metadata` 里 |

Plex 可以用库条目的相似条目（`/library/metadata/{id}/similar`）回答 `related()`；文件夹片源除了它的一串之外不需要别的。

账号插件不需要新增什么：节点的 `GET /internal/v1/accounts/candidates`（[站点账号](2026-10-28-site-accounts.zh.md#what-plays-after-an-item)）为环节 6 到 8 提供 `sameBy`、`continuing` 和 `updates`。

agent 插件也不需要新增：节点自己组装挑选请求，像运行屏幕的请求一样通过 agent 插件运行它。

接续链在需要答案时去问插件，不依赖插件推送的事件：一次有序的拉取对"接下来播什么"只给一个答案，而几个插件各自推送自己的下一个会互相争抢。

### 路由、状态和版本

<a id="routes-state-and-versions"></a>

**`PlaybackState`：** `upNext` 增加新的 `from` 值（`agent`、`by`、`continuing`、`updates`、`related`、`agent_pick`）、`reason`（agent 挑选时的那一行原因）、防护拦下时的 `hold: "still_watching"`，以及问 agent 期间的 `pending: "agent_pick"`。状态增加 `next`，即 agent 设定的内容。这些都是新增字段：不认识某个 `from` 的客户端不显示原因，忽略 `hold` 的客户端显示它现在显示的卡片，而 Hub 仍然会停下这个条目。

**报告**带上 `inputAge`，即距屏幕最后一次输入的秒数；不发送它的屏幕，视为在它发出的每条命令时有过输入。

**`/v1`：**

- `GET /v1/playback/up-next` 列出接续链将要播放的全部内容，每项带 `from`，并说明 agent 设定了什么和防护的计数。
- `PUT /v1/playback/next` `{ items?, from?, then?, clear? }`，`control` 权限，设定 agent 的下一个；`POST /v1/playback/play` 接受同样的 `next` 对象。
- `GET` 和 `PATCH /v1/owner/playback` 按档案读取和修改设置：`keepGoing` 和 `askAgent`。

**节点**（[节点内部 API](../../implemented/architecture/2026-10-07-node-internal-api.zh.md)）：`GET /internal/v1/next?source=&profile=&exclude=` 一次请求回答环节 6 到 9，来自 `related()` 和账号的候选；`POST /internal/v1/agents/next` 运行挑选；`POST /internal/v1/warm` 接受 `ready: true`。每一项都是新增：旧节点回答 404 或忽略这个字段，相当于这些环节为空、warm 只做解析，所以 `NODE_PROTOCOL` 不变。

**D1：** 下一个迁移增加 `playback_settings`（`user_id`、`profile_id`（用户本人的档案为 NULL）、`keep_going`、`ask_agent`、`updated_at`），上一个版本从不读它。agent 设定的下一个和防护的计数随会话存在 Hub 的存储里，不在 D1。

**`CLIENT_PROTOCOL` 不变：** 每个字段都是新增的，网页播放器的卡片对不认识的 `from` 本来就不显示原因。

### MCP 工具

| 工具 | 变化 |
|---|---|
| `set_next`（新增，`control`） | `{ items?, from?, then?, clear?, device? }`，见[上文](#what-an-agent-sets-as-next)；回答接续链此刻的头几个条目，以及替换了什么 |
| `up_next`（新增，`read`） | `{ device?, limit? }`：接续链将要播放的内容，每项带它的环节，以及 agent 设定了什么；用于"接下来播什么？" |
| `play` | `next?`，即 `set_next` 的对象，在播放之后生效 |
| `get_status` | `upNext` 带它的环节，以及 agent 设定了什么、由谁设定 |
| `control` | `next` 的说明写接续链，而不是"队列的下一项" |

服务器说明增加一行：要说明你播的东西之后接什么，在 `play` 上传 `next` 或调用 `set_next`；人只要这一个时用 `then: "stop"`。`device` 遵循[屏幕会话](../../implemented/architecture/2026-10-31-screen-sessions.zh.md#which-screen-a-request-reaches)的默认规则。

## 备选方案

**一串排在队列前面。** 流媒体服务不管还有什么待播，都先播下一集，但它们没有队列。Yolo 的队列是用户本人或 agent 点名要的，一串在它之后接上，这是[接着播放](../../implemented/feature/2026-10-23-up-next.zh.md)定下的；agent 设定的下一个是针对这个条目本身的要求，排在两者之前。

**把 agent 设定的下一个当作放在队列开头的条目。** 不需要新的状态，但队列条目比请求活得长：人点了别的之后，agent 的三个后续条目还会接在后面播。让 agent 设定的下一个只在这段观看里有效，就把它和 agent 被要求的事绑在一起。

**agent 设定的下一个只管正在播的这一个。** "接着放这个频道的"只能管一个条目，每次结束都得再问 agent。**一直保留到 agent 或人清除：** 一个晚上的请求设下的规则，第二天还会左右这块屏幕上的观看。

**在作品结束处停下**，发现只在结束页上提供。车里或房间另一头的屏幕会在每个单独视频之后停下，没人去点。带防护的自动播放让它一直播，同时仍能停下一块没人看的屏幕。

**不设防护的自动播放**，像视频网站那样。开着不管的屏幕会连播几个小时相关视频，耗费节点和网站的带宽；加上 agent 挑选，还耗费用户本人的订阅额度。

**只有外部 agent 设定的下一个，家里没有 agent。** [地板](2026-10-11-yolo-1-0.zh.md#experience-layers)是一个没有任何来源、只会问 agent 的用户；它播的东西结束后，除非那个 agent 想到设定 `next`，否则什么都不会接上。家里的 agent 插件可以在结尾被问到；claude.ai 和 ChatGPT 无法被回调，所以它们在播放时设定 `next`。

**在发现环节之前问 agent。** agent 了解这个人，但每个单独视频都要花一次 agent 调用，而片源的相关推荐和关注都不花钱；它是最后一环，只在免费的环节都为空时使用。

**让插件推送下一个的事件钩子。** 每次结束时几个插件都会各推一个候选，Hub 反正得在它们之间裁决。一次有序的拉取、只在前面的环节为空时才问，对一部剧不花任何代价，并只给一个答案。

**由客户端构建接续链。** 网页播放器、Apple TV 和 iOS 会各自合并环节、过滤看过的，然后彼此偏离；条目的结尾会因屏幕而异。Hub 有历史往前、队列、一串和会话，每个客户端只画 `upNext` 和那一行。

**屏幕预加载下一个条目的媒体。** 能从内存开始播下一个，但 canvas 引擎的队列是有意设成有界的，用 LTE 的车会下载一个可能不播的条目，电视上两个 `<video>` 元素要占解码器。节点的待用会话在屏幕上什么都不加，就拿到大部分好处。

**结束页上的倒计时。** 播完前的卡片已经在倒计时；结束页是人选择不继续、或防护拦下的地方，所以那里什么都不会自动播。

## 验收标准

1. **B 站第 1 集 → 第 2 集。** 在网页播放器和车里，从番剧集页面播的第 1 集在最后 20 秒显示卡片"下一集 · E2 *标题*"；播完后，在家庭网络上 2 秒内从就绪一步的缓存开始播第 2 集，防护计数保持为 0。合集里的 B 站视频同样接着播合集的下一个视频。
2. **下一季。** 第一季最后一集的卡片显示"第 2 季 · E1"，接着播第二季第一集，从不播第一季的配音版或衍生作品；没有下一季时，接续链继续到环节 6。
3. **agent 播的单个视频。** Claude 在车上播一个 YouTube 视频，没有队列。(a) 没有 `next` 时，卡片写出频道的下一个视频"来自 *频道*"并播放它；屏幕上没有输入、连播三个发现条目之后，卡片问"还在看吗？"，第四个停在结束页上，带这个问题和那一行卡片。(b) 用 `play { next: { from: <频道视频页 URL> } }` 时，频道的视频按顺序播，防护从不拦它们。(c) 用 `then: "stop"` 时，视频结束在"你的 agent 说播到这里为止"，什么都不播。
4. **地板。** 一个只有内置链接播放和 Claude Code agent 插件的用户，在屏幕上要求播一个直接的 `.mp4` 链接。结束前两分钟，卡片显示"正在问 Claude Code…"，然后是"Claude Code 挑的"和它的一行原因；结束时播挑出的条目。设置关闭时，或在 Family 会话上，改为显示结束页。
5. **有效期。** agent 设定 `next`，含两个条目和一个播放列表 `from`；第一个条目播放，然后是用户本人加进队列的一项；之后 agent 的第二个条目仍然接着播。然后用户本人点了一张历史卡片：`upNext` 不再指向 agent 的条目，`up_next` 不显示 `next`。
6. **队列优先。** 队列里有两项、正在播一部剧时，先播队列，然后这部剧从下一集继续。
7. **Apple TV 和 iOS。** 在 Apple TV 上，最后 20 秒上下文操作里出现"播放下一个"和原因，关掉卡片后接着是带"重播"和那一行卡片的结束页。在 iPhone 上，浮层卡片出现，锁屏的"下一首"命令播下一个，手机锁屏时一部剧会一直播下去。
8. **两块屏幕和档案。** 家里的电视（Family）和用户本人的手机同时播放；各自沿自己的接续链播下去；电视从不拿到用户本人关注里的候选。在电视上"在这里继续"会带上手机上 agent 设定的下一个，电视的防护计数从 0 开始。
9. **失败和旧节点。** 解析失败的下一个条目被跳过，播再下一个；连续三个失败时显示带"重试"的错误面板。面对没有新路由的节点，环节 6 到 10 为空，接续链在结束页结束。
10. **检查。** `npm run check` 通过，包括 Hub 对顺序、有效期及其结束、防护和 `inputAge`、跳过失败、一串的 `next`、档案规则的测试；yt-dlp 片源基于录制回答的 `related()` 和 `next` 测试；以及一致性测试套件针对 Apple TV 和 iPhone app 的卡片、结束页和未知 `from` 场景。

## 风险

- **发现环节播了人不想看的东西。** 相关列表会跑偏，UP 主的下一个视频可能不相干。防护把没人看时的连播限制在三个，卡片写明每个来自哪里，用户本人可以按档案关掉发现环节的自动播放。
- **网站会改页面。** 相关列表和频道页是从会变的网站页面读的；`related()` 失败时环节 6 和 9 为空，它的测试基于录制的回答固定解析。读取这些会给网站增加请求：每播一个单独视频，一次相关列表和一次频道列表，共用 30 分钟。
- **agent 挑选要花钱。** 每次挑选是用户本人订阅上的一次 agent 调用；因为有防护，没人看时最多连续三次，而且只在免费环节都为空时才发生。挑选用的是用户本人的权限，所以对其他档案默认关闭。
- **agent 可能直接播放而不是设定。** 挑选期间调用 `play` 的 agent 会打断正在播的条目；指示里说了不要这样做，Hub 也会以 `invalid_request` 拒绝来自挑选请求的 `play`，并指明 `set_next`。
- **就绪一步会把节点的工作花在可能不播的条目上。** 跳过卡片或改主意会浪费一次 `prepare` 和几个分段；每块屏幕一个待用会话和 2 分钟的过期时间限制了它。有些网站的流 URL 几分钟内就过期；C4 检查这一点，过期的 URL 回退到普通的 prepare。
- **选季的规则是经验规则。** 对 C1 没覆盖到的番剧，在配音版和衍生作品之间选下一季可能出错；选错的下一季会在 20 秒前把标题显示在卡片上，用户本人可以关掉它。
- **放弃的：** 节点离线时的接续链（队列和历史仍然能回答，但什么都播不了）、一个档案在公开列表和相关推荐之外的发现、结束页上的倒计时，以及由外部 agent 的会话回调家里的 agent。
