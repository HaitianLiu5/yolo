# Agent Note: Yolo 替用户盯着：兴趣、活的首页，和一个准备好内容的池子

Status: proposed

[English](2026-11-04-living-home-and-media-pool.md) | 中文

## 问题

Yolo 的首页是一个文件夹。它显示历史、队列、播放列表和 Plex 的媒体库，只有用户做了什么它才会变。任何新东西能到屏幕上，都是因为用户跟 agent 说了。下面是 2026-11-04 太平洋时间 20:08，用户自己的实例上的真实情况：

| 当时在发生什么 | 首页显示了什么 |
|---|---|
| 五场 NBA 正在打（湖人 51–46 国王，第二节还剩 3:23，以及另外四场），就在用户常看且已登录的网站上，用户当晚早些时候还在那里看了另一场 | 什么都没有。那一场是用户问 agent 才看到的 |
| 用户看了街霸联赛 Division S 第 6 节 15,412 秒里的 15,119 秒。同一个频道把两个组别的第 7 节都标成即将开始，Division F 第 6 节已经结束 | 什么都没有，当时没有，以后也不会有 |
| 《排练人生》第 3 集，来源是知道的 | 已看过那一集的卡片：继续观看会接到多 P 视频的下一 P，但接不到 B 站剧集的下一集 |
| 一个 `Esports` 媒体库里有 Evo France，只因为它被提前下载并放进了 Plex | 就是那个媒体库，直到有人下载下一个之前都不变 |

视频服务的两种做法都不适合 Yolo。Plex 只显示用户精心挑选并提前下载好的东西，这是苦差事。YouTube 不用问就会推荐，但不留副本，所以每次点播都要看当时的网络。Yolo 既有屏幕，又有一台磁盘常在线的机器（这台还剩 1.1 TiB），所以能做到两者都做不到的事：发现用户会想看什么，并在用户看之前准备好。

现在这两件都没做，每次点播都在付代价：

- **每次点播都从零开始。** 2026-11-04 测得一次 yt-dlp 运行要 3.5 到 3.9 秒，之后才开始传第一个字节。
- **余量很小。** 到 YouTube 的单个连接跑 6.0 到 6.5 Mbps，对 3,440 kbps 的 1080p60 流只有实时的 1.8 倍；四个连接合计 24 Mbps。
- **网站会抖。** node 在 2026-10-27 到 2026-11-05 的日志里有 89 次对冲请求，其中 88 次在 B 站 CDN 上，75 次是 1.5 秒内没有首字节，单个会话就有 34 次。

agent 也一样看不见。`search` 只能找到媒体库里的东西，`history` 只知道已经播过的，没有任何东西说什么是新的。agent 也不能成为唯一入口：node 日志显示用户的 Claude Code 登录在 2026-11-05 的 02:22 和 03:54 UTC 都已过期，走这条路的话，依赖 agent 的首页就没有声音了。

最接近的几份提案都没解决这件事。[网站账号](2026-10-28-site-accounts.zh.md)读取用户在网站上关注的内容，需要登录，不知道今晚有什么比赛，也会漏掉用户在看但从没订阅的联赛。[接续链](2026-10-31-continuation-chain.zh.md)决定一个条目播完后放什么，不决定首页显示什么。[Yolo 1.0](2026-10-11-yolo-1-0.zh.md) 把缓存和预取排在最后。用户在 2026-11-04 的判断是：自己会变的首页最重要，而下载好媒体的池子，是 Yolo 不再受制于每次点播的办法。

## 提案

Yolo 在 node 上全天自己工作，分三层。每一层没有下一层也有用，都不等 agent：

```
history, the owner, agents ──▶ interests (D1, visible, editable)
                                     │  the Worker's cron sends a digest
                                     ▼
sites ──plugins' fresh()/find()──▶ feed (node) ──▶ rows on every home, get_feed
                                     │
what is unfinished, queued, next ────┴──▶ pool (node's disk) ──▶ a press plays from disk
```

- **兴趣**是用户在意的东西：一个频道、一项赛事、一支球队、一个话题。它是看得见、带理由的记录，不是隐藏的权重。
- **feed** 是 Yolo 此刻为这些兴趣找到的内容。
- **池子**是 node 已经下载好的内容，有一个用户无需操心的预算。

`service/` 里不出现任何站点名字：一个条目属于什么、那里有什么新东西，都由插件来说。

### 兴趣

下一个 D1 迁移新增 `interests`（`user_id`、`profile_id`、`key`、`title`、`kind`、`follows`、`origin`、`state`、`why`、时间戳；模型的 `queries` 在第二阶段加入），这样 node 离线时 agent 和屏幕仍能读到，D1 备份也会保留。`origin` 是 `history`、`model`、`owner` 或 `agent`；`state` 是 `active` 或 `muted`，已静音的兴趣不会再被提出。兴趣有四个来源：

1. **来自历史，不需要模型或登录。** 来源插件新增 `follows(source)`，说明一个条目属于什么：`[{ id, kind: "channel" | "schedule" | "team", title, within? }]`。node 在最近播放的摘要里统计这些 follow；一个 follow 在 30 天内出现在两次播放里，或者某次播放超过了条目一半长度或 30 分钟，就成为兴趣。街霸联赛的一场转播得到那个频道；一场 76 人的比赛得到 NBA 赛程和这支球队。
2. **来自标题，需要模型。** 每天调用一次 `yolo.models`（[给插件用的模型](../../implemented/architecture/2026-10-25-models-for-plugins.zh.md)），把最近 30 天的标题变成话题，并生成标题原语言的搜索词："Street Fighter League" 配 `ストリートファイターリーグ`。没有模型就没有话题类兴趣，其他一切照常。
3. **来自用户。** 设置 › 兴趣列出每一项和它在这里的原因，卡片的次要操作提供"不感兴趣"和"不再关注"。新首页可以用大白话问用户关注什么（"NBA、街霸、Lex Fridman"），和[首页冷启动](2026-10-31-home-cold-start.zh.md)里"你平时在哪里看"并列。
4. **来自 agent**，通过[下面的工具](#agents)。

兴趣和历史一样属于档案（[屏幕会话](../../implemented/architecture/2026-10-31-screen-sessions.zh.md)）：Family 的兴趣来自 Family 的观看，绝不显示用户自己的。

### feed

`service/node/src/feed.js` 在被忽略的 `.media-cache/feed/` 下保存快照，删除后可以从网站重建，节奏、上限、失败时保留上次快照以及 claim 的做法，都沿用[网站账号](2026-10-28-site-accounts.zh.md)为列表设计的方式。node 从不调用控制面，所以 Worker 现有的五分钟 cron 增加一步：每 30 分钟，当 node 在线时，通过 `nodeFetch()` 发送每个档案的摘要（最近 200 次播放及各自看了多少，以及兴趣），并保存 node 在回复里提出的兴趣。node 没有某个档案的摘要时，这个档案的首页会立刻发送一份。之后 node 按自己的定时器读取。一个网站同一时间只发一个请求。

来源插件新增三个可选方法（[来源插件 API](../../implemented/architecture/2026-10-11-source-plugin-api.zh.md)）：

| 方法 | 用途 | 返回 |
|---|---|---|
| `follows(source)` | 一个条目属于什么，如上 | `Follow[]` |
| `fresh(follow, { limit, signal })` | 这个 follow 现在有什么正在进行或新出现的 | `{ entries: Entry[] }` |
| `find(query, { limit, signal })` | 全站搜索，网站允许时按最新排序 | `{ entries: Entry[] }` |

**Entry** 是 `{ source, title, by?, thumbnail?, duration?, at?, tags?, paid?, live?, matchup? }`。`live` 是 `{ state: "upcoming" | "live" | "ended", startsAt? }`。`matchup` 是 `{ left: { name, badge, score? }, right: { … }, period? }`，用于任何双方对阵的内容。`title` 绝不带结果（[比赛和剧透](#games-and-spoilers)）。`paid` 条目只有在插件能用 node 的登录播放时才出现。接续链的 `related()` 和 `sequence()` 进入同一份存储，[账号插件](2026-10-28-site-accounts.zh.md)的列表也是一种输入。

第一个插件读取的内容，2026-11-04 在家里的机器上不登录测得：

| Follow | 读取 | 间隔 | 实测 |
|---|---|---|---|
| 赛事赛程（腾讯体育） | `matchUnion/list?columnId=&startTime=&endTime=` | 有比赛进行中或 2 小时内开始时 5 分钟，否则每小时 | 三天的数据 1.1 到 2.2 秒、32 KB：26 个条目，带比赛阶段、比分、队徽、`isPay`，以及来源已经能播的比赛页 |
| 频道（YouTube） | yt-dlp 平铺列出 `videos` 和 `streams` 标签页，再为接下来两场转播各跑一次 | 30 分钟 | 每个标签页 1 到 1.3 秒；标题、时长、播放量、封面、`is_upcoming` 或 `is_live`，加 `approximate_date` 还有日期。转播的时间不在列表里：单独跑一次 1.5 秒，得到 `release_timestamp` |
| 话题（YouTube） | `ytsearch`，或按日期排序的结果页 | 6 小时 | 10 条结果 1.4 到 1.6 秒 |
| 最近的条目（B 站） | `archive/related` | 播完时 | 40 个视频 0.44 秒 |
| 频道（B 站） | 它的动态需要登录 | 配合账号插件 | `feed/space` 返回 412，yt-dlp 的 UP 主列表只给 id 没有标题 |

后来比赛成了自己的类型：[赛事库](../../implemented/feature/2026-11-06-event-libraries.zh.md)让 `source-tencent-sports` 读取上面的赛程，并为每个联赛在首页加一行，比分规则相同。那个插件还没有 `follows` 和 `fresh`，所以 feed 只读频道，比赛来自联赛那一行；第二阶段给它加上这两个方法，让关注球队的比赛进入 `live`，回放进入 `replays`。

有两种看似很自然的读取方式失败了，因此不采用。YouTube 的 RSS 对所有请求都返回 404，固定版本的 yt-dlp 也已经没有 `ytsearchdate`。

### 首页上

行由 node 生成，所以每个客户端只负责绘制；Worker 叠加档案的进度，并去掉已看过或已忽略的内容。新行出现在首页现有的行之上：

| 行 | 卡片 | 上限 |
|---|---|---|
| `live` | 正在进行的比赛和转播，然后是 3 小时内开始的（关注球队的是 24 小时内），关注的球队优先 | 12 |
| 继续观看 | 和现在一样，它本来就会接到一串内容的下一项；B 站剧集现在也把一季作为它所在的那一串，所以下一集也显示在这里 | 30 |
| `picks` | agent 挑选的内容，每项附一句理由 | 5 |
| `new` | 所有兴趣里的新内容，按分数排序，各兴趣轮流出现，避免一个频道占满整行，每项说明原因（"来自 Capcom Fighters JP"） | 30 |
| `replays` | 最近 48 小时结束的比赛的完整回放，关注的球队优先 | 12 |
| `interest` | 最多三个兴趣各一行，要求至少有三个未看条目 | 每行 20 |
| 队列、播放列表、媒体库 | 和现在一样 | |
| `popular` | 网站的公开榜单，只在首页的个人化行少于两行时出现 | 20 |

条目的分数是它所属兴趣的权重（最近 30 天观看比例之和，每项按 14 天半衰期衰减）乘以它的新鲜度。排序只有这些；判断力放在 agent 的挑选里。

卡片带着让首页有生气的信息：`LIVE` 和比赛阶段、开始时间、`New`，以及表示已在池子里的标记。在网页和电视上，第一行的第一张卡片画得更大，带图片和原因。卡片在发布后 48 小时内算 `New`。屏幕在打开和获得焦点时取行，首页显示时每 5 分钟取一次，有 `live` 行时每 60 秒取一次，node 还在读取所关注的内容时每 10 秒取一次，并就地替换，所以一场比赛开打时，没人碰的首页也会出现它。行保存在屏幕已有的启动记录里（[网页客户端](../../implemented/feature/2026-10-11-yolo-web-client.zh.md)），所以首页能立刻打开。

点 `live` 卡片和现在播放比赛一样；点 `upcoming` 卡片会说明什么时候开始。

### 比赛和剧透

<a id="games-and-spoilers"></a>

[赛事库](../../implemented/feature/2026-11-06-event-libraries.zh.md)已经为比赛实现了前两条规则。满是体育内容的首页不能毁了上面的比赛。现在比赛的名字带比分（[`tencent-sports.js`](../../../../plugins/source-ytdlp/src/tencent-sports.js) 的 `gameReplays()`），这个名字还会留在历史和会话里：同一场比赛在 iPhone 上叫 `76人 106–102 活塞`，在车上叫 `76人 97–88 活塞`。

- 标题绝不带比分：无论保存在哪里，都写 `76人 vs 活塞`。
- 比分只出现在进行中比赛的卡片上，来自 `matchup`，也有设置可以隐藏。已结束的比赛不显示比分。
- 插件只列出已结束比赛里不剧透的视频。腾讯的 `playbackList` 符合（`NBA常规赛：76人vs活塞英文原声全场回放`），`totalList` 不符合（`费城112-106活塞 布朗30分…`）。
- 回放用用户常选的语言和形式：`preferredReplay()` 已经优先选英文全场，这也正是用户历史显示的偏好。

76 人那场比赛结束后 80 分钟内，回放就已列出。频道的标题没法这样清理（"SGA was NOT GUARDABLE with 42 PTS"）：[风险](#risks)里有说明。

### 池子

池子是 node 磁盘上一个放完整文件的目录 `.media-pool/`（被忽略，`POOL_DIR` 写入 `.env.example`）。

**多大。** 默认预算是 50 GB 和可用磁盘十分之一中较小的那个，并始终留出 20 GB 可用空间。设置 › 池子提供关闭、25、50、100、200 或 500 GB，并显示里面有什么。按实测 1080p60 每小时 1.55 到 2.58 GB 计算，50 GB 是 20 到 30 小时，或七场街霸联赛转播。

**放什么**，排名高的优先：

| 排名 | 内容 |
|---|---|
| 1 | 用户或 agent 要求保留的 |
| 2 | 最近 14 天没看完的 |
| 3 | 队列接下来的五项，以及 agent 设定的下一个 |
| 4 | 每个进行中系列的接下来两项 |
| 5 | 关注球队比赛的完整回放 |
| 6 | 按分数排序的新条目，每天最多五个；超过两小时的转播只来自用户曾看完过的兴趣 |

**什么时候离开。** 超出预算时，已看过的条目 3 天后离开，然后是排名最低、最旧的；候选条目绝不挤掉排名更高的，正在播放的文件绝不删除。保留的条目只由用户或 agent 手动移除。

**怎么下载。** node 调用插件自己的 `prepare(source, { capabilities: POOL_TARGET, limits, reason: "pool" })`，把得到的 Input 变成文件：`file` 用范围请求，`split` 用两路范围请求加 ffmpeg 重封装（`-c copy -movflags +faststart`），`hls` 用 ffmpeg。`live` 或 `transcoder: true` 的 Input 绝不进池子，没有用 `pool: true` 选择加入的来源也不进；Plex 和文件夹本来就在家里。请求沿用流水线的故障切换和刷新，所以插件 API 几乎不变，任何来源都能用。`prepare` 说的内容（标题、封面、时长、音轨和字幕轨、章节，以及用户偏好选中的文本字幕）保存在文件旁边。

**下载什么。** `POOL_TARGET` 是 MP4 封装的 H.264 和 AAC，最高 1080p、6,500 kbps，每块屏幕都能播。设置 › 池子 › 画质可以提高到来源提供的最佳。

**怎么播放。** `sources.prepare()` 先查池子，直接用 `{ type: "local", path }` 和保存的描述回答，不调用插件。从这里开始走的就是[文件夹来源](../../implemented/feature/2026-10-26-folder-source.zh.md)的路径：`buildLocal()` 原样播放文件、复制成 HLS，或者按屏幕的上限转码。历史、续播和音轨都用同一个 `sourceKey`，所以 node 之上看不出区别，只是开播很快，网站挂了也能继续播。文件出错时回退到插件。还不在池子里的条目和今天一样播放，一次点播会把它提到排名 2。

**播放永远优先。** 只要有屏幕正从网站读取，下载就暂停，结束 30 秒后恢复。同时最多两个下载、每个网站一个，每个下载两个连接（按实测速率，6.9 GB 的转播约 77 分钟），每个网站每天最多 20 个条目。网站返回 403、429 或人机验证时，该网站的池子工作暂停 6 小时，绝不加大重试。失败三次的条目放弃一周。

**它解决不了什么。** 池子把网站从点播链路里拿掉了。但从家到屏幕的那段链路它帮不上忙：车上最近一次走中继的会话是一场直播，有一次 521 秒的卡顿，node 上有文件也帮不了它。那段链路归[流畅播放优先](../architecture/2026-10-21-smooth-playback-first.zh.md)负责，直播比赛也根本进不了池子。

### Agent

<a id="agents"></a>

| 工具 | 权限 | 内容 |
|---|---|---|
| `get_feed` `{ row?, query?, since?, limit? }` | `read` | 各行内容，每项带上它在这里的原因、直播状态、是否在池子里；默认不超过约 2,000 token |
| `interest_list`、`interest_add` `{ title, queries?, url? }`、`interest_remove` `{ id, mute? }` | `read`、`control` | Yolo 替用户关注的东西；"我开始关注 SFL 了"会成为比对话活得更久的记录 |
| `feed_pick` `{ item \| url, why, until? }` | `control` | 把一个条目放进某个档案所有屏幕的 `picks` 行 |
| `pool_list`、`pool_add` `{ item, keep? }`、`pool_remove` | `read`、`control` | "明早开车前把这个准备好" |
| `search` `{ web: true }` | `read` | 同时询问插件的 `find()`，屏幕上的搜索也一样 |

服务器说明和 [yolo 技能](../../../../skills/yolo/SKILL.md)会要求：遇到"现在有什么""有什么好看的"先读 `get_feed`，并把对方说自己关注的东西记录下来。

**编辑。** 每天一次，以及每新播放五次之后，node 以最低优先级（和接续链的挑选一样）请屏幕选定的 agent 插件（[屏幕上的 agent](../../implemented/feature/2026-10-18-agent-from-the-screen.zh.md)）读取历史、兴趣和 feed；它可以添加或静音兴趣，最多挑三项并各写一句理由，把条目保留到池子，还可以上网搜索插件看不到的东西。每天占用用户订阅的一轮，加载了 agent 插件时默认对用户的档案开启，设置里有开关。这是 YouTube 算法做不到的部分：它能用用户自己的话说明原因，用户也能纠正它。其他一切都不等它，登录过期的首页只是少一个 `picks` 行。

### 和其他笔记的关系

- **[网站账号](2026-10-28-site-accounts.zh.md)。** 它的登录、列表、MCP 工具和插件保留。它的快照和行变成 feed 的：账号列表进入同一份存储，关注的频道就是 follow，`/v1/accounts/rows` 在实现之前就由 `/v1/feed/rows` 取代。
- **[接续链](2026-10-31-continuation-chain.zh.md)。** 发现类环节取自 feed，已在池子里的条目跳过预备步骤。
- **[首页冷启动](2026-10-31-home-cold-start.zh.md)。** 有兴趣的首页不再是空的；它的问题多一个并列项：用户关注什么。
- **[Yolo 1.0](2026-10-11-yolo-1-0.zh.md)。** 承诺 1 从用户的来源扩大到这些来源的新内容；承诺 5 的缓存和预取提前。
- **[Agent 画布](../architecture/2026-10-21-agent-canvas.zh.md)。** 画布是 agent 在一块屏幕上的一时之举；`picks` 是持久的，出现在一个档案的所有屏幕上。

### 路由、数据和版本

| 位置 | 路由 | 权限 |
|---|---|---|
| `/v1` | `GET /v1/feed/rows?limit=`、`GET /v1/feed/rows/:id?offset=&limit=` | `read` |
| `/v1` | `POST /v1/feed/feedback` `{ source?, interest?, signal: "not_interested" \| "stop_following" }` | `control` |
| `/v1` | `GET`、`POST`、`DELETE /v1/interests[/:id]` | `read`、`control` |
| `/v1` | `GET /v1/pool`、`PUT`、`DELETE /v1/pool/items/:key` | `read`、`control` |
| `/v1/owner` | `PATCH /v1/owner/pool` `{ budget, quality, paid }` | passkey 会话 |
| node | `POST /internal/v1/feed/digest`、`GET /internal/v1/feed/rows?profile=`、`GET`、`PATCH /internal/v1/pool` | node 的密钥 |

每条路由都是新的。旧 node 返回 404，控制面将其理解为 `available: false` 且没有行；旧客户端不调用它们，所以 `NODE_PROTOCOL` 和 `CLIENT_PROTOCOL` 不变。D1 新增 `interests` 和 `feed_dismissed`，上一个版本不会读它们。行和池子的列表绝不保存在 D1。`site/public/privacy.html` 和 `site/public/zh/privacy.html` 这一对隐私页面在同一次改动里说明：node 会把根据用户观看内容生成的搜索发给网站，会在用户的机器上保留视频副本，并把标题发给用户的模型。上线时要更新上面这些笔记，以及[来源插件 API](../../implemented/architecture/2026-10-11-source-plugin-api.zh.md)、[`/v1`](../../implemented/architecture/2026-10-07-v1-http-api.zh.md)、[node 内部 API](../../implemented/architecture/2026-10-07-node-internal-api.zh.md)、[远程 MCP 服务器](../../implemented/feature/2026-10-07-remote-mcp-server.zh.md)和 [D1 数据模型](../../implemented/architecture/2026-10-07-d1-data-model.zh.md)。

### 计划

每个阶段都能单独上线和回滚。首页先变，因为用户说这最重要。

1. **会变的首页，不下载、不用模型。已实现。** `follows`、`fresh`，`source-ytdlp` 里的频道读取，`feed.js`，cron 的摘要，来自历史的 `interests`，`/v1/feed/rows`，网页播放器里的 `live`、`new` 和 `replays` 行，以及卡片上的"不感兴趣"和"不再关注"。实现时去掉了单独的 `next` 行，因为继续观看已经会显示下一项，同一样东西不能出现两次。比赛有了自己的来源后，`source-ytdlp` 自己读取赛程的代码也去掉了：两份并存会让每场比赛以两个 id 出现两次。
2. **公开的兴趣，以及其他客户端。** `source-tencent-sports` 的 `follows` 和 `fresh`，设置 › 兴趣、模型生成的话题、`find`、兴趣行、`get_feed` 和 `interest_*` 工具，并通过 YoloKit 让 Apple TV 和 iOS 显示同样的行。
3. **池子。** 下载器、预算和排名、`sources.prepare()` 的回退、设置 › 池子、卡片标记和 `pool_*` 工具。
4. **编辑和挑选。**
5. **账号**，按[它自己的笔记](2026-10-28-site-accounts.zh.md)计划，进入同一份存储。

### 用户可以推翻的决定

1. 池子默认开启，50 GB，因为用户不该为此操心。新用户会在冷启动时看到这一点。
2. 直播比赛的卡片显示比分，因为这是让这一行有生气的东西，也能帮人挑一场胶着的比赛。已结束的比赛绝不显示。
3. 池子里的文件是 1080p，所以车上要经过转码，而局域网上能直播 4K 的 Apple TV 从池子里拿到的是 1080p：流畅优先于清晰。
4. 付费回放不进池子，直到用户打开 `paid` 开关（[风险](#risks)）。

## 备选方案

**先做网站账号。** 它已有设计，关注列表也是好数据。但它每个网站都要登录，不显示比赛，也会漏掉这位用户的联赛。从用户自己的历史出发、匿名读取，大约三秒就拿到了五场直播和那个联赛的下一节。账号之后再进入同一份存储。

**让 agent 来写首页。** 每次打开或每小时，由 agent 决定行，也许通过画布。这最灵活，几乎不需要新代码。但首页要花 agent 的轮次和几秒钟才能加载，登录一过期就没了声音，写这份笔记的当天就发生了两次。确定性的几层生成首页，agent 每天编辑一次。

**在 Worker 里跑 feed。** node 离线时也能回答，但网站会封云地址，Worker 没有登录和出站规则，Workers Free 还要计算每个请求。读取由 node 做，D1 只保存兴趣。

**填充分段缓存，而不是保存文件。** 提前读取流会请求的内容可以复用缓存，播放代码不用改。但点播时仍要对网站运行 `prepare`，范围取决于清晰度和路径，缓存条目不能按条目淘汰，也无法说一个条目已经就绪。完整文件才能把网站从点播里拿掉。

**让插件用 yt-dlp 下载。** 它的下载器很稳，版本也已固定，但只适用于一个插件，还要新方法；每个来源的 Input 已经说明如何取得字节，流水线也已经带故障切换地在取。

**把下载放进 Plex 或文件夹媒体库。** 可以复用媒体库，但条目会得到新 id，历史和续播会一分为二，文件还会显示成单独的媒体库。这正是这份笔记要离开的文件夹视图。

**每个条目只保留开头几分钟。** 一行 40 张卡片都能立刻开播，几乎不占磁盘，但开播后中途仍要交给网站，这正是池子要消除的故障，引擎和流水线还得拼接两路流。等[拼接](../architecture/2026-10-21-smooth-playback-first.zh.md)上线后值得再看。

**每个条目两种清晰度。** 给车一个 720p 副本、给电视一个更好的，可以避免转码，但磁盘几乎翻倍。D2 说明在这台机器上转码很便宜；更弱的机器可能会改变这个结论。

**比赛开打时推送行。** node 不能调用控制面，而让 Durable Object 为每块屏幕轮询它，比屏幕在显示这一行时每分钟问一次更贵。

**真正的推荐系统。** 一个家庭的数据不够训练，网站自己的相关列表和用户的 agent 已经覆盖了加权计数做不到的部分。

**像视频网站那样悄悄推断兴趣。** 要做的界面少一些，但用户看不到、也改不了某样东西为什么出现，而一个用户自己运行的服务没有理由隐藏这些。每张卡片都说明原因。

**把兴趣放在 node 上。** 对 node 更简单，但 node 离线时 agent 和屏幕也需要它们，而且它们是用户的数据，D1 有备份。

**从公开榜单开始。** 一个请求就能给任何人填满一行，但热门视频是 Yolo 能显示的最不个人化的东西，所以只在没有更好内容时出现。

## 验收标准

- **不登录、无模型、无 agent。** 在播放过一场 NBA 的实例上，比赛开打后 5 分钟内，正在进行的比赛出现在首页顶部，无需刷新，点一下就能播。关闭 agent 插件只会少一个 `picks` 行。
- **用户在看的联赛。** 把一场街霸联赛转播看过一半后，首页会显示该频道即将开始的下一节和未看的各节为新内容，每项说明原因，这个兴趣也带着理由列在设置里。"不再关注"会移除它，而且它不会再回来。
- **没有剧透。** 历史、会话、行和 MCP 回答里的标题都不带比分。已结束比赛的卡片不显示比分，回放列表里没有带比分的视频，回放是用户常用的语言。
- **接下来是什么。** 进行中剧集的下一集显示在继续观看里，不需要先播放任何东西。
- **它自己会变。** 一块没人用的屏幕隔一天打开两次，显示的行不同，全程没有 agent 参与。
- **池子。** 池子里的条目在局域网屏幕上开播时不向网站发任何请求，把网站封掉也能播到结束。走中继的车按自己的上限，经转码播放同一个文件。历史和续播不变，同一个 `sourceKey` 显示同样的进度。
- **不用操心。** 按默认设置，池子自己填充和淘汰，从不超出预算，留出 20 GB 空间，有屏幕从网站播放时暂停。一个网站的 429 只暂停这个网站。关闭会删除文件。
- **Agent。** 在没有任何上下文时问 agent"有什么好看的"，它能根据 `get_feed` 说出一场直播和下一节比赛。"明天之前把这个准备好"会让它进入池子，`get_feed` 显示它已就绪。
- **档案和旧版本。** Family 屏幕只显示 Family 的行。旧 node 不给行也不报错，旧客户端照常工作。
- **检查。** `npm run check` 通过；`service/` 下没有已跟踪文件出现站点名字；插件测试用录制的回答固定解析结果；隐私页面说明以上内容。

## 风险

<a id="risks"></a>

- **家庭地址的信誉是最大的风险。** 从家庭地址后台下载可能招来网站的人机验证，这也会影响用户自己的点播。所以才有每日上限、6 小时退避、播放优先，以及信任这些数字之前的 D7。
- **服务条款。** 在一些网站上，保留副本比流式播放走得更远，用于下载的账号也可能被标记。池子只拿 `prepare` 已经给的东西，绝不绕过 DRM，且只属于一个家庭。付费条目默认不进，由用户了解情况后按网站打开。
- **猜错要花磁盘和流量，按流量计费的家庭宽带要为此买单。** 预算、每天五个猜测的上限和关闭开关限制了它，设置 › 池子会显示用量。
- **用笔记本做家里的机器。** 这个实例的 node 跑在 MacBook 上，休眠时既不读取也不下载。此时首页显示上一次的行，池子等待。
- **池子不改变最后一段链路。** 指望它治好车上 LTE 卡顿的用户，在家庭上行或中继是瓶颈时会失望。车上的转码还要占用 node 一个核，机器更弱时占得更多。
- **网站会变。** 2026-11-04 失败的两种读取方式都曾是最显而易见的做法。读取失败时保留上次快照并说明，没有哪一行依赖单个网站。
- **视野变窄。** 来自历史的兴趣只会带来更多同类内容。相关列表和编辑的挑选能拓宽一些，但仍比不上一个网站的完整目录。
- **赛程之外的剧透。** 频道的标题和封面可能泄露结果，只有模型才能猜出哪些会。想避开结果的用户可以不再关注那个频道。后续可以让模型隐藏这类标题。
- **屏幕显示什么，网站听到什么。** 首页现在会把兴趣展示给坐在面前的任何人，包括乘客，根据观看内容生成的搜索也会发给网站。兴趣按档案区分，静音只需点一下，隐私页面都有说明。
- **node 上运行的东西变多，Worker 的负担也变多。** feed 和下载器给同时要供流的机器加了工作，每张卡片的封面都是一次 `/v1/thumbnail` 请求，计入 Workers Free。屏幕会缓存封面，cron 这一步每天增加 48 个请求。
- **放弃的东西：** 比轮询更新鲜的行、屏幕自己的离线副本、把直播放进池子、按条目区分清晰度，以及任何基于多个家庭训练的推荐。
