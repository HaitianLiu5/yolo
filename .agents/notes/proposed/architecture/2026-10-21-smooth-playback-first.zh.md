# Agent Note: 流畅优先：换画质从不丢弃缓冲

Status: proposed

[English](2026-10-21-smooth-playback-first.md) | 中文

## 问题

Yolo 的播放首先看流畅：一直在动的画面胜过更清晰的画面，已经缓冲的媒体从不丢弃，自适应画质的机制也要简单到让人放心。车上的情况说明了原因。行驶中的网络从半兆到几兆都有可能，canvas 引擎最多保留 210 秒的已编码分片，就是为了让一段没信号的路悄无声息地过去（[canvas 引擎](../../implemented/architecture/2026-04-04-canvas-playback-engine.zh.md)）。现在每一次换画质、每一次恢复都替换掉流，把这份缓冲扔掉。

### 现在谁决定画质

一个流的码率由六方共同决定：

| 一方 | 决定什么 | 在哪里 |
|---|---|---|
| 播放器的控制器 | 每秒测量吞吐和缓冲，请求一个上限不同的流：卡顿 8 秒或短缓冲持续流失 20 秒后降档；在 1.6 倍余量、缓冲 30 秒的条件下保持 90 秒后升一档；另有冷却时间，以及升了又降之后把等待时间加倍的惩罚 | [`quality.js`](../../../../clients/player/src/quality.js)、[自适应画质](../../implemented/feature/2026-10-11-adaptive-quality.zh.md) |
| Hub | 记住设备自己上一次请求的上限 30 分钟（`QUALITY_MEMORY_MS`），所有路径共用一个值，用于这台设备接下来播放的任何内容 | [`hub-core.js`](../../../../service/control/src/hub/hub-core.js) 里的 `deviceLimits` |
| 节点 | 取这个上限和媒体路径上限中较小的一个：局域网 200,000 kbps，远程直连播放 20,000，中继 4800 | [媒体离开 Worker](../../implemented/architecture/2026-10-13-media-off-the-worker.zh.md) |
| 片源插件 | 把上限对应到一种码率版本：Plex 按上限转码，画面尺寸查自己的表（2000 kbps 起 720p，1200 起 480p，600 起 360p）；yt-dlp 在上限以下挑选格式 | [`playback.js`](../../../../plugins/source-plex/src/playback.js)、[`formats.js`](../../../../plugins/source-ytdlp/src/formats.js) |
| Plex 的转码器 | 决定实际输出的画面：2200 kbps 一档请求 1280×720，解码出来却是 720×404，比 1500 kbps 一档的 852×480 还小 | Plex |
| hls.js 或原生 HLS | 在上限以下的多变体播放列表的变体之间切换，只在 `<video>` 引擎上 | [两个引擎](../../implemented/architecture/2026-10-12-two-playback-engines.zh.md) |

### 现在怎样应用一次变化

一次变化，不论升降，都是一次 `POST /v1/playback/play`，带上 `reason: "quality"`、当前位置、被替换的会话和 `maxVideoKbps`。Hub 准备一个新的节点会话（对 Plex 来说是一次新的转码，`offset` 设在当前位置），并停掉旧会话。`load` 到达后，[`player.js`](../../../../clients/player/src/player.js) 里的 `play()` 销毁引擎，连同它的解码器和已编码的缓冲，新建一个引擎，等新流缓冲到 3 秒才开始播放。

恢复走的是同一条路。`isRecoverablePlaybackError()` 接受的引擎错误（包括任何匹配 "decod" 的消息）会在 1、3、10、30、60 秒的退避之后，在当前位置请求一个新流（`reason: "recovery"`），这个流同样替换掉引擎。直连路径在播放中途失败时，以同样的方式换到下一条路径（[媒体离开 Worker](../../implemented/architecture/2026-10-13-media-off-the-worker.zh.md)）；缓冲里还有几分钟内容时会话过期，也是如此（[Plex 会话恢复](../../implemented/bug-fix/2026-09-10-plex-session-recovery.zh.md)）。跳转到流无法提供的位置，比如一个从中途开始的 Plex 转码的起点之前，会在那里请求新流（`reason: "seek"`）。

### 2026-10-21 发生了什么

车上通过中继、走 LTE 播放一部 Plex 电影。时间为 UTC，来自车上的设备事件和节点日志：

| 时间 | 发生了什么 | 前方缓冲 |
|---|---|---|
| 19:03:45 | 以中继的上限播放，720p、4800 kbps：Hub 没有记住任何上限。8.6 秒后出现第一帧，接着卡顿 5.5 秒和 1 秒 | 最多 3 秒 |
| 19:04:18 | 降到 1500 kbps（`draining`：测得 2713 kbps，需要 4928）。新的转码替换了流，随后一次重启式跳转让它从 3:13 而不是 8:16 开始，这个 bug 另行修复。19:04:41 继续播放 | 6 秒，被丢弃 |
| 19:12:24 | 升到 2200 kbps（测得 4787 kbps）。新的转码替换了流，19:12:40 开始播放，画面是 720×404，比之前还小 | 216 秒（约 64 MB），被丢弃 |
| 19:17:52 | 在 16:10 处出现 "Decoding error."。恢复以 2200 kbps 启动了新的转码，它在没有任何缓冲的情况下卡住；19:18:11 降档又启动了一个 1500 kbps 的转码。画面一直停到 19:18:30，约 39 秒 | 216 秒（84 MB），被丢弃 |

整个行程中有 153 次分片下载超过 3 秒（`network_segment_slow`），这些下载的速度在 0.6 到 3.4 Mbps 之间。网络弱，但能用：1500 kbps 的流从 19:04:41 播到 19:12:24 没有卡顿，缓冲涨满到 216 秒。解码错误的原因没有查明。最可能的是车上（大概是硬件）视频解码器的一次性故障，其次是 Plex 给了一个损坏的分片（插件向 Plex 请求未完成的分片：`X-Plex-Incomplete-Segments: 1`）；已排除的有：编码变化但没有重新配置、关键帧之前的帧、内存增长。"Decoding error." 这段文字视频解码器和音频解码器都一样，而播放器没有记录是哪一个出的错。

### 哪里违背了目标

1. **起步不看网络实际承载过什么。**Hub 30 分钟后就忘掉设备的码率，并且所有路径共用一个码率，于是每次出行都从路径的上限起步，第一分钟一路卡顿着降到车上早已知道的码率。
2. **每次变化都扔掉缓冲。**只有缓冲满了才会升档，所以丢掉最多的那一步，恰恰发生在一切正常的时候。降档丢得不多，但新流仍然从零开始。
3. **解码器故障找网络要办法。**解码器出错的那些分片本来就在车上；重建解码器不需要网络，而正是网络让新流卡住了。
4. **没有唯一的负责方。**控制器、Hub 的记忆、节点的上限、插件的表、Plex 的转码器、hls.js，各自决定码率的一部分；控制器的 18 个策略参数（冷却时间、振荡惩罚、条目结尾规则）大多是为了限制重建本身的代价。

## 提议

### 原则

1. **流畅优先。**一次卡顿比任何画面尺寸都更伤；两者冲突时，选低码率。
2. **从不丢弃已缓冲的媒体。**任何换画质、恢复或换路径，都不扔掉播放位置前方的已编码分片。只有用户本人跳到缓冲之外的位置时，才离开它们。
3. **从行得通的码率起步。**流从这块屏幕在这条媒体路径上最近一次稳定播放的码率起步，这个码率被持久记住；没有记录时，用这条路径保守的默认值。
4. **在缓冲的末尾换码率。**新码率只用于还没下载的分片；已缓冲的内容先播完。
5. **只在缓冲满且余量持续足够时升档；缓冲见底时降档。**由缓冲水位决定，两条水位线之间是不做任何变化的死区。
6. **先就地恢复。**解码器故障就从已编码的缓冲重启解码器；不能再下载的流从缓冲末尾接上新流；在播放位置请求新流是最后的手段。
7. **每个决定只有一个负责方。**下面每个决定都恰好有一个负责方；其他各方只执行限制或保存数值，不做决定。

### 码率控制器

[`quality.js`](../../../../clients/player/src/quality.js) 保留现有的测量，改用这些规则：

| 规则 | canvas 引擎 | `<video>` 引擎，单一变体的流 |
|---|---|---|
| 估计 | 维持现状：最近 8 次下载的第 25 百分位和它们的移动平均取较小值；30 秒内没有下载完成、也没有下载在进行时，不采用 | 维持现状：hls.js 的估计，或缓冲增长的速度 |
| 起步 | 这块屏幕在这条路径上记住的码率；没有时用路径的默认值 | 同左 |
| 低水位 | 前方缓冲 60 秒 | 10 秒 |
| 满 | 前方缓冲 180 秒，或条目剩下的全部 | 30 秒（hls.js 默认的缓冲目标），或条目剩下的全部 |
| 降档 | 低于低水位且估计低于流的码率 × 1.15，或卡顿 8 秒：取不超过估计的 75%（减去音频、除以倍速）的最高一档，从缓冲末尾起生效 | 同左 |
| 升档 | 缓冲满，且估计在 90 秒里一直不低于下一档码率 × 1.6：升一档，从缓冲末尾起生效 | 同左 |
| 其他情况 | 保持 | 保持 |

保留的部分：同一时间最多一个变化在进行，直播不做自适应，倍速对每个码率的放大，400 到 13,000 kbps 的档位表，以及片源没有更低一档时这个条目不再降档。条目剩下的部分全部缓冲之后，不再有任何变化。

没有记住的码率时，流从路径的默认值起步：

| 路径 | 默认起步 |
|---|---|
| 局域网直连播放 | 路径的上限，设备能直接播放原文件时就是原文件 |
| 远程直连播放 | 1500 kbps |
| 中继 | 1500 kbps |

1500 kbps 是 2026-10-21 那天没有卡顿的码率，也是 Plex 的 480p 预设；中继的上限仍是 4800 kbps。

### 记住码率

Hub 在它的 Durable Object 存储里为每台设备的每条路径（`lan`、`wan`、`relay`）各记一个码率，不过期，替代现在所有路径共用、只记 30 分钟的一个值。它记下设备自己在这条路径上的请求里的 `maxVideoKbps`（和现在一样），以及控制器不发请求就定下码率时，上报的 `health` 里可选的 `rate: { path, kbps }`。这台设备上每一次没有指定码率的播放都用它：agent（智能体）的点播、队列的下一项、转移、恢复播放。在中继上学到的码率绝不用于局域网。上一个版本会忽略新的键和新的字段，所以协议版本号不变（[客户端协议](../../implemented/architecture/2026-10-19-client-protocol.zh.md)）。

### 从缓冲的末尾接着播

换码率变成一次拼接：旧流播到它缓冲的末尾，新流从那里接着播。

1. 播放器选定拼接时刻 T：已缓冲媒体的末尾，也就是流的各个播放列表中最早的那个末尾，它总是分片边界。播放器取消旧流在 T 之后的预读，不再下载旧流。
2. 它和现在一样向 Yolo 请求：`POST /v1/playback/play`，带上 `reason: "quality"`、`startTime: T`、被替换的会话和 `maxVideoKbps`。
3. Hub 和现在一样准备新会话并停掉旧的节点会话，因为播放器已经拿到了它需要的那部分。对 `quality` 和 `recovery`，Hub 继续按屏幕实际所在的位置计算进度，而不是按 T，这样连接断开后的恢复播放不会跳过已缓冲的那一段。
4. 片源像准备任何起点一样在 T 准备：Plex 以 T 为 `offset` 启动转码，yt-dlp 在新的上限下解析格式。插件 API 不变。
5. 引擎把新流的 Input 加进同一个 HLS 预取器。预取器对两个流共用一个字节上限（128 MiB）和一个下载槽位，并且绝不为了给新流腾地方而淘汰旧流在 T 之前的分片。旧流播放的同时，新流从 T 开始填充。
6. 到了 T，视频生产者结束旧轨道的迭代器（`canvases(start, T)`），在新的解码器上启动新轨道的迭代器（`canvases(T)`）；canvas 从新流的第一帧取新的画面尺寸。音频同样用 `buffers(start, T)` 和 `buffers(T)` 写入同一个环形缓冲，按时间戳放置，所以小的间隙变成静音，重叠的部分被裁掉。新流的声音需要别的采样率时，在 T 重新打开音频输出。
7. 播放越过 T 之后，释放旧的 Input 和它的分片。

换画质（升或降）都拼接。预读以 `SESSION_EXPIRED` 或重试耗尽告终、直连路径在播放中途失败，也都拼接：已缓冲的部分照常播放，新流从它的末尾开始填充。前方没有任何缓冲时，T 就是播放位置，这次拼接就是现在的替换，只是没什么可丢。跳到缓冲之外的位置和换音轨字幕，仍然在用户本人选的位置请求流。新流的媒体比 T 晚开始超过一个分片，或者它的时间戳不在条目的时间轴上，就不能拼接：引擎把缓冲播到 T，再在那里加载新流，会在 T 停顿一下，但缓冲仍然保住了。

### 就地恢复

解码错误沿一个阶梯处理，每一步都记录是哪个解码器出错（视频或音频）、时间戳和分片：

1. 在当前位置从已编码的缓冲重启出错轨道的解码器，走 `restartProducers()`，和现在打开声音时 `seek(t, { preserveHlsBuffer: true })` 走的路一样。只有画面的解码器出错时，声音继续播放，车上不发出任何请求。
2. 同一个时间戳再次出错，就从同一个会话重新下载那个分片（它可能损坏或不完整），并用 `hardwareAcceleration: "prefer-software"` 打开视频解码器。
3. 第三次出错，跳到下一个关键帧。
4. 到这时才在当前位置请求新流，走现在的恢复流程和它的退避。

### 每个决定只有一个负责方

| 决定 | 负责方 | 其他各方 |
|---|---|---|
| 单一变体的流上还没下载的分片用什么码率 | 播放器的控制器 | 节点用路径的上限封顶；Hub 保存它 |
| `<video>` 引擎上多变体流选哪个变体 | hls.js 或原生 HLS | Yolo 的控制器不介入；现在对这类流卡顿后降档的做法删除 |
| 流从什么码率起步 | 屏幕在这条路径上记住的码率 | Hub 保存它，并用于不是屏幕自己发起的播放 |
| 一个码率对应哪种码率版本 | 片源插件，从画面不随码率升高而变小的档位里选 | Plex 的转码器输出插件的档位经检查确认会输出的画面 |
| 恢复 | 先是引擎（解码器、缓冲），然后是播放器（新流） | 代理和节点从不重启播放，和现在一样 |

### 对照硬性约束

- **canvas 引擎的规则。**解码后的视频队列仍是一个 6 到 16 帧的队列：旧的生产者在 T 结束之后，新的才开始。两个流的已编码分片共用一个 128 MiB 上限和一个下载槽位，所以预读仍然一次只下一个，旧流在 T 之后什么也不下载（[canvas 引擎](../../implemented/architecture/2026-04-04-canvas-playback-engine.zh.md)）。
- **Plex 转码。**新码率就是一次带 `offset` 的新转码，和现在一样。拼接要求它的时间戳在条目的时间轴上，从中途开始的转码本来就是如此：引擎把它的第一个时间戳读作它开始的位置，跳到它之前会请求新流。拼接还要求 T 或更早处有媒体：插件的 `offset` 是 T 向下取整到整秒，节点会裁掉它之前 Plex 的占位分片。Plex 的分片长度随码率不同（节点日志里被裁掉的占位分片数表明，4800 kbps 时分片 3 秒，1500 和 2200 时 8 秒），所以拼接按时间而不是按分片序号。有一小段时间会同时跑两个转码，和现在一样。
- **yt-dlp 格式。**码率版本是固定的：新码率就是 `prepare` 时重新选一个格式，和现在一样按字节范围拼接。因为镜像慢而在上限以下起步的片源（`capped`）仍从那里升档（[媒体管线](../../implemented/architecture/2026-10-11-node-media-pipeline.zh.md)）。
- **中继的上限。**仍是 4800 kbps，不会请求高于路径上限的档位。
- **两个引擎。**拼接属于 canvas 引擎。`<video>` 引擎把多变体流交给浏览器；单一变体的流仍然替换，遵守同样的控制器规则；它的缓冲是 hls.js 的 30 秒，不是车上的 210 秒（[两个引擎](../../implemented/architecture/2026-10-12-two-playback-engines.zh.md)）。

### 节点给出多变体播放列表会不会让这些更简单？

部分会，但不在证据所在的地方：

- **对 `<video>` 引擎和本来就有多种码率版本的片源，会。**节点给出一个主播放列表，列出 yt-dlp 的几种格式，每种都像现在这一种一样按字节范围拼接，hls.js 和原生 HLS 就能自己自适应，不需要 Yolo 的控制器，也不需要新会话。
- **对 Plex，不会。**一次转码只产出一种码率版本，所以一个档位表意味着每一档一个转码，在播放器第一次请求那一档时才启动，跑在同时服务其他所有屏幕的那台机器上。浏览器的 ABR 往上试探时会启动随后又被放弃的转码；各档的分片网格也不同（上面的 3 秒和 8 秒），对不上共同的边界。
- **对车上，不会。**Mediabunny 把播放列表的每个变体读成一条独立的轨道，所以 canvas 引擎要在变体之间切换，需要的正是拼接所做的：在时刻 T 切换到一个新的解码器。

无论哪条路，工作量都在拼接上。拼接做好之后，canvas 引擎也能用它在一个多变体流的轨道之间切换；如果遥测显示网页端单一变体的重建成了问题，再另写一份提议，为 yt-dlp 片源做节点档位表。

### 删除或简化什么

- `play()` 不再因为换画质、预读过期或换路径而替换引擎，`onLoad()` 也去掉对画质 `load` 的 `Math.max(getPlaybackPosition(), startTime)` 修正：新流本来就从 T 开始。
- 控制器 18 个策略参数中去掉 7 个：第 1 阶段去掉 `upMinAfterDownMs`、`upMaxSustainMs`、`oscillationWindowMs`、`penaltyResetMs`；第 3 阶段去掉 `downAfterDrainingMs`、`downCooldownMs`、`minRemainingSeconds`。`healthyBufferSeconds` 变成满水位。
- Hub 的 30 分钟记忆（`QUALITY_MEMORY_MS`）变成按路径、不过期的记忆。
- `<video>` 多变体流卡顿后降档的做法删除。
- `isRecoverablePlaybackError()` 不再匹配解码器的消息：解码错误由引擎处理，只有阶梯的最后一步才交给播放器。
- Plex 插件从码率到画面的表，变成一份经过检查的档位清单。

### 从其他播放器借鉴什么

- **hls.js**（1.7.3，`<video>` 引擎打包的版本）。它的自动切换只决定下一个片段的档位，从不清空缓冲；只有手动设置 `currentLevel` 或 `nextLevel` 才会（[`hls.ts`](https://github.com/video-dev/hls.js/blob/v1.7.3/src/hls.ts#L760-L820)）。它的估计取快、慢两个移动平均中较小的一个（点播为 3 秒和 9 秒），同档或降档时用估计的 0.95，升档时用 0.7；如果下完正在下载的片段所需的时间比剩下的缓冲还长，就放弃这个片段（[`config.ts`](https://github.com/video-dev/hls.js/blob/v1.7.3/src/config.ts#L507-L516)、[`abr-controller.ts`](https://github.com/video-dev/hls.js/blob/v1.7.3/src/controller/abr-controller.ts)）。借鉴：新码率只用于还没下载的部分，升档的余量比降档更严，以及取消 T 之后的预读。
- **Shaka Player**（4.16）。它的 ABR 切换默认不清空缓冲（`clearBufferSwitch: false`），新变体在已缓冲的内容之后才播放。估计累计到 128 kB 之前它不做决定，最多每 8 秒切换一次，估计取半衰期 2 秒和 5 秒的两个移动平均中较小的一个（[`player_configuration.js`](https://github.com/shaka-project/shaka-player/blob/v4.16.53/lib/util/player_configuration.js#L315-L344)、[`simple_abr_manager.js`](https://github.com/shaka-project/shaka-player/blob/v4.16.53/lib/abr/simple_abr_manager.js)）。借鉴：不清空缓冲，以及第一次决定之前要有最少的样本数，控制器的 `minSamples` 已经是这样。
- **Media3**（1.11.1，ExoPlayer 的后继）。`AdaptiveTrackSelection` 在缓冲不足 10 秒时推迟升档，在缓冲达到 25 秒或更多时推迟降档，并在估计的 0.7 以内选最好的轨道（[`AdaptiveTrackSelection.java`](https://github.com/androidx/media/blob/1.11.1/libraries/exoplayer/src/main/java/androidx/media3/exoplayer/trackselection/AdaptiveTrackSelection.java#L318-L324)）。`DefaultBandwidthMeter` 按网络类型和国家给出初始估计（4G 为 0.68 到 2.5 Mbps），网络类型变化时重置（[`DefaultBandwidthMeter.java`](https://github.com/androidx/media/blob/1.11.1/libraries/exoplayer/src/main/java/androidx/media3/exoplayer/upstream/DefaultBandwidthMeter.java#L56-L84)）。借鉴：围着死区的缓冲水位线，以及按网络种类起步，Yolo 按路径从屏幕自己的历史里学到这个起点。不借鉴：丢弃前方 25 秒以外的已缓冲块，再以更高画质重新下载。
- **Netflix 基于缓冲的码率自适应**（[Huang 等，SIGCOMM 2014](https://yuba.stanford.edu/~nickm/papers/sigcomm2014-video.pdf)）。没有找到 YouTube 生产环境 ABR 的官方或经过同行评审的描述，所以这里采用的大型服务公开设计是 Netflix 的：稳定状态下码率跟随缓冲水位，水库（reservoir）以下用最低码率，其上的缓冲垫（cushion）里码率逐步升高，容量估计只在起步阶段起作用。在 Netflix 的服务上，它与当时的默认算法相比，在平均码率相近的情况下把重新缓冲减少了 10% 到 20%；它的第一个版本用 240 秒的缓冲和 90 秒的水库。借鉴：稳定状态下由缓冲决定，通过水位线和死区；车上 210 秒的缓冲是同一个量级。

### 决定

1. **没有记住码率时的默认起步：**远程直连播放和中继用 1500 kbps；局域网从它的上限起步。
2. **记忆的有效期：**不过期。记住的码率只决定一个流从哪里起步；有余量时，控制器照样会升档。
3. **车上的升档：**第 3 阶段上线前，只在一个流到下一个流之间升；上线后，在条目内从缓冲末尾升。
4. **canvas 引擎的水位线：**低水位 60 秒，满水位 180 秒。
5. **Plex 的档位：**只用在用户本人的 Plex 服务器上检查过解码画面的档位，目前是 4800 kbps 对应 1280×720、1500 kbps 对应 852×480，去掉 2200 kbps。3000 kbps 的 720p 和 700 kbps 的 360p 检查过后再加入。
6. **网页端单一变体的流：**在新规则下替换；暂不为 yt-dlp 片源做节点档位表。

## 分阶段

每个阶段都能单独发布，也能单独回滚。

### 第 1 阶段：从行得通的码率起步，绝不为升档重建

- Hub 按设备和路径记住码率、不过期，`health.rate`，以及各路径的默认起步。
- 两个引擎上升档都不再替换流：它成为屏幕记住的码率，下一个流从那里起步。只为防止升降来回振荡的四个参数删除。降档保持现在的规则，仍然替换流；它触发时缓冲不到 20 秒。
- Plex 插件只保留检查过的档位。
- Yolo 的控制器把 `<video>` 多变体流交给浏览器。

在 2026-10-21，这会保住 19:12:24 时的 216 秒，下一次在中继上出行从 1500 kbps 起步。

### 第 2 阶段：就地恢复

- canvas 引擎里的解码器阶梯，事件里带上出错的解码器、时间戳和分片。
- 在现有的 `videoStallMs` 旁边加一个 `decodeErrorAt` 故障注入，供测试使用。

在 2026-10-21，如果第一步或第二步修好了解码器，19:17:52 的错误只会让画面停顿片刻，而不是约 39 秒、两次新转码和 216 秒的缓冲。

### 第 3 阶段：从缓冲的末尾接着播

- canvas 引擎和它的预取器里的拼接；`player.js` 对换画质、过期或失败的预读、换路径做拼接；Hub 对 `quality` 和 `recovery` 保留屏幕的位置。
- 控制器在两个方向上都用缓冲水位线，条目内从缓冲末尾升档；再删除三个策略参数。

在 2026-10-21，19:04:18 的降档会先播完已缓冲的 6 秒，1500 kbps 的流在它后面填充，而不是等一个从零开始的新流：到它的第一帧要 6 秒，算上那次重启式跳转要 23 秒。

## 回滚

任何一个阶段之后，`npm run yolo -- rollback` 都能回到上一个版本。第 1 阶段的键和 `health.rate` 会被上一个版本忽略，它退回 30 分钟的记忆。第 2 阶段只改播放器。第 3 阶段改播放器，以及 Hub 对两种原因计算位置的方式，不保存任何新数据。没有哪个阶段需要迁移数据。

## 考虑过的其他方案

**调整现有的数值。**升档前等更久、降档前等更短，改变的是什么时候替换流，而不是会不会替换；每次变化仍然扔掉缓冲。

**降低中继的上限，比如 2200 kbps。**它能让车在 2026-10-21 从接近可行的码率起步，但中继上的每块屏幕在每种网络上都要为此付出代价，而且每次变化仍然替换流。按路径记忆能从车自己的历史里给出同样的起点。

**每条路径固定一种画质，像最初的特斯拉播放器那样。**网络撑得住时流畅，撑不住时卡住且没有出路（[自适应画质](../../implemented/feature/2026-10-11-adaptive-quality.zh.md)）。

**节点为每个片源都给出多变体播放列表。**Plex 一次转码只产出一种码率版本，而 canvas 引擎无论如何都需要拼接才能切换变体；见上文。

**在节点里、在同一个会话背后拼接。**节点保留设备的播放列表，用新的转码提供后面的分片。Plex 的分片网格随码率不同，同一条轨道里出现另一种尺寸的画面需要重新配置解码器，而引擎不会在轨道中途这样做，设备也不知道码率在哪里变了。

**两个引擎在 T 交接。**第二个引擎会带来第二个 AudioContext、canvas 和一套解码器，而车上报告的设备内存只有 2 GB，交接时声音也会断。一个引擎加两个 Input，共用音频输出和字节上限。

**丢弃已缓冲的分片，以更高的码率重新下载**，像 Media3 那样。车上的缓冲是它穿过没信号路段的保险，更高的码率可以等到缓冲末尾再用。

**只看吞吐，像现在的控制器大体上那样。**2026-10-21 测得的速率几分钟内就在 0.6 到 4.8 Mbps 之间变化；缓冲水位是更稳定的信号，Netflix 的研究也得出了同样的结论。

**把码率记在屏幕自己的存储里。**不是屏幕发起的播放（agent 的点播、队列的下一项）在 `prepare` 时就需要这个码率，而 `prepare` 由 Hub 发起；一个归属就能同时满足两者。

## 验收标准

- **第 1 阶段。**在一条路径上以某个码率播放过的屏幕，在这条路径上的下一个流从这个码率起步，第二天、由 agent 发起时也是如此。升档不替换流：升档之后没有 `reason: "quality"` 的 `stream_selected`。每一档 Plex 的解码画面都不小于下一档。`<video>` 多变体流不发出 Yolo 的画质请求。
- **第 2 阶段。**注入的解码错误从缓冲恢复，不发流请求，丢掉的已缓冲分片不超过一个图像组（GOP）。在车上，解码错误会显示它的恢复步骤和出错的解码器，除非每一步都失败，否则不会有新会话。
- **第 3 阶段。**换画质、预读过期、换路径，只要缓冲多于新流起播所需，都不卡顿地继续播放；换的时候已缓冲的秒数从不下降，位置跳动从不超过 1 秒。在中继上开一趟，没有由换画质引起的 `stall_start`。

## 风险

- **拼接依赖新流的时间戳。**片源在另一条时间轴上启动新流，或者新流加载时位置读错，都会在错误的地方拼接；2026-10-21 从 8:16 跳到 3:13 就发生在一次画质 `load` 之后，它的修复另行提交。引擎会检查新流的第一个时间戳是否在 T 的一个分片之内，否则退回到在 T 加载；第 3 阶段建立在那个修复之上。
- **T 处的间隙或重叠。**Plex 从中途开始的转码可能略早或略晚于 T：重叠被裁掉，间隙则在最多一个分片的时间里显示最后一帧并静音。
- **低起步要牺牲清晰度。**网络比记住的好的那天，流起步更低，要等缓冲满了才往上升：第 3 阶段是几分钟，第 1 阶段要等下一个流。这正是目标要求的取舍。
- **车上的内存。**拼接期间两个流共用 128 MiB 上限，有一小段时间第一个解码器收尾时第二个已经启动，而车上报告的设备内存只有 2 GB。
- **canvas 引擎里的逻辑更多。**拼接和解码器阶梯都在引擎里，车的端到端测试在 Chromium 里运行它；WebKit 从不运行它。
- **放弃了什么。**第 1 阶段不在条目内升档；`<video>` 引擎仍然替换单一变体的流；已缓冲的分片从不以更高码率重新下载。
