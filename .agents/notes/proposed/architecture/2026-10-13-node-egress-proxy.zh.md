# Agent Note: 媒体节点按规则走代理的出口层

Status: proposed

[English](2026-10-13-node-egress-proxy.md) | 中文

## 问题

片源播放的每个字节都由节点经家里的网络下载（[媒体管线](../../implemented/architecture/2026-10-11-node-media-pipeline.zh.md)），而从这条网络访问片源 CDN 的质量随时间变化很大。2026-10-12 和 2026-10-13 从家里的节点测量，同一个 Bilibili 镜像前一天只有 172 kbps，第二天达到 72 Mbps；其他镜像只有 2–5 Mbps，并且会卡顿。

对冲的分片读取和节点对每个主机的记忆会实时选出最好的镜像（[分片读取](../../implemented/architecture/2026-10-11-node-media-pipeline.zh.md#segment-reads)）。但从节点的网络看所有镜像都慢时，它们帮不上忙；片源只对某些地区开放、而节点不在这些地区的内容，它们也拿不到。

## 提案

在节点核心里加一个出口层，把选定的上游请求经一个有名字的代理发出；再加一种插件类型，用来提供代理。

### 出口层

- **出口层放在节点核心里，不认识任何具体服务商。** 它按 `yolo.config.json` 里的主机规则，对每个请求决定直连还是经某个有名字的代理。
- **它从来不是全局代理。** 没有匹配任何规则的主机直连；通往控制面的 cloudflared 隧道和这台机器的其他所有连接都不受影响。
- **一条规则列出可用的线路。** 规则匹配一组主机模式，列出这些主机可以走的线路，排列顺序是节点没有更好依据时的尝试顺序。`direct` 是其中一条线路；不含它的规则让这些主机只经代理访问，有地区限制的内容需要的正是这样。第一条匹配的规则生效。
- **节点的每条出口路径都用同一套规则：** 管线的上游请求（`upstream.js`、`hedge.js`）、片源插件经插件 API 新增的 `yolo.fetch` 发出的请求、yt-dlp 经 `--proxy` 的解析，以及 ffmpeg 经 `-http_proxy` 对分离输入的读取。
- **子进程拿到的是本机回环监听端口，而不是代理本身。** `--proxy` 和 `-http_proxy` 指向节点在 `127.0.0.1` 上运行的一个 HTTP 代理，它对自己打开的每个连接套用规则，所以 yt-dlp 对未匹配主机的请求仍然直连。凭据不会出现在命令行里，而 Node 的 `execFile` 会把命令行复制进它的错误信息。

```json
{
  "plugins": ["./plugins/source-ytdlp", "./plugins/proxy-url"],
  "egress": {
    "proxies": { "relay": { "provider": "url", "options": { "env": "EGRESS_PROXY_URL" } } },
    "rules": [
      { "hosts": ["*.bilivideo.com", "*.bilivideo.cn"], "via": ["direct", "relay"] },
      { "hosts": ["*.video.example"], "via": ["relay"] }
    ]
  }
}
```

### 代理提供方

代理提供方是一种新的插件类型。节点入口用 `yolo.registerProxyProvider(id, impl)` 注册一个。提供方只负责给出当前的端点 `{ url, username?, password?, expiresAt? }`（`url` 是 `http` 或 `socks5` 地址），并自己处理登录和刷新。Yolo 会在 `expiresAt` 之前、以及代理拒绝凭据之后再向它要一次。提供方从来看不到哪些请求或主机在用它。

- **Yolo 提供一个通用的官方提供方 `plugins/proxy-url`，** 用于从环境变量读取的固定 HTTP 或 SOCKS 地址。用户本人像其他插件一样把它列进 `yolo.config.json`；它不在 `plugins/official.json` 里。
- **商业加速器服务的提供方是本地插件，不是官方插件。** 这类服务要通过私有 API 登录并拿到端点。这个 API 会不经通知地变化，让插件失效；服务条款可能禁止第三方客户端；设备数量限制还可能让节点上的一次登录把用户本人在另一处的会话挤下线。接受这些的用户本人通过 `yolo.config.json` 加载自己的提供方（[插件架构](../../implemented/architecture/2026-10-11-plugin-architecture.zh.md)）；Yolo 不提供绑定某个具体服务的代码。

### 对冲和主机记忆里的线路

直连和经代理是拿到同一份字节的两条线路，所以节点把每一对 URL 和线路当作一个候选。节点对主机的记忆（`hosts.js`）按主机和线路分别记录故障和吞吐。对冲的分片读取在现有的阈值和上限之内，给这些候选排序并让它们赛跑。其他上游请求走排在最前的线路，失败时换到下一条，就像 `file` 请求换到下一个 URL 那样。

没有任何规则按时段生效：一条线路的好坏和镜像一样随时段和字节范围变化，所以只有实时测量才能给线路排序。提供方还没有当前端点的代理，在拿到端点之前不算一条线路。

### 凭据和遥测

- 凭据放在 `.env.example` 记录的环境变量里。`yolo.config.json` 至多写出变量名，任何日志行或错误信息都不包含代理的凭据或完整地址。
- 节点的对冲和切换日志行带上每次尝试的线路，每次分片读取都记录最终完成它的主机和线路，所以遥测会记下每个分片走的是哪条线路。提供方的刷新和失败也会记录，但不含凭据。

### 范围

只有节点到片源这一段会变。设备的路径（经控制面的隧道，以及[局域网直连播放](../../implemented/feature/2026-10-12-lan-direct-play.zh.md)）不变，Plex 也不变。

## 何时开始

工作还没有开始。满足下面任一条件时开始：

- 遥测显示剩下的卡顿都发生在所有镜像都慢的时候：按节点每行日志上的 UTC 时间戳对齐，Workers Logs 里设备的 `stall_start` 事件（[设备埋点](../../implemented/feature/2026-10-11-device-telemetry.zh.md)）对应的正是节点发现这个分片的每个镜像都慢的对冲。
- 用户本人需要片源只对某些地区开放的内容。

## 各部分及复杂度

| 部分 | 复杂度 | 原因 |
|---|---|---|
| 节点核心里的规则和线路选择 | 小 | 只是配置和节点对主机的记忆的纯函数 |
| `hosts.js` 和 `hedge.js` 里的线路 | 中 | 候选变成 URL 和线路的组合；阈值和上限不变，但每个排序和对冲的测试都要加上线路 |
| 节点进程内经代理的请求（`upstream.js`、`yolo.fetch`） | 中 | 为 Node 的 `fetch` 支持 HTTP 和 SOCKS 代理，凭据还会刷新 |
| 给 yt-dlp 和 ffmpeg 用的回环监听端口 | 中 | 一个只接受本机回环连接的 HTTP 代理，按连接套用规则，再直连或经代理转发 |
| 提供方插件类型和 `plugins/proxy-url` | 小 | 注册、在过期前和凭据被拒后刷新，以及一个没有过期时间的提供方 |
| 遥测和脱敏 | 小 | 在现有日志行上加一个线路字段，每个分片再加一行 |
| 某个加速器服务的本地提供方 | Yolo 之外 | 取决于这个服务的私有 API，并随它变化 |

## 曾考虑的替代方案

**全局模式的系统级 VPN 或 TUN 客户端。** 它不需要改 Yolo，但会把通往控制面的 cloudflared 隧道，连同这台机器发出的其他所有流量，都经代理所在的地区转发，于是每个设备的媒体和控制面发给节点的每个请求也都要绕这条远路。

## 验收标准

- 没有 `egress` 配置段时，所有上游请求都直连。
- 有规则时，节点按它对主机的记忆排序，经规则列出的线路读取匹配主机的分片；节点的日志行写明每个分片的线路；未匹配的主机和 cloudflared 隧道从不使用代理。
- 只经代理的规则下的内容能用 yt-dlp 解析并播放。
- 凭据不出现在 `yolo.config.json`、任何日志行、错误信息或命令行里，`.env.example` 记录了每个变量。
- `service/` 里没有任何代理或加速器服务的名字，并且[插件架构](../../implemented/architecture/2026-10-11-plugin-architecture.zh.md)记录把代理提供方列入插件类型。

## 风险

- 代理会增加首字节前的延迟，所以经代理的线路可能在 1.5 秒的首字节阈值上输掉对冲并被降级，即使它的吞吐更高。
- 跨两条线路的对冲可能把同一份字节读两遍，而经代理的字节可能计入付费流量额度。
- 本地提供方在插件信任模型下拥有节点的全部权限，包括 `.env` 和 `NODE_SECRET`，并且服务的私有 API 一变它就会失效。它没有端点时，规则也列了 `direct` 的主机改为直连，只经代理的规则下的内容则无法播放。
- 这台机器上的任何进程都能经回环监听端口发出请求；直接调用全局 `fetch` 的插件会绕过规则。
- 重启后节点对主机的记忆是空的，所以在测出各条线路之前，它按每条规则列出的线路顺序尝试。
- 经代理播放有地区限制的内容，可能与片源的条款冲突。
