# Agent Note: 用 Transocks 账号作出口层的中国代理

Status: implemented

[English](2026-10-28-transocks-proxy-provider.md) | 中文

## 问题

用户的实例把少数只回应中国观众的主机，腾讯视频的播放接口和 B 站的页面，经中国的出口代理发出（[出口层](../architecture/2026-10-13-node-egress-proxy.zh.md)，[B 站页面走出口规则](2026-10-27-bilibili-through-the-egress-rule.zh.md)）。用户付费使用 Transocks，一个加速器，它的浏览器扩展让 Chrome 经账号的某条线路上网。2026-10-28 之前，节点经 `proxy-url` 使用其中一条线路：它的地址和凭据是 2026-10-26 从扩展的存储里手工抄出来的。

2026-10-27 那条线路开始拒绝连接，扩展里存着的另外四条线路也都不通，于是在有人再抄一条新线路之前，用户屏幕上的每个 B 站视频都报 “Unable to connect to proxy”。Transocks 的线路不是固定的：它的凭据属于账号在这条线路上开的一个会话，线路会增减，账号列出六十多条线路，其中一些在国外。

## 决策

一个官方插件 [`plugins/proxy-transocks`](../../../../plugins/proxy-transocks/src/node.js) 注册代理提供者 `transocks`。用户只给账号，插件做扩展连接时做的事。

- **账号放在 `.env` 里：** `TRANSOCKS_ACCOUNT`（邮箱，或者手机号加 `TRANSOCKS_COUNTRY_CODE`）和 `TRANSOCKS_PASSWORD`。`yolo.config.json` 里的代理写明提供者，`"cn": { "provider": "transocks" }`，可选 `options.locations`，线路的位置或名字必须包含的词（`["GuangZhou"]`）。插件不在 `plugins/official.json` 里。
- **它按扩展的方式登录，** 用的是扩展用的接口（[`src/api.js`](../../../../plugins/proxy-transocks/src/api.js)，唯一知道接口格式的文件）：每个请求用 AES-256-CBC 加密，密钥由扩展公开的客户端密钥和请求时间推出，再用 HMAC-SHA1 签名；每个回答也这样解开。节点在 Transocks 那里是一台独立的设备，名字是账号的哈希（`TRANSOCKS_DEVICE_ID` 可以改），所以每次启动都是同一台设备。登录和扩展一样带 `autokick`，设备数满了的账号会登出最早的一台设备，而不是拒绝节点；这是用户 2026-10-28 的选择。
- **它选线路。** 在账号的线路里，它只留出口在中国的，不要国外的中转线路（`isRelay`），也不要接口标为故障的。它从节点测每条线路检测端口的 TCP 连接时间，这就是扩展自己的测速，测两次取短的，然后按顺序试最快的五条：在线路上开一个会话，拿到线路的 HTTP 代理和凭据，再检查代理接受这些凭据并能打开到 `www.baidu.com:443` 的 `CONNECT` 隧道。第一条通过的交给节点。失败的线路十分钟内跳过。线路列表保留一小时，每条线路的测速保留十分钟。
- **它让线路一直能用。** 地址 11 小时后过期，比扩展结束自己的会话早一小时，节点到时再问：插件在同一条线路上开一个新会话，失败了才换线路。代理拒绝凭据之后也这样做。节点说代理失败时（[出口层](../architecture/2026-10-13-node-egress-proxy.zh.md)），插件检查这条线路：仍能建隧道的留下，因为问题在网站；不能的关闭，换成下一条最快的。令牌快过期，或者接口说会话已结束、账号在别处登录时，它重新登录。
- **日志里没有机密。** 日志用线路的名字和位置称呼它，从不写它的地址或凭据，错误里也没有密码或令牌。

## 曾考虑的替代方案

**继续把线路抄进 `proxy-url`。** 这不需要绑定服务的代码，但那一条线路一坏或者会话一结束就不能用，得有人发现、打开扩展的存储、再抄一条；这正是这次问题的起因。

**仓库外的本地插件，** 出口层的笔记起初就是这样定商业服务的。它能让 Yolo 的代码里没有该服务的私有接口，但用户希望这个提供者随每个检出一起发布，并和其他部分一起测试；无论放在哪里，风险都一样，也都由用户承担。

**读同一台机器上扩展的存储。** 这样不用登录，但扩展里只有它连过的线路，它的存储是浏览器的内部数据库，节点也不一定和 Chrome 跑在同一台机器上。

**让 Transocks 自己选（`recommendLine`）。** 接口可以自己挑线路，但它是替发请求的设备挑的，不知道节点自己的连接时间，也不检查线路能不能建隧道。

## 后果

线路坏掉时，用户的中国规则仍然能用：失败之后的下一个请求就会找到另一条线路，没有人需要手工抄任何东西。代价：

- 插件依赖一个私有接口和扩展代码里的常量；Transocks 改了其中任何一个，登录或线路列表就会失败，接口自己的消息出现在节点日志和 `yolo doctor` 的出口状态里，插件需要修改。
- 账号设备数已满时，登录可能登出用户最早的 Transocks 设备，比如 Chrome。
- 到线路检测端口的连接时间衡量的是距离，不是吞吐；近而慢的线路会一直用到它失败为止。
- 账号的密码放在节点的 `.env` 里，在插件信任模型下每个插件都能读到。

[`plugins/proxy-transocks/test/`](../../../../plugins/proxy-transocks/test/) 里的测试固定了：加密封装；对假网关的登录和线路请求；网关切换；以及对假账号的提供者行为：能建隧道的最快中国线路，不响应或不能建隧道的线路被跳过，`options.locations`，代理失败而线路仍能建隧道时保留、不能时换掉，在同一条线路上续期，会话结束后重新登录，日志和错误里没有机密。
