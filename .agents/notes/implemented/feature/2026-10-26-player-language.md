# Agent Note: The player speaks the screen's language

Status: implemented

English | [中文](2026-10-26-player-language.zh.md)

## Problem

The player was written in English only. Its owner speaks Chinese, and the screens that matter most are a car and a phone whose browsers may be set to English: the Mac whose Chrome answers `en-US` heard Chinese voice requests without a Chinese hint, and the speech model, left to detect the language, wrote some of them in traditional characters. Following the browser alone could not say what the person in front of the screen reads and speaks. The pages Yolo's server renders for signing in, pairing, and approving were English too, so a screen set to Chinese sent its owner to an English page.

## Decision

The player shows English or Simplified Chinese, and each screen chooses ([`clients/player/src/i18n.js`](../../../../clients/player/src/i18n.js)).

- **The choice.** **Settings › This screen › Language** offers Automatic, English, and 简体中文, each named in its own language, and keeps the choice in `localStorage` (`yolo.language`), as with the agent the screen asks. Automatic shows [the account's language](2026-11-06-account-language.md) when it has one, and otherwise follows the browser's languages in order: the first that is Chinese, in any script or region, means Simplified Chinese, the first that is English means English, and none of either means English. A choice made on the screen wins over both. Changing it reloads the page, so everything is drawn again in it; the language is read once, when the page loads.
- **The text.** The English text is the key: `t(text, values)` returns the text in the screen's language, from [`clients/player/src/locales/zh-Hans.js`](../../../../clients/player/src/locales/zh-Hans.js) for Chinese, and the English itself where the catalog has no entry. A value goes in by name (`{agent}`), so a translation can place it anywhere in its sentence. The page's own text in `index.html`, its text nodes and `aria-label`, `placeholder`, `title`, and `alt` values, is looked up the same way when the page starts, before anything draws, and `<html lang>` says the language. Dates take the language as their locale.
- **What is translated.** Everything the player itself shows: the home screen, search, episodes, the player's controls and menus, the loading and error screens, Ask and its voice input, pairing, and Settings. Device events, logs, error codes, and what the screen sends to Yolo stay as they are. An API error's message shows as the server wrote it, on the owner's pages too, as do titles, agents' names, and agents' answers.
- **What it says to Yolo.** A screen with a choice sends that language with a voice request (`POST /v1/agent/transcriptions?language=`) and a question to its agent; without one it sends the account's language, or else the browser's. A screen set to Chinese is therefore heard as Chinese by the transcriber, in simplified characters, whatever its browser says ([voice input](2026-10-18-agent-from-the-screen.md#voice-input)), and its agent is told the screen is set to `zh-Hans`.
- **The owner's pages.** The sign-in, pairing, consent, account, and plugin-request pages the control plane renders show the same two languages ([`service/control/src/auth/i18n.js`](../../../../service/control/src/auth/i18n.js)). The server writes them before any script runs, often for a phone that just scanned a QR code, and it cannot read `localStorage`, so it takes the player's order from what it can read: a `yolo-language` cookie, then the account's language, then the `Accept-Language` header in its order of preference, by the same rule as Automatic (`languageFromTags()` in [`service/core/src/language.js`](../../../../service/core/src/language.js)). The player writes that cookie from the screen's own choice each time it loads and clears it on Automatic, so a browser whose player has a choice sees these pages in it. The account's language is the owner's, read from D1 for each page, since most of these pages come before any sign-in; a phone that never opened the player shows it too, and a failed read falls through to the browser. Each request gets its own `t` (`await pageWords(request, db)`), because the Worker answers many at once and a language kept in the module would cross between them. The English text is the key here too ([`service/control/src/auth/locales/zh-Hans.js`](../../../../service/control/src/auth/locales/zh-Hans.js)); the pages' inline scripts take their words from the same `t`, `<html lang>` says the language, and a plugin's title, summary, and privacy line use its `zh` text.
- **The gate.** [`clients/player/test/unit/i18n.test.js`](../../../../clients/player/test/unit/i18n.test.js) reads every `t()` of a literal under `clients/player/src` and the page's own text, and fails when one has no Chinese, when the catalog holds an entry nothing shows, or when a value is named differently in the two languages. Text therefore goes through `t()` as a literal where it is written, never as a variable. [`service/control/test/unit/i18n.test.js`](../../../../service/control/test/unit/i18n.test.js) does the same for `service/control/src/auth`, and renders every page in both languages, failing on English left in a Chinese page's text or script.

The native Apple apps take the same decisions, with the platform's tools ([`clients/apple/Shared/Language.swift`](../../../../clients/apple/Shared/Language.swift)):

- **The choice.** **Settings › This screen › Language** on the iPhone and iPad, and **Settings › Language** on the Apple TV, offer the same three, kept in UserDefaults (`yolo.language`). Automatic shows [the account's language](2026-11-06-account-language.md) when Yolo has one, which a welcome and a `language` message carry and the device keeps for its next launch (`yolo.accountLanguage`); a welcome that leaves it out changes nothing. Without one it follows the system's languages by the same rule as the player ([`ScreenLanguage`](../../../../clients/apple/YoloKit/Sources/YoloKit/Language.swift), in YoloKit with its tests). A change applies at once and leaves whatever plays alone: SwiftUI looks every literal up again when the environment's locale changes, and `t()` reads the language through observation, so what called it draws again. The choice or the account's language is also written to `AppleLanguages`, the system's per-app language and the only thing that reaches what the system draws for the app (the keyboard, the Apple TV player's own menu items, system alerts), which reads it as the app launches; with neither, that key is removed, so the languages in the device's Settings are followed, and iOS's own per-app language counts as one of them.
- **The text.** The English text is the key, in the String Catalog [`clients/apple/Shared/Localizable.xcstrings`](../../../../clients/apple/Shared/Localizable.xcstrings), and `InfoPlist.xcstrings` translates the local network prompt. A literal in SwiftUI (`Text("Home")`) needs nothing more than the locale `RootView` sets; text that is a `String` before SwiftUI sees it goes through `t("…")`. A value goes in by position (`%@`, `%1$@`) as the compiler writes it. The Chinese is the player's where the two say the same thing. Dates take the language with the device's region as their locale.
- **What is translated.** Everything the apps themselves show, with the player's exceptions: what they report to Yolo, such as a stream's failure, stays English, and titles, agents' words, and the server's stay as written. YoloKit carries no text the apps show except the languages' own names and the message it gives a refused credential: an agent's steps, a busy screen's question, and an unnamed track's name belong to the app layer.
- **What it says to Yolo.** A question to the agent carries the choice, then the account's language, else the system's first language. The Apple TV has no voice request of Yolo's own: Ask's field dictates through the system keyboard, which speaks the system's language.
- **The gate.** [`scripts/apple-strings.test.js`](../../../../scripts/apple-strings.test.js) runs in `npm run check`, which compiles no Swift, so it reads the apps' source as the player's gate does: every literal in a call that looks it up needs Chinese, the catalog holds nothing else, a value's types match in both languages, and a literal that must go through `t()` fails: one after `??` or in a UIKit title, which would show as written, and a navigation title or search prompt, where a bar can keep a literal's old language after a second change. An entry a build of Xcode adds to the catalog is then the same key the gate read.

## Alternatives considered

**Following the browser's language only.** It needs no setting, but the car's and the owner's own browsers are set to English while the owner reads and speaks Chinese, which is how voice requests came back in traditional characters. The browser stays the default; a choice on the screen overrides it.

**One language for the whole account.** Owner settings sit behind the passkey session, which the car rarely has, and two people watching on different screens may read different languages. A per-screen choice is made where it is seen, without signing in, like the agent the screen asks. The account now keeps a default for screens on Automatic ([account language](2026-11-06-account-language.md)), and each screen's choice stays.

**Symbolic keys (`ask.listening`) or a library such as i18next.** Keys would need an English catalog beside the code and a lookup to read any screen's text, and a library adds a dependency and a format to a client that has none. The English text as key keeps the code readable as it was, falls back to English by itself, and the gate keeps the catalog complete.

**Switching the language in place, without a reload.** Every screen would have to draw itself again on a change, and text made when a module loads would stay in the old language. A language changes rarely, from Settings, so a reload is the simpler whole.

**A script on the owner's pages that reads `localStorage` and redraws them.** It needs no cookie, but each page would first show in the browser's language, and the answer to a form would have to be drawn again the same way. The cookie tells the server before it writes anything, a form's answer included.

**The language in the pairing link.** A screen set to Chinese could put its language in its QR code, and the sign-in page would have to carry it through `next`. The page is read on the phone by whoever holds it, so that phone's own choice decides, then the account's language, which every screen already shares.

**For the Apple apps, `AppleLanguages` alone.** It would translate everything with no lookup of Yolo's own, but it takes effect only at the next launch, an iOS or tvOS app cannot relaunch itself, and an app that quits is treated as a crash. Its matching would also not give Simplified Chinese to a system set to Traditional Chinese, which the player's rule does. It stays as what reaches the system's own text.

**For the Apple apps, a catalog of Yolo's own in place of a String Catalog.** A dictionary as the player's would keep one shape across clients, but SwiftUI looks literals up in the app's String Catalogs by itself, Xcode finds their keys when it builds, and the system needs a real `zh-Hans.lproj` in the app before it shows its own text in Chinese.

**Converting the transcriber's traditional characters to simplified on the node.** It would fix only the voice input's script, for every owner, including those who read traditional characters, and not the language the player shows. The screen's choice settles both, and an automatic screen still follows the account's language or its browser.

## Consequences

A screen set to Chinese reads Chinese throughout and is heard as Chinese, in simplified characters, whatever its browser says. Every new text in the player or on the owner's pages needs its Chinese in the same change, which the gates enforce, and a sentence is written whole with named values rather than built from pieces. Text from Yolo's server and from agents is not translated, so a Chinese screen or owner's page can still show an English error from the server. A browser with a chosen language sends one short cookie with each request to Yolo's origin, which the server reads for these pages and does not keep. A phone that never opened the player shows the account's language, or else its own languages; anyone who opens one of these pages sees it in the account's language, signed in or not. Only English and Simplified Chinese exist; another language is a catalog and a line in `LANGUAGES`. Changing the language reloads the page, which stops what the screen plays until it resumes. In the Apple apps a change takes no reload, and what the system draws for the app follows only at the next launch, so until then a keyboard or the Apple TV player's own menu items can be in the language before; text a model already holds, such as an answer on Ask's screen, stays as it was written. Every new text in the Apple apps needs its Chinese in the same change too, which their gate enforces.
