# Agent Note: What plays next

Status: implemented

English | [中文](2026-10-23-up-next.zh.md)

## Problem

When an item ended, the Hub played the queue's head or stopped. A show's episodes and a multi-part video's parts never followed one another: the owner, watching the first of eight parts of a show on Bilibili, played that part four times. Nothing on the screen said what would play next, and when nothing followed, the player sat on the last frame, paused, with Next greyed out. An agent could queue one item a call, so "the next ten episodes" took ten calls, and a Bilibili video's other parts were reachable only by importing them as a playlist.

## Decision

### The order

`next`, and an item that ends, take the walk forward through history first ([Hub](../architecture/2026-10-07-hub-and-realtime-channel.md#previous-and-next)), then the queue's head, then the next item of the run of what was playing. The queue is what the owner asked for, so it goes first; the run is what they were watching, so it goes on once the queue is empty, as a music player goes back to an album after the songs queued into it.

### The run

A source says which run an item belongs to with `sequence(source)` ([source plugin API](../architecture/2026-10-11-source-plugin-api.md#methods)): every item in playing order and the item's place among them.

- **Plex:** an episode's run is its show's episodes, across seasons, from one `allLeaves` listing; a movie has none.
- **yt-dlp:** a Bilibili video's run is its parts, from a flat listing of the page without `?p=`; a URL with `list=` is in that playlist. Every video of a run shares the one listing for 10 minutes, and any other URL costs no yt-dlp run ([`sequence.js`](../../../../plugins/source-ytdlp/src/sequence.js)).

The node passes the run from the item on, at most 50 items after it (`GET /internal/v1/sequence`, [node's internal API](../architecture/2026-10-07-node-internal-api.md)).

The Hub keeps the run in its storage (`run`: its title and the items after the one it is at). An item played directly (a tap, an agent's `play`, previous) replaces it: the Hub drops the old run and asks the node for the new item's run in the background, so the stream never waits for it. A queue item keeps the run. A play from the run moves it on, and asks the node again when fewer than 10 items are left, keeping what it has when the answer has none. An item the listing leaves unnamed, such as a Bilibili part, is described before it shows as next. A node from before this change has no such route, which reads as no run.

### What the state says

The `PlaybackState` names what `next` plays: `upNext: { from, title?, item }`, where `from` is `history`, `queue`, or `sequence` and `title` names the run. The Hub refreshes it after a play, a change to the queue, and the node's answer. A screen shows Next while `upNext` is there; it reads the walk and the queue as before only from a Hub that sends no `upNext`.

### On the screen

In an item's last 20 seconds, on items of at least 90 seconds, a card names what plays next, with Play now (the player's Next) and a dismiss ([`up-next.js`](../../../../clients/player/src/up-next.js)). Play now fills from the left as the item runs out, so the time left shows without a number to read. After a dismiss, the screen's `ended` says `advance: false`, and the Hub stops the item there, as when nothing follows. An item that ended on the screen with nothing after it shows "Finished" under the centre button, which plays it again, instead of a paused last frame.

In the car profile the card and every sheet sit on the left, the driver's side, in reach from the steering wheel; the web profile keeps them on the right.

### Agents

`queue_add` and `POST /v1/queue` take `count`: the item and the ones after it in its run, up to `count` in all and 30 at most. Items the listing leaves unnamed are described, and the answer's `items` says how many there were.

## Alternatives considered

**The run before the queue.** A streaming service plays the next episode whatever else is pending, but it has no queue. Yolo's queue is what the owner or an agent asked for, so it goes first, and the run picks up after it.

**A countdown on the Hub after `ended`.** It would need its own timer and state across hibernation, and the screen would sit on the last frame while it ran. The card before the end puts the choice where the owner is looking and lets the next item start at once.

**Copying the run into the queue.** Each play would put up to 50 items into the queue, which the owner would have to clear when they turn to something else.

**Dragging the card and the sheets to where the owner wants them.** A drag fights taps and scrolling, a sheet has nowhere better to go, and a left-hand-drive car needs nothing set up for the driver's side. A right-hand-drive car would need a switch for the side.

**Naming every item of a run.** That takes one yt-dlp run per part; only the next item shows, so only it is described.

## Consequences

A show or a multi-part video plays through without the owner, Next works at the end of a queue, and an agent queues a season in one call. Each item played directly costs one more node request (for Plex two library requests, for yt-dlp one flat listing shared by the run), and an unnamed next part one more `describe()`. Each Bilibili part is its own item in history (`?p=2`), and the first part spelled with and without `?p=1` stays two items, as before. A video opened from a YouTube playlist goes on for the 50 videos after it, since the videos' own URLs name no list to ask again. The Apple TV goes on through the run, since the Hub plays it, but shows no card.

## Deferred

The Up next sheet in the player, play next and play last from each card's menu, a Continue Watching row with one card for each run, a history page, and the card on the Apple TV are designed but not built.
