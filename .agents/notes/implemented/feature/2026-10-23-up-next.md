# Agent Note: What plays next

Status: implemented

English | [中文](2026-10-23-up-next.zh.md)

## Problem

When an item ended, the Hub played the queue's head or stopped. A show's episodes and a multi-part video's parts never followed one another: the owner, watching the first of eight parts of a show on Bilibili, played that part four times. Nothing on the screen said what would play next, and when nothing followed, the player sat on the last frame, paused, with Next greyed out. An agent could queue one item a call, so "the next ten episodes" took ten calls, and a Bilibili video's other parts were reachable only by importing them as a playlist.

## Decision

### The order

`next`, and an item that ends, take the walk forward through history first ([Hub](../architecture/2026-10-07-hub-and-realtime-channel.md#previous-and-next)), then the queue's head, then the next item of the run of what was playing. The queue is what the owner asked for, so it goes first; the run is what they were watching, so it goes on once the queue is empty, as a music player goes back to an album after the songs queued into it.

### The run

A source says which run an item belongs to with `sequence(source)` ([source plugin API](../architecture/2026-10-11-source-plugin-api.md#methods)): every item in playing order and the item's place among them.

- **Plex:** an episode's run is its show's episodes, across seasons, from one `allLeaves` listing, each labelled with its season and episode ("S1 · E3"); a movie has none.
- **yt-dlp:** a Bilibili video's run is its parts, from a flat listing of the page without `?p=`, which names none of them: Bilibili's own part list gives each its name and length in one request, each is labelled with its place ("P3"), and each shows the video's cover, which every part shares. A URL with `list=` is in that playlist. A Bilibili series' episode page (`bangumi/play/ep…`) is in its season: Bilibili's season API names the show and its episodes in one request, without trailers and extras, each labelled with its number ("E3") and named "<show> 第3集", and a season page (`bangumi/play/ss…`) is its first episode ([`bilibili-bangumi.js`](../../../../plugins/source-ytdlp/src/bilibili-bangumi.js)). Every video of a run shares the one listing and part list for 10 minutes, and any other URL costs no yt-dlp run ([`sequence.js`](../../../../plugins/source-ytdlp/src/sequence.js)).

A run item's `label` is its short place in the run, for the cards that show it.

The node passes the run from the item on, at most 50 items after it (`GET /internal/v1/sequence`, [node's internal API](../architecture/2026-10-07-node-internal-api.md)). A screen reads it with `GET /v1/library/items/:id/sequence`: `{ title, items }`, each item with its `sourceKey`, Source, title, thumbnail, and duration, the item asked about first, and no items for an item in none or from an older node. The iPhone player lists it beside the picture.

The Hub keeps the run in its storage (`run`: its title and the items after the one it is at). An item played directly (a tap, an agent's `play`, previous) replaces it: the Hub drops the old run and asks the node for the new item's run in the background, so the stream never waits for it. A queue item keeps the run. A play from the run moves it on, and asks the node again when fewer than 10 items are left, keeping what it has when the answer has none. An item its source leaves unnamed (a playlist's, or a Bilibili part when Bilibili's part list did not answer) is described before it shows as next. A node from before this change has no such route, which reads as no run.

### What the state says

The `PlaybackState` names what `next` plays: `upNext: { from, title?, item }`, where `from` is `history`, `queue`, or `sequence` and `title` names the run. The Hub refreshes it after a play, a change to the queue, and the node's answer, and each time it names another item, has the node resolve that item ahead for the screen that plays (`warm`), so Next and the item's end start it sooner. A screen shows Next while `upNext` is there; it reads the walk and the queue as before only from a Hub that sends no `upNext`.

### On the screen

In an item's last 20 seconds, on items of at least 90 seconds, a card names what plays next, with Play now (the player's Next) and a dismiss ([`up-next.js`](../../../../clients/player/src/up-next.js)). Play now fills from the left as the item runs out, so the time left shows without a number to read. After a dismiss, the screen's `ended` says `advance: false`, and the Hub stops the item there, as when nothing follows.

An item that stopped at its end on the screen while something was next leaves the end screen: the last picture dimmed, "Finished", Play again, and a home screen row of everything next would have played, in its order, each card playing its item here (a queue item from the queue). So after episode 2, episode 5 is one tap. The row comes from `GET /v1/playback/up-next` ([`/v1`](../architecture/2026-10-07-v1-http-api.md)): forward through the walk, the queue, then the run, at most 30, for the item that ended even after the Hub went idle. An item that ended with nothing after it shows "Finished" under the centre button, which plays it again, instead of a paused last frame.

A press that plays something else here (Next, Previous, Play now, a card on the end screen) is answered at once: the item it plays shows its picture and title under the loading ring, and the item on screen pauses, because Yolo sends the `load` only once the node has prepared the stream, a few seconds for a web video. A refusal puts the screen back and says why. An item that plays to its end with something next shows that item starting the same way while the Hub goes on to it; the Hub stopping instead, or no stream within 30 seconds, puts the screen back.

In the car profile the card, Play again, and every sheet sit on the left, the driver's side, in reach from the steering wheel; the web profile keeps them on the right.

### Agents

`queue_add` and `POST /v1/queue` take `count`: the item and the ones after it in its run, up to `count` in all and 30 at most. Items the listing leaves unnamed are described, and the answer's `items` says how many there were.

## Alternatives considered

**The run before the queue.** A streaming service plays the next episode whatever else is pending, but it has no queue. Yolo's queue is what the owner or an agent asked for, so it goes first, and the run picks up after it.

**A countdown on the Hub after `ended`.** It would need its own timer and state across hibernation, and the screen would sit on the last frame while it ran. The card before the end puts the choice where the owner is looking and lets the next item start at once.

**Copying the run into the queue.** Each play would put up to 50 items into the queue, which the owner would have to clear when they turn to something else.

**Dragging the card and the sheets to where the owner wants them.** A drag fights taps and scrolling, a sheet has nowhere better to go, and a left-hand-drive car needs nothing set up for the driver's side. A right-hand-drive car would need a switch for the side.

**Naming every item of a run with yt-dlp.** That takes one yt-dlp run per part. Bilibili's part list names a video's parts in one request; an item another source leaves unnamed is described only when it shows next, and the end screen labels it by its place.

**Playing the end screen's first card after a countdown.** The card before the end counts down already; the end screen is where the owner chose not to go on, so nothing there plays by itself.

## Consequences

A show or a multi-part video plays through without the owner, Next works at the end of a queue, and an agent queues a season in one call. Each item played directly costs one more node request (for Plex two library requests, for yt-dlp one flat listing shared by the run, and for a Bilibili video one request to its part list), and an unnamed next item one more `describe()`. Resolving what plays next ahead costs a web video one yt-dlp run when it changes, the run Next then skips. Each Bilibili part is its own item in history (`?p=2`), and the first part spelled with and without `?p=1` stays two items, as before. A video opened from a YouTube playlist goes on for the 50 videos after it, since the videos' own URLs name no list to ask again. The Apple TV goes on through the run, since the Hub plays it, but shows no card and no end screen.

## Deferred

The Up next sheet in the player, play next and play last from each card's menu, a Continue Watching row with one card for each run, a history page, and the card and the end screen on the Apple TV are designed but not built.
