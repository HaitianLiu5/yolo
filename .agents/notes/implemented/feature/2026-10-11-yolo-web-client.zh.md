# Agent Note: Yolo Web：带设置页的浏览器客户端

Status: implemented

[English](2026-10-11-yolo-web-client.md) | 中文

## 问题

车上的播放器曾是 Yolo 唯一的屏幕。在电脑或手机上，用户本人无法浏览片库、在浏览器里播放，也不能把浏览器当作车上播放的遥控器。也没有设置页：撤销 agent（智能体）只能手动删除它在 `OAUTH_KV` 里的记录，passkey 和设备只能通过 `/v1` 和 MCP 管理；车的显示大小是首页最下面一排百分比按钮，在 Mac 上显示的档位毫无意义（100%、77%、68%……）。

## 决策

### 一个应用，两种 profile

车上的屏幕和 Yolo Web 是同一个应用，即播放器（[`clients/player`](../../../../clients/player)），在站点根路径下以一份打包提供，其中的 [`player.js`](../../../../clients/player/src/player.js) 驱动两个播放引擎（[两个引擎](../architecture/2026-10-12-two-playback-engines.zh.md)）。[`profile.js`](../../../../clients/player/src/profile.js) 选择 profile，并写到 `<html data-profile>` 上：

| | `car` | `web` |
|---|---|---|
| 何时 | 用户本人为这台设备选的类型是「car」；Yolo 还没告诉页面类型时，[特斯拉指纹](2026-10-07-device-code-pairing.zh.md)匹配 | 其他所有类型：电脑或手机的浏览器 |
| 显示大小 | 在设置里提供（[显示大小](2026-10-11-display-size.zh.md)） | 没有：用浏览器自己的缩放 |
| 引擎 | canvas 引擎 | 被特斯拉指纹认出的页面用 canvas 引擎；其他情况用浏览器的 `<video>` 元素，只能跑 canvas 引擎时用 canvas 引擎 |
| `hello` 里的能力描述 | `CAR_CANVAS_CAPABILITIES` | 被特斯拉指纹认出的页面为 `CAR_CANVAS_CAPABILITIES`；其他情况为带浏览器编码的 `WEB_NATIVE_CAPABILITIES`，`maxHeight` 按显示屏取 2160、1440、1080 或 720（`displayMaxHeight`）；用 canvas 引擎时为 `WEB_CANVAS_CAPABILITIES`；两个引擎都不能用时为 `REMOTE_CAPABILITIES`（[能力协商](../architecture/2026-10-07-capability-negotiation.zh.md)） |
| 点一个条目 | 在本机播放 | 在正在播放的地方播放（见下文） |
| 配对 | 二维码优先 | 用户本人的 passkey 优先，配对码作为从另一台设备批准的方式 |

用户本人选的类型（配对时选，或之后在设置里改）在 profile 上优先于指纹（布局、显示大小，以及点一下在哪里播放），并记住供下次打开使用；类型改变时，布局立即跟着变。被特斯拉指纹认出的页面，引擎不由类型决定：这样的页面总是用 canvas 引擎播放，并声明 `CAR_CANVAS_CAPABILITIES`，所以类型无法在这一点上纠正指纹的误判（[两个引擎](../architecture/2026-10-12-two-playback-engines.zh.md)）。其他页面上，类型改变后引擎从下一个流开始改变，能力描述从下一次连接开始生效。应用每个页面上的 COOP/COEP 和自动播放规则（浏览器不让出声时静音播放，并提示「Tap for sound」）在两种 profile 下都保持；canvas 渲染只属于车。

### 各种窗口尺寸下的布局

- **车上**，CSS 视口约 773×601、像素比 1.53，默认显示大小下页面按 946 像素宽排版。行的上方是一条细的页头（左侧是 Yolo 标志、Ask 和 Ask 的麦克风，驾驶位够得着，然后是搜索和设置）；设置以面板形式盖住窗口右侧三分之二（`min(620px, 66cqw)`）。浏览器窗口在车机应用栏的上方结束，所以不需要避让它（[设计原则](../architecture/2026-07-13-in-car-design-principles.zh.md)）。
- **电脑上**是同样的行，边距更宽，搜索框居中、最宽 560 像素，设置是从右边缘滑出的面板（`clamp(380px, 42cqw, 560px)`），正在播放栏悬浮、最宽 960 像素。
- **手机上**（640 像素及以下）只显示标志不显示文字，设置铺满整个窗口，设备选择器是底部面板，正在播放栏只显示设备名；各行把操作放到文字下方，而不是挤压文字。

### 点一下在哪里播放

由 [`play-target.js`](../../../../clients/player/src/play-target.js) 决定。车在自己身上播放：它就是车里人面前的那块屏幕。Yolo Web 像 Spotify Connect 一样在正在播放的地方播放：如果正在播放或暂停的是另一台在线设备，就在那台设备上播，这样当遥控器用的手机或电脑不会意外把播放抢过来；别处没有在播时，在这个浏览器里播。不能播放的浏览器把这一下交给上一次播放的设备，或者唯一一台在线的其他设备；有好几台时，由用户本人选一台。

### 遥控器

另一台设备在播放时，首页显示正在播放栏（[`remote.js`](../../../../clients/player/src/remote.js)）：条目、「Playing on」哪台设备、根据 Hub 的 `position` 和 `positionAt` 推算的进度线、后退 10 秒、播放/暂停、队列下一项，以及用 `PUT /v1/playback/device` 切换播放设备的设备选择器；这个浏览器能播放时，也可以切到它自己。所有命令都用这台设备的凭据走 `/v1`；正在播放栏只读取 Hub 的 `state`、`queue` 和 `devices` 广播，从不回应它们（[Hub](../architecture/2026-10-07-hub-and-realtime-channel.zh.md)）。Hub 的播放状态、队列和播放列表，无论来自广播、welcome、首页加载，还是这块屏幕自己改动后的回应，都写进同一个地方（[`store.js`](../../../../clients/player/src/store.js)）；由它重绘每个显示这些内容的界面（队列和播放列表两行、正在播放栏、播放器的上一个和下一个），并判断上一个和下一个有没有地方可去。

### 搜索

页头的搜索框在用户本人输入时查询 `/v1/library/search`（停顿 300 毫秒后、从两个字符起）；粘贴一个 http(s) 链接时提供 **Play link** 和 **Add to queue**，播放时由片源插件认领它。

### 设置

设置是 `/settings` 上的模态面板（[`settings.js`](../../../../clients/player/src/settings.js)），从首页页头的齿轮打开，分三组：

- **This screen（这块屏幕）**：标题下是 Yolo 给这台设备的名称和类型；然后是显示大小（仅车上）、**Danmaku**（弹幕）及开着时才显示的密度、区域、不透明度和字号（[弹幕](2026-10-13-danmaku.zh.md)）、**Home network**（家庭网络），即通过家庭网络播放的开关，及这块屏幕最近一次探测的结果（[局域网直连播放](2026-10-12-lan-direct-play.zh.md)）、**Media path**（媒体路径），即这块屏幕下一个流走的路径，走中转或无路可走时附上直连路径没有应答的原因（[媒体离开 Worker](../architecture/2026-10-13-media-off-the-worker.zh.md)）、**Ask with**（这块屏幕的 Ask 问哪个 agent）、**Microphone**（麦克风）及其测试（[屏幕直接问用户自己的 agent](2026-10-18-agent-from-the-screen.zh.md)），最后是 **Forget this screen**（`DELETE /v1/devices/self`），解除它的配对。这几项用设备凭据就够了。
- **Your Yolo（你的 Yolo）**：设备（每台写明类型、是否在线和上次播放走的路径；一个 Edit 在原地打开名称、带图标的分段类型选择和 Remove）、已连接的 agent（每个 OAuth 客户端一行，可撤销）和**重置图片链接**（让 agent 拿到过的每个封面链接都失效；[封面图片](2026-10-07-remote-mcp-server.zh.md#cover-images)）、分享链接（[分享链接](2026-10-20-share-links.zh.md)）、passkey（列出、再添加一个、除最后一个外都可移除）、媒体路径（家庭网络的状态和节点地址，可以立即检查；远程直连播放的开关；中转的模式），以及退出登录。它们使用需要用户本人 passkey 会话的[用户本人的路由](../architecture/2026-10-07-v1-http-api.zh.md#owner-routes)，从不使用设备凭据。登录在页面里用现有的 `/auth/passkey/*` 接口跑 WebAuthn，所以播放不会中断；车的浏览器可能用不了 passkey，所以车上还会显示一个二维码，用手机扫码即可在手机上打开这些设置。
- **About（关于）**：版本和提交、媒体节点的状态和版本，以及 `/diag`。

每一行只说一件事：它的名称、几个字的状态，只在用户本人有事可做时才给出解决办法；只在排查问题时才看的细节（证书日期、路由器映射方式）交给 `yolo doctor`。开和关都用开关。几个选项的选择放在名称旁边，面板窄时换到名称下面。这个面板触屏和键盘都能用：48 px 的行里放 40 px 的触控目标，因为设置是停车时改的（[设计原则](../architecture/2026-07-13-in-car-design-principles.zh.md)），没有需要悬停的操作，焦点留在面板里，用 Escape、明显的 Close（以及点面板旁边）离开，返回键也会关闭它。破坏性的操作在原地再问一次（「Remove?」），而不是再弹出一个对话框。

### 配对浏览器

浏览器和车一样用设备授权配对（[设备码配对](2026-10-07-device-code-pairing.zh.md)）。在 web profile 下，配对屏幕以用户本人的 passkey 为先：在这个浏览器上已登录（或者在这里登录之后），按一下就能通过 `POST /v1/owner/pairing/approve` 批准这个页面自己的配对码。它仍是同一个只能用一次、10 分钟有效的配对码和同样明确的批准，只是不需要第二台设备；其他网站发不出这个请求（用户本人路由的同源检查）。

### 启动

已配对的屏幕从不等实时通道连上才显示内容，也从不显示「Connecting…」。它把自己显示的内容存进 `localStorage`，只为这台已配对的设备保存（`yolo.home.<device id>`，[`home-cache.js`](../../../../clients/player/src/home-cache.js)）：首页的各行（队列、播放列表、Continue Watching 和片库的行，每行最多 200 项；记录将超过 1.5 MB 时先丢掉片库的行）、Hub 最近一次的 `state`，以及 Yolo 的设备列表；启动时要显示的内容变化后一秒写入（只是位置变化不写），页面隐藏或离开时也写入。解除配对或忘记这块屏幕时删除它，它尚未完成的写入也不会再把它写回来。启动时画不出来的记录（这个版本读不懂的形状）同样会被删除，页面按没有保存任何内容的方式启动，设备事件里记一条 `start_cache_failed`；无论哪种情况，它都会连接。首次绘制之前，[`index.html`](../../../../clients/player/index.html) 的第一个脚本查找设备凭据和这条记录，设置 `<html data-boot>`；然后 [`main.js`](../../../../clients/player/src/main.js) 一边连接通道，一边显示第一个屏幕：

- **有记录（热启动）：** 首页照原样显示，正在播放栏显示保存的状态，静止不动（进度线不往前走）。如果保存的状态表明这块屏幕会续播某个条目（与 [`resume-decision.js`](../../../../clients/player/src/resume-decision.js) 为返回的页面所做的判断相同），就改为显示那个条目的加载屏幕和它的封面图。之后 Yolo 的应答在原位替换各行：条目相同的行不会重画，所以不会闪烁，也不会把封面图再加载一遍。
- **没有记录（冷启动）：** 在某个浏览器里第一次打开，或者清除存储之后。页面绘制启动标志（[`launch.js`](../../../../clients/player/src/launch.js)）：Yolo 标志先以暗色出现，一道光扫过它，随后点亮，背后有一层很淡的光晕，全程不到一秒；开启减少动态效果时，它直接以点亮状态静止显示。它没有最短时长：第一个有内容可显示的屏幕（welcome 的续播、首页、某部剧、配对或一条消息）出现时，它在 360 毫秒内淡出。welcome 在启动后 1.2 秒仍未到，就改为显示带骨架屏的首页。

welcome 之前显示的一切都只供查看。点一下在哪里播放、返回的页面续播什么、保留的播放器、错过的命令，都只依据 welcome。在此之前点一个条目，会先等 welcome，再决定在哪里播放（[`welcome-wait.js`](../../../../clients/player/src/welcome-wait.js)）：只有最近一次点按会等待，它的卡片保持按下状态，等待超过加载圆环的延迟后显示圆环；等待期间的新点按取代它，等待失败的点按则被丢弃：通道停止或屏幕重新配对时静默丢弃；请求等待 welcome 的 20 秒内仍未等到时，首页显示那行一句话的提示「Yolo did not answer in time. Try again.」。车总是在自己身上播放，所以车上会立刻显示该条目的加载屏幕，而它的请求和所有请求一样等待 welcome（[唤醒时的请求顺序](../bug-fix/2026-10-11-wake-request-ordering.zh.md)）。这样的点按优先于续播：它之后的第一次 welcome（页面的第一次，或重新配对后的第一次）不再续播任何东西。正在播放栏的按钮也是如此：最近一次按下会等待，按钮变暗。在此期间打开的设置凭设备凭据认出这块屏幕。首页的数据在一次启动及其 welcome 中只请求一次：请求随启动发出，那次 welcome 带来的加载使用它们的应答，但保留 welcome 发来的队列和播放列表，因为它们更新。如果 welcome 续播了某个条目或执行了一次点按，这些应答就被丢弃，从该条目返回时会重新向 Yolo 请求。首页的每一次加载（启动、从播放器返回、重新连接）都立刻显示首页，各行保持原样，直到新的条目替换它们；重新连接后的加载保持当前的滚动位置。从某部剧的地址启动时，剧集不必等后面片库各行加载完就会显示。

连接和重新连接时，内容上方什么都不显示。通道断开 4 秒后（[`connection-indicator.js`](../../../../clients/player/src/connection-indicator.js)），首页页头的标志变暗，角上出现一个琥珀色小圆点，并告知屏幕阅读器；下一次 welcome 清除它。播放器和它的加载屏幕上不显示这个标记：播放继续，它的请求等待通道。只有需要用户本人处理的状态才保留自己的屏幕：配对（向 Yolo 请求配对码期间，二维码底板、配对码和地址以占位块显示）；另一个窗口正在播放（按 **Take over here** 之后只显示加载圆环等待）；以及错误。

所有等待看起来都一样：冷启动时的启动标志；条目尚在路上的地方显示骨架屏，一道柔和的微光沿一行逐张卡片扫过（车上保持静止：[设计原则](../architecture/2026-07-13-in-car-design-principles.zh.md)）；从点按到画面动起来，条目的封面图上方是那个加载圆环（[设备埋点](2026-10-11-device-telemetry.zh.md)）。没有任何屏幕显示「Connecting…」或「Loading…」。

在端到端测试栈上给每个请求加 150 毫秒（大致相当于移动网络），在浏览器窗口和车的窗口里各重新加载五次取中位数：之前「Connecting…」显示 0.7 秒，首页条目在 1.2 秒后出现。现在热启动在 0.56 秒、紧随首次绘制显示它们，冷启动在 0.92 秒、随 welcome 一起显示。车唤醒后续播时，条目的加载屏幕在 0.75 秒出现；之前要先显示 0.9 秒的「Connecting…」，在 1.14 秒才出现。

### 测试

[`test/e2e/web-playback.test.js`](../../../../test/e2e/web-playback.test.js) 覆盖：通过 `<video>` 引擎播放，用返回回到正在播放栏，用 passkey 配对并在 1440×900 和手机的 390×844 下播放，以及需要 passkey 会话的用户本人设置（设备凭据和跨站请求都被拒绝；改名、撤销一个 agent、保留最后一个 passkey、退出登录）。一个单元测试覆盖每个 profile 选用的引擎，控制面的单元测试覆盖用户本人的路由。[`start-up.test.js`](../../../../clients/player/test/unit/start-up.test.js) 覆盖保存的记录（只属于一台设备、`index.html` 的第一个脚本能找到它、它的大小上限、解除配对后它被彻底删除）、等待 welcome 的按下，以及连接标记的延迟。浏览器在返回之后重新加载、车被唤醒时，都先在 welcome 之前用页面保存的内容显示首页和正在播放栏或加载屏幕，然后换成 Yolo 自己的内容；页面画不出来的记录让它冷启动；唤醒后返回显示的是 Yolo 的历史，而不是启动时的；车在一次点按之后被移除、重新配对，会显示它的首页。

## 曾考虑的替代方案

**为网页客户端做一个设备插件。** 一阶段的两个客户端都是 Yolo 自己的，讲同一套协议，所以实时通道留在核心里；只有一个实现的接口设计不好。

**单独做一个网页应用。** 从 2026.26 版软件起，车的浏览器自称桌面版 Chrome，所以服务器无法把车和电脑分别引到不同的应用；两个应用还会重复外壳、配对和实时通道的代码，并且越走越远。所以改为同一个应用在设备上选择自己的 profile。

**让 `/v1` 认 cookie，这样已登录的浏览器无需配对。** 这会让每个 `/v1` 路由都暴露在跨站请求之下，也打破 [OAuth 服务器](../architecture/2026-10-07-oauth-authorization-server.zh.md)「一种 token」的模型。改为每个浏览器都是一台已配对的设备；用户本人的会话只用于用户本人的设置，以及批准浏览器自己的配对码。

**把用户本人的设置放在服务器渲染的 `/account` 页面上。** 设置必须能在车上作为首页之上的触屏面板使用，而且不离开播放；它们还要显示只有客户端知道的东西（这台设备、它的显示大小）。服务器渲染的页面保留那些必须在设备配对之前就能用的流程：登录、批准配对，以及 agent 的授权确认（[用户本人的网页](../architecture/2026-10-12-owner-web-pages.zh.md)）。

**点一下总是在本机播放。** 当遥控器用的手机只要有人在上面浏览，就会把播放从车上抢走。

**在 welcome 之前显示启动画面。** 这只是把等待藏起来，而不是消除它：票据、socket、hello 和 welcome 要三到四个往返才能显示任何东西，每个往返 150 毫秒时就是 0.7 秒的「Connecting…」。屏幕保存的内容可以立刻显示，welcome 只是确认或替换它。

**把保存的状态当作 Yolo 的状态。** 那样点一下会在保存的状态所说的地方播放，而那台设备可能早已停止；返回的页面也会依据几小时前的状态续播或执行错过的命令。保存的状态只用于显示，决定由 welcome 做出。

## 后果

用户本人可以在电脑或手机上浏览、搜索、播放并控制任何一块屏幕，不碰 `OAUTH_KV` 就能管理设备、agent 和 passkey，只用 passkey 就能配对一个浏览器。车的行为不变：它在自己身上播放，保留 canvas 渲染，显示大小改在设置里。跑不了 canvas 引擎的 iPhone 和 iPad 上的 Safari，用它自己的 `<video>` 元素播放；只有两个引擎都不能用的浏览器才是遥控器。profile 跟随用户本人为设备选的类型，所以被配对成浏览器的车会失去显示大小，直到在设置里把类型改成车；它仍用 canvas 引擎播放（[两个引擎](../architecture/2026-10-12-two-playback-engines.zh.md)）。片源和插件还不能在设置里管理，它们仍在节点上的 `yolo.config.json` 里。启动时显示的是屏幕保存的内容，可能略有滞后：Yolo 应答之后，某一行或正在播放栏可能会变；启动时为某个条目显示的加载屏幕，如果 Yolo 不再续播它，会让位给首页。浏览器的存储里会有用户本人在这里看过的内容的标题和封面链接，与它原本就保存的设备凭据放在一起。
