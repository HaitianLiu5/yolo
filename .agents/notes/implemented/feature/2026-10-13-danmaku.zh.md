# Agent Note: 画面上的弹幕

Status: implemented

[English](2026-10-13-danmaku.md) | 中文

## 问题

Bilibili 的视频带有弹幕：观众的评论，每一条都对应视频里的一个时刻，从画面上滚过，或停在画面顶部、底部。很多人在那里看视频，很大程度上就是为了弹幕，而 Yolo 播放这些视频时没有弹幕。要显示弹幕，每一层都会牵扯到：Bilibili 只是众多插件里的一个提供方，核心代码不能提它的名字；页面只能访问 Yolo 自己的主机；画面上的文字由播放器负责，而不是片源；在车上，canvas 引擎在页面的主线程上呈现视频帧，任何长任务都会表现为掉帧，而弹幕一直在画面上移动。

## 决定

### 评论是片源的一项可选能力

片源插件可以实现 `comments(source, { start, end })`（[片源插件 API](../architecture/2026-10-11-source-plugin-api.zh.md)）。条目没有评论时它回答 `null`，否则回答 `{ comments, start?, end? }`：评论 `{ t, text, mode?, color?, size?, weight? }`（秒；`scroll`、`top` 或 `bottom`；`#rrggbb`；相对正常大小的倍数；提供方给这条评论打的分，0 到 10，观众越想看到分越高），以及这些评论完整覆盖的那一段，至少从 `start` 起，例如提供方给出的一个分段，或整个条目（`end: null`）。[`service/core/src/danmaku.js`](../../../../service/core/src/danmaku.js) 里的 `normalizeComments` 丢掉没有时间或文字的评论，把文字截到 100 个字符，每次回答最多保留 20,000 条。核心、控制面和节点的代码都不提任何提供方。

节点保存这些回答（[`service/node/src/comments.js`](../../../../service/node/src/comments.js)）：它每次向片源要一个 6 分钟的窗口，同一个窗口同时只要一次，记下每次回答覆盖了哪些窗口，任何区间都从已有的内容里给出。失败的窗口要过一分钟才会再要。最多保留 16 个条目、共 200,000 条评论，最久未用的条目先淘汰。片源可能有评论的条目开启会话时，节点趁屏幕加载，先读取开始播放处的那个窗口。同一份缓存回答两个地方：

- **正在播放的屏幕**从自己的媒体会话读取 `/m/{token}/comments?start=&end=`（[媒体管线](../architecture/2026-10-11-node-media-pipeline.zh.md)）；片源可能有评论、且不是直播时，流描述里的 `comments` 就是这个路径。它来自流自己的源站，即节点的局域网或远程监听端口，或者 Yolo 的中转，所以页面不访问别的主机；评论和媒体一样，除非用户本人打开了中转，否则不经过 Worker。
- **agent** 通过控制面的 `nodeFetch()` 读取 `/internal/v1/comments?source=&start=&end=`（[节点内部 API](../architecture/2026-10-07-node-internal-api.zh.md)）；片源没有 `comments()` 时，它回答 `available: false, supported: false`。

### yt-dlp 插件里的 Bilibili

[`plugins/source-ytdlp/src/danmaku.js`](../../../../plugins/source-ytdlp/src/danmaku.js) 为 Bilibili 的页面（`bilibili.com`、`b23.tv`）提供评论，对其他所有网站立即回答 `null`，不运行 yt-dlp。只有在要求字幕时，yt-dlp 才会把条目的评论 XML `https://comment.bilibili.com/<cid>.xml` 列为它的 `danmaku` 字幕，所以插件对每个页面用 `--write-subs --sub-langs danmaku` 运行一次 yt-dlp（`-j` 不写任何文件），并为 32 个页面保留结果。

先用 XML：一次请求拿到整个条目，Bilibili 把它限制在最新的 `maxlimit` 条评论。2026-10-13 匿名实测，对同样的视频，XML 里的评论是 Bilibili 网页播放器所读的分段 protobuf 接口的 2 到 3 倍：44 分钟的视频是 7,200 条对 2,827 条，23 分钟的是 3,600 条对 1,380 条，2 分钟的是 600 条对 283 条。XML 失败、且它的 URL 是 Bilibili 自己的时，插件读取 `api.bilibili.com/x/v2/dm/web/seg.so` 中包含 `start` 的那个 6 分钟分段；超出结尾的分段回答 304，没有评论。模式 1 到 3 和 6 是滚动，4 是底部，5 是顶部；脚本类评论（模式 7、8、9，以及特殊弹幕池）被丢掉。每条评论保留 Bilibili 的 `weight`，即它的「智能云屏蔽」据以屏蔽评论的 1 到 10 分：XML 的第九个字段，分段里的第 9 号字段。

请求带上浏览器的 User-Agent 和 Bilibili 的 Referer，和插件的媒体请求一样，并带上所配置的 cookies 文件（`cookiesFile` 或 `YTDLP_COOKIES_FILE`）里属于该主机的 cookie。浏览器配置文件里的 cookie（`cookiesFromBrowser`）只交给 yt-dlp，所以用它时评论是匿名获取的。一次回答最大 8 MiB，最多等 15 秒。

### 绘制弹幕

评论的样子和移动方式照 Bilibili 网页播放器的默认设置来，取自 2026-10-14 读到的它的代码（`s1.hdslb.com/bfs/static/player/main/` 下 `core.<hash>.js` 里的默认设置和 `npd.491.<hash>.js` 里的渲染器），而不是某个开源弹幕引擎；原因见「曾考虑的替代方案」。[`danmaku-layout.js`](../../../../clients/player/src/danmaku-layout.js) 按媒体时间安排评论的位置：

- **字号。** 正常评论的字号是 Bilibili 在打开「弹幕随屏幕缩放」（它的默认）时，按画面高度（CSS 像素）取的曲线：314 像素以下为 16 像素，之后逐渐增大，约 610 像素时为 25 像素，700 到 816 像素之间为 27 像素，1080 像素时为 42 像素，超过 1300 像素为 40 像素。车上的画面（默认显示大小下高 532 CSS 像素）是 21.8 像素，1440 × 900 窗口的画面（810）是 27 像素。字号设置再把它乘以 0.82 或 1.2，评论自己的字号（Bilibili 的 18、25 或 36）再乘一次。
- **速度。** 滚动评论横穿画面的时间由画面宽度决定，用 Bilibili 的表：558 CSS 像素以下 4.5 秒，888 以内 7.1 秒，1082 以内 8.1 秒，1246 以内 9.1 秒，1452 以内 10.1 秒，1744 以内 11.1 秒，2314 以内 13.1 秒，2560 以内 14.1 秒，再往上是 16.1 秒，每多 500 像素加一秒；所以越长的评论移动越快。顶部或底部评论居中停留 4.5 秒。
- **弹道。** 三种评论共用一组弹道，屏幕上任何两条评论都不重叠：评论占用第一条可用的弹道（从顶部数起，底部评论从底部数起），条件是在与这条弹道上已有的每条评论同时显示的整段时间里，和它保持一段间距（半条弹道高，至少 12 个 CSS 像素）。两条滚动评论之间，这就是 Bilibili 的规则，也是 weizhenye/danmaku 的规则：前一条已完全进入画面并留出间距，后一条（越长越快）在前一条离开之前追不上它；这里对两者同时显示的整段时间精确成立。因此顶部或底部评论占用的弹道上，它显示期间没有滚动评论经过它的位置，它也就不会遮住任何滚动评论。大于正常字号的评论占两条弹道。弹道的高度是当前字号下字幕字体的墨迹高度（一个汉字、拉丁大写字母和下伸部分，由文字 worker 测量一次），加上两侧各 1 个 CSS 像素的描边，再加 1 像素的间距（Bilibili 的行距），按设备像素比乘以车上的 CSS zoom 向上取整到整数设备像素；每条评论的位图正好是它所占弹道的高度，所以不会画进别的弹道。
- **密度。** 在 `normal` 密度下，`weight` 低于 3 的评论被隐藏，和 Bilibili 的智能云屏蔽在默认等级（`aiLevel: 3`）下一样；一秒内进场的滚动评论不超过这块区域的弹道数，这是 Bilibili 的配额（`getRollDanmakuMaxCountPerSecond`）。Bilibili 一次放进整批配额，所以一阵密集的评论会在同一帧进场，每条弹道一条，看上去像一列。这里评论一条一条进场，把配额摊到这一秒里：平均每条比前一条晚一条弹道分得的那份秒数（一秒除以弹道数），每条评论在这个基础上浮动为它的一半到一倍半，同一帧里绝不会有两条进场；而且只要别的弹道放得下，就不进入不到一秒前刚进场那条评论的上一条或下一条弹道，所以一阵评论进入空弹道时会交错排开，而不是叠成阶梯。在 `low` 和 `normal` 密度下，评论为等到轮次和弹道最多等 1 秒，在 `high` 密度下最多等 2 秒，之后就丢掉，和 Bilibili 丢掉放不下的评论一样。`low` 保留约三分之一，每次都是同样的三分之一；`high` 连低分评论也保留。
- **时间。** 暂停的画面在同样的位置显示同样的评论，更快的播放速度让它们移动得更快。加载或跳转后，屏幕从空白开始：那一刻之前的评论都不显示，之后的评论从边缘进场，和 DPlayer、CommentCoreLibrary 跳转后一样。向前跳超过一秒或向后退超过四分之一秒算一次跳转；第一帧比流的起点晚一秒以上，也算一次跳转。新到的评论从已排布的最后时刻接着排；尺寸或密度改变时，按自上次加载或跳转以来（最多往前 16 秒）的播放过程，把同一时刻重新排布一遍。同时在屏幕上的评论最多 200 条。

[`danmaku.js`](../../../../clients/player/src/danmaku.js) 在一块 `<canvas>` 上绘制它们，这块 canvas 覆盖两个引擎中画面本身的矩形，位于画面之上、字幕和控件之下。它在每个动画帧读取正在播放的引擎的位置；canvas 引擎会计数自己画出的帧（`presentedFrames`），用它播放时，只在画面变化时才绘制，所以页面仍按视频的帧率更新。只有在显示评论、页面可见、位置在变时，动画帧才会运行；暂停时画一帧后就停止。尺寸只在窗口、画面、显示大小或某项设置变化时读取，从不逐帧读取；后备存储跟随车上显示大小的 CSS zoom 和设备像素比，每个 CSS 像素最多 2 个设备像素。字体用页面的字幕字体，大小如上，配 Bilibili 的默认描边（描边类型「重墨」）：字形周围约 1 个 CSS 像素宽的深色边，黑色文字则用白色；不透明度是这一层的 CSS opacity。

文字处理从不占用主线程的帧：一个 worker（[`danmaku-worker.js`](../../../../clients/player/src/danmaku-worker.js)）在一个窗口的评论到达时测量其中每一条，事先加载这些评论需要的那部分页面字幕字体（它根据页面的 `@font-face` 规则添加字体），并在每条评论第一次出现在屏幕上时，把它连同描边画进一个 ImageBitmap，只画一次。位图到达后的下一帧，这条评论才显示；这时滚动评论离画面边缘只有几个像素。一帧就是一次清除，加上每条评论一次 `drawImage`；位图最多保留 300 个、共 600 万像素。不能在 worker 里绘制文字的浏览器，就在页面上测量和绘制（[`danmaku-text.js`](../../../../clients/player/src/danmaku-text.js)）。屏幕读取播放位置所在的评论窗口，并在到达下一个窗口前 30 秒读取它。

### 设置，每块屏幕各自保存

每块屏幕在浏览器里保存自己的设置（[`danmaku-settings.js`](../../../../clients/player/src/danmaku-settings.js)），按 [`service/core/src/danmaku.js`](../../../../service/core/src/danmaku.js) 校验：

| 设置 | 取值 | 默认 |
|---|---|---|
| 开或关 | | 开 |
| 密度 | `low`（约三分之一，每次都是同样的三分之一）、`normal`（放得下且不重叠的，一条一条进场，去掉低于 3 分的）、`high`（连低分的也保留，最多等 2 秒弹道；都不重叠） | `normal` |
| 区域 | 画面从顶部起的 `full`、`half`、`quarter` | `quarter` |
| 不透明度 | 0.2 到 1；设置页提供 40%、60%、80%、100% | 0.8 |
| 字号 | `small`、`normal`、`large` | `normal` |

车上和网页上的默认值相同，都是 Bilibili 网页播放器自己的默认值（它代码里的 `dmSetting`）：开，80% 不透明度（`opacity: 0.8`），正常密度并把智能云屏蔽设在 3 级（`dmdensity: 1`、`aiLevel: 3`），字号 100%（`fontsize: 1`），速度适中（`speedplus: 1`）。只有带评论的条目才显示弹幕，而看这些条目的人期待看到它们，Bilibili 也默认显示；车上的媒体电脑（运行 Chrome 148 的 AMD Ryzen）有余力，弹幕占用主线程的开销见下面的实测。区域是唯一的例外：Bilibili 网页播放器出厂是半屏（`dmarea: 50`），但会带上每个账号自己的选择；在 BV1soWF6qEjF 上，用户本人的 Bilibili 只在画面顶部四分之一显示评论，约五行，而 Yolo 的全屏区域用约十七行盖满了画面。顶部四分之一让车上的画面保持清楚，车上有 5 条弹道，1440 × 900 窗口里有 6 条，配合上面的密度，就是 Bilibili 在那里适中密度的样子。全屏区域在显示字幕时空出画面底部的五分之一，所以评论从不遮住字幕。

浏览器只保存这块屏幕上选过的设置，带 `version: 2`，所以没选过的设置都跟随默认值，默认值改了也会生效。Yolo 0.6.0 在改过任何一项之后会保存全部设置；从这样的记录里，不同于 0.6.0 默认值（区域 `full`）的值算作选择，等于它的值让位于当前的默认值。

播放器控件里有一个按钮开关弹幕，只在条目有评论时出现。Settings > This screen 里有这个开关，以及四项选择，每项都是 48 像素的选项。agent 用 `set_danmaku` 修改它们：Hub 给这块屏幕发一条 `danmaku` 消息（[Hub 和实时通道](../architecture/2026-10-07-hub-and-realtime-channel.zh.md)），屏幕应用并保存这项修改。屏幕确认之前，Hub 一直保留这项修改，并在屏幕下一次 welcome 之后重发，所以一条已失效却没人察觉的连接不会把它弄丢；车主在这期间在屏幕上改过的设置项，保持车主设的值，除非页面之后又重新加载过。

### agent 读取的内容

`get_comments` 读取某个时刻前后的评论，默认是正在播放条目的位置，回答很紧凑：30 秒的窗口（最多 120 秒），按时间顺序给出 `{ t, text }`，同一句话说了多次合并成一条并带上次数 `n`，超过 60 条（最多 200 条）时保留重复最多和离该时刻最近的（[远程 MCP 服务](2026-10-07-remote-mcp-server.zh.md)）。

### 埋点

播放器的 `health_heartbeat`（[设备埋点](2026-10-11-device-telemetry.zh.md)）带有 `danmaku`，即弹幕层自上次心跳以来的情况：`enabled`、`available`、`comments`（保存的条数）、绘制的 `frames`、`avgDrawMs` 和 `maxDrawMs`（主线程排布并绘制一帧所用的时间）、`slowFrames`（超过 5 ms 的绘制）、`bitmapsDrawn`、`maxOnScreen` 和 `bitmaps`（保留的位图）。

### 实测开销

在 Apple 芯片 Mac 上的桌面版 Chrome 155 里，用可见窗口模拟车上的尺寸（773 × 601 CSS 像素，设备像素比 1.53，车机 profile，canvas 引擎，默认显示大小），播放 720p30 H.264 HLS，弹幕是把真实 Bilibili 评论重新排定时间做成的测试数据，在 HLS 预取器第一轮突发下载之后的稳定状态下测量。每一行是 8 对 6 秒的窗口，先关弹幕再开；CPU 是 Chrome 各进程之和，取每对之差的中位数，因为 Mac 在不同类型核心之间的调度会让基线在窗口之间相差多达 10 个百分点。

| 测试数据 | 同屏最多 | Chrome 的 CPU，关 → 开 | 差值中位数（GPU 进程、渲染进程） | 掉的视频帧，关 / 开 | 长任务，关 / 开 | 弹幕每绘制一帧占用主线程的时间：平均、最长（各窗口的中位数） |
|---|---|---|---|---|---|---|
| 一般：每秒 3 条评论 | 25 条 | 30.5% → 33.5% | +3.0 个百分点（+2.1、+1.3） | 1,466 帧中 0 帧 / 1,466 帧中 0 帧 | 0 / 0 | 0.22 ms、0.64 ms |
| 密集：每秒 12 条评论 | 92 条 | 32.8% → 44.0% | +12.0 个百分点（+7.3、+4.8） | 1,435 帧中 15 帧 / 1,443 帧中 12 帧 | 3 / 3 | 0.55 ms、1.37 ms |

超过 5 ms 的绘制，一般密度下约 1,450 次中有 1 次，密集时有 4 次；关弹幕时的长任务和开弹幕时一样多：有弹幕时，主线程呈现视频和没有弹幕时一样流畅。弹幕花费的 CPU 主要在 GPU 进程和合成器上，并随同屏评论数增加。

这些是用 0.6.0 的排布、在整个画面上测的。2026-10-14 调整后的排布默认同屏评论更少，它自己的工作量也很小：在 Node 里用 BV1soWF6qEjF 的真实评论（64 分钟共 8,593 条）跑过最密集的两分钟，默认的顶部四分之一下一次更新最长 0.4 ms，整个画面、`high` 密度下最长 0.2 ms，把同一时刻重新排布一遍最长 0.6 ms。上面的 CPU 表没有重新测。

## 曾考虑的替代方案

**先用分段 protobuf 接口。** 它是 Bilibili 网页播放器读取的接口，按 6 分钟分段，但匿名时对同样的视频给出的评论比 XML 少 2 到 3 倍，而且每个分段一次请求，而不是每个条目一次。

**用 CSS 动画移动 DOM 元素。** 合成器可以不经主线程移动它们，但每条评论都是一个要在主线程上创建、设置样式、排版的元素；暂停、跳转和改变速度时，还要按引擎的时钟调整每个正在运行的动画，而 canvas 引擎的时钟本来就在主线程上。

**在主线程上绘制文字。** 第一个版本在那里绘制每条评论的位图，每帧几条：按车上尺寸实测，一个位图最长要 15 到 25 ms，原因是 emoji 或第一次用到的字体分块，这就是一个长帧。在排布时测量每条评论的文字，跳转后最长要 23 ms。

**按显示器的刷新率绘制。** 对 30 帧的视频，页面每个视频帧要更新两次；跟着 canvas 引擎绘制时再画，页面的更新次数保持原样。

**用设备凭据通过 `/v1` 提供评论。** 它在每条路径上都能经过 Worker 工作，但这样评论总要经过 Cloudflare；而媒体会话本来就按屏幕自己的路径从节点到达屏幕。

**车上默认关闭。** 车上的媒体电脑是 Ryzen，实测主线程开销每帧不到一毫秒；除了开销之外，没有别的理由支持默认关闭。

**在插件里缓存。** 每个片源都得给自己的缓存设上限；节点的缓存统一设限，片源只需回答区间。

**用开源弹幕引擎代替这套排布。** 2026-10-14 对照 Bilibili 的行为比较：CommentCoreLibrary（MIT）从不丢评论，而是把哪儿都放不下的评论放进另一个池子、叠在别的评论上，它的追及判断是近似的；weizhenye/danmaku（MIT）的「完全进入」和「追不上」判断和这里的一样精确，但放不下的评论会绕回来叠在别的评论上，默认速度是固定的每秒 144 像素，所以横穿时间随宽度增长；ArtPlayer 的 danmuku 插件（MIT）把放不下的评论无限期排队，它可能在自己的时间之后很久才出现，并且它的 worker 依赖 DOM 测量；DPlayer（MIT）丢掉放不下的评论，但用 DOM 元素和 CSS 动画排布。没有一个能在 worker 里按引擎的时钟绘制、同时保证评论从不重叠，所以排布仍是 Yolo 自己的，采用 Bilibili 的字号、速度和密度，以及 DPlayer 和 CommentCoreLibrary 的跳转行为。没有复制它们的代码。

**像 Bilibili 一样让一阵评论在同一帧进场。** 开头常有的同一时刻的十几条评论，会每条弹道一条地叠成一列；一条一条进场时，它们仍然都能在 Bilibili 允许的那一秒里放下。

**像 Bilibili 播放器那样恢复跳转之前的评论。** 它会读取新时刻之前一个横穿时间内的评论，让它们从半路显示；而这里的排布还要测量和绘制，于是一整屏评论会一下子冒出来。所以屏幕从空白开始，评论从边缘进场。

**合并重复弹幕。** Bilibili 网页播放器没有这个设置，它的 App 的「屏蔽重复弹幕」默认关闭，它的 Android 引擎 DanmakuFlameMaster 默认也不合并，所以 Yolo 不合并；agent 读到的重复文字会合并并带上次数。

**默认整个画面，或 Bilibili 网页的半屏。** Yolo 0.6.0 用整个画面：约十七行、比同一画面上 Bilibili 的字更大的文字盖满了画面。半屏是 Bilibili 网页的默认值，但在热门视频的开头会占满十行，而用户本人的 Bilibili 显示了五行。

## 后果

Bilibili 视频在车上和网页上都连同弹幕一起播放，agent 能说出某一刻观众在说什么，其他片源实现一个方法就能提供评论。这一层主要花在 GPU 进程和合成器上，因为它增加了一个画面大小、随每个视频帧变化的图层；它在主线程上的工作每帧不到一毫秒。评论在它的位图画好后的下一帧出现，一个窗口的评论在宽度测好之后出现。XML 把评论限制在 Bilibili 的 `maxlimit`，也就是最新的那些；脚本类评论不绘制；用浏览器配置文件的 cookie 时，评论是匿名获取的。加载或跳转后屏幕从空白开始，所以就在那一刻之前发送的评论看不到；在 `normal` 密度下，Bilibili 评分最低的五分之一评论被隐藏，评论为一条一条进场最多等一秒。设置留在每块屏幕上，所以新屏幕从默认值开始，agent 也读不回这些设置。

## 测试

[`danmaku-layout.test.js`](../../../../clients/player/test/unit/danmaku-layout.test.js) 固定了 Bilibili 的字号和速度曲线、弹道、经过暂停、跳转和速度变化的时间、加载或跳转不显示那一刻之前的评论、密度和被隐藏的低分评论，以及同屏上限；它用一份密集的测试数据检查：经过暂停、跳转和尺寸变化，任何两条已安排的评论在各自同时显示的整段时间里都不重叠，即使十几条评论在同一时刻也没有两条在同一帧内进场，以及按默认设置，评论在车上和电脑上都留在画面顶部四分之一以内；[`danmaku-settings.test.js`](../../../../clients/player/test/unit/danmaku-settings.test.js) 检查只保存选过的设置、0.6.0 的记录保留它们的选择；[`danmaku.test.js`](../../../../plugins/source-ytdlp/test/danmaku.test.js) 解析 XML 测试数据和一个 protobuf 分段及其评分，并覆盖 cookie 和退路；[`comments.test.js`](../../../../service/node/test/comments.test.js) 覆盖节点的窗口、失败和上限；[`mcp.test.js`](../../../../service/control/test/unit/mcp.test.js) 覆盖两个工具。[`test/e2e/danmaku.test.js`](../../../../test/e2e/danmaku.test.js) 通过假的 yt-dlp 和一份 XML 测试数据，在车上的 canvas 引擎里播放一个 Bilibili 页面：评论经过暂停和跳转都在各自的时间出现、跳转之前的评论不出现、位于画面之内，agent 读取它们并关闭弹幕，页面只访问 Yolo 自己的主机。
