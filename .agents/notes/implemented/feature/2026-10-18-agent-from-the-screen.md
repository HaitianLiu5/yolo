# Agent Note: Screens ask the owner's own agent

Status: implemented

English | [中文](2026-10-18-agent-from-the-screen.zh.md)

## Problem

Agents control Yolo through its [remote MCP server](2026-10-07-remote-mcp-server.md), so finding something to watch starts in ChatGPT or Claude. Someone already in the player, in the car or a browser, has no way to say "play the next episode of Friends" or "find a video about the new Model Y": they leave Yolo for another app. Yolo needs a way to ask an agent from the screen itself, and the owner wants that agent to be the one they already run and pay for, so Yolo needs no model API key, holds no model credential, and costs nothing beyond the owner's own plan.

## Decision

A screen's words go to an **agent plugin on the media node**, which hands them to an agent the owner already runs on that machine. The official ones, [`plugins/agent-claude-code`](../../../../plugins/agent-claude-code/) and [`plugins/agent-codex`](../../../../plugins/agent-codex/), run the owner's signed-in Claude Code or Codex, and each screen chooses which it asks. The agent works through its own MCP connection to Yolo, as it would from a terminal, and the play reaches the screen through the Hub like any other.

```
screen ──POST /v1/agent──▶ control plane ──nodeFetch──▶ node /internal/v1/agent ──▶ agent plugin ──▶ claude -p
   ▲                                                                                                    │
   └──────────── Hub play command ◀── Yolo's MCP tools (/mcp) ◀───────────────────────────────────────────┘
```

### The request

- **`POST /v1/agent`** `{ text, language?, agent? }` needs the `control` scope; `agent` is the screen's choice of agent. A paired screen's own credential makes that screen the agent's default target: the control plane looks up its name and passes `device: { id, name }` with the text. It also passes `playing`, what plays now as the Hub has it: `{ itemId, title, position, duration, status, device }`, where `device` is the screen it plays on, which may not be the one asking, and `duration` is null for a live stream; null when nothing plays. The screen sends nothing for it, so every client gets it alike. `text` is at most 1,000 characters. The answer is NDJSON (`application/x-ndjson`), streamed as the agent works: `{ type: "tool", name }` for each tool it calls (Yolo's own by their MCP names, such as `search` and `play`), `{ type: "text", text }` for words it writes on the way, then `{ type: "done", text }` with its one sentence or `{ type: "error", error }`. A refusal before the agent starts (no text, no agent on the node, the node offline) is an ordinary `/v1` error status.
- **`GET /v1/agent`** answers `{ available, id?, title?, reason?, agents? }`, read from the node: the agent a screen that names none asks, and in `agents` every one it may choose, `{ id, title, available, reason? }`; a node from before agents answers 404, which becomes `available: false` with "Upgrade the media node".
- **On the node**, [`service/node/src/agents.js`](../../../../service/node/src/agents.js) keeps the agents plugins register, asks the one a request names (`agent`), or else the first registered whose `health()` says it can answer, and runs one request at a time: a new request aborts the one still running, since the person changed their mind, and starts once that one has stopped, so two never play or queue at once; a closed connection aborts it too. `/internal/v1/agent` (GET for the status, POST for the stream) sends its headers at once; `nodeFetch()`'s 15-second timeout covers only them, and cloudflared flushes NDJSON as it is written. The endpoint is new and only the new control plane calls it, so `NODE_PROTOCOL` stays.

### Conversations

The control plane keeps the owner's conversations with the agent in D1 (`agent_conversations` and `agent_messages`, migration `0009`, [D1 data model](../architecture/2026-10-07-d1-data-model.md)), so one started on a phone continues in the car and survives a reload. `POST /v1/agent/conversations/{id}/messages` takes the same `{ text, language?, agent? }`, and without `agent` the agent that answered the conversation answers again. A conversation has one agent, since agents share no session: the player starts a new conversation when the screen has chosen another agent, and the control plane gives an agent that differs from the conversation's a session of its own; `new` as the id starts a conversation titled by the question. Its stream is the node's, unchanged, after a first line `{ type: "conversation", id, title }`. The control plane reserves the answer's row with the question, so a late answer stays next to its question, reads the stream on the way, and fills the row in when it ends: the answer's sentence, the tools it called, and whether it ended `done`, with an `error`, or `stopped` because the screen went away (a `waitUntil` write). A node that cannot be reached, or stops mid-answer, is recorded as an error and streamed as one, so the conversation shows what happened. A row the Worker could not fill in keeps no status, and the panel shows it as no answer yet. `GET /v1/agent/conversations` lists them, `GET …/{id}` returns one with its messages, and `DELETE …/{id}` removes one.

D1 holds only what a screen shows: never the agent's tool results, reasoning, or prompts. An answer keeps at most 4,000 characters and 20 steps; starting a conversation keeps the owner's newest 500 and drops those idle for 90 days, and a conversation in use keeps its newest 200 messages. The agent's own session id is kept beside the conversation and sent down with the next question as `session` (null for the first), and the node's `done` line carries the session and the agent's id back; an answer moves its session on only if no newer answer has finished, so an answer recorded late cannot take it back, and a newer one that failed holds nothing back. A conversation's follow-up therefore continues the agent's session however long ago it was asked, and New starts a fresh one. `POST /v1/agent` without a conversation still works as before, for clients that keep none. A node from before conversations ignores `session` and sends no session back, so its plugin falls back to its per-screen memory; it still answers, so `NODE_PROTOCOL` stays, since raising it would make that node refuse every request, playback included. [Conversations with any of the owner's agents](../../proposed/feature/2026-10-18-multi-agent-conversations.md) plans the rest: several agents, and a token in place of each CLI's own Yolo connection.

### The agent plugin

An agent plugin calls `yolo.registerAgent(id, { title?, health?, ask })` in its node factory ([`@useyolo/plugin-api`](../../../../service/plugin-api/src/index.js)); a screen asks the one it chose in Settings, or else the first registered that can answer. `ask(request, { signal, emit })` gets `{ text, device, playing, language }`, plus `session` when the request belongs to a conversation, reports `tool` and `text` events through `emit`, stops when `signal` aborts, and resolves `{ text, session? }`, where `session` is what a follow-up continues. A failed start removes the plugin's agents with its sources.

`agent-claude-code` runs `claude -p --output-format stream-json --verbose` once per request, in the plugin's cache directory, with the request on stdin so nothing a person says is read as a flag:

- **Its own login and Yolo connection.** No key or token passes from Yolo. The CLI uses the owner's Claude Code login and its MCP server named `yolo` (the `server` option), which [`yolo-connect-agent`](../../../../skills/yolo-connect-agent/SKILL.md) adds with user scope. The plugin reads that entry from Claude Code's user config (`~/.claude.json`, or under `CLAUDE_CONFIG_DIR`) and passes it back with `--mcp-config`; the same name, type, URL, and headers find the OAuth token Claude Code already keeps for it. With no such entry the agent reports itself unavailable, so screens show no Ask button; when the CLI's first message shows a server it cannot reach, the request fails with a message that says to connect it.
- **Yolo's server alone, narrow tools, no prompts.** `--strict-mcp-config` leaves out the owner's other MCP servers and plugins, and `--setting-sources ""` their settings files, whose allow rules would otherwise add to the ones here; a request, or a page it reads, cannot reach another integration. `--tools WebSearch,WebFetch` leaves only web search and page reading of the built-in tools: nothing runs commands or edits files. `--allowedTools mcp__yolo,WebSearch,WebFetch` with `--permission-mode dontAsk` refuses anything else without asking, and `--disallowedTools` removes Yolo's deleting tools (`remove_device`, `queue_remove`, `queue_clear`, `playlist_delete`). It never bypasses permissions.
- **What it is told.** `--append-system-prompt` says it acts for a Yolo screen that may be a car's while someone drives, plays on the screen that asked unless told otherwise, searches the library before the web, reads "this", "here", and "now" as what plays and where (with `get_transcript` and `get_frame`, not by asking), plays when one match clearly fits, and when several are plausible plays nothing and names up to three, asking which; the person's next request answers. It ends with one short sentence in the person's language.
- **Sessions.** A request in a conversation continues its `session` with `--resume`, or starts one when it is null, and resolves the CLI's session id; a resumed request begins with a line naming the screen it was asked at, since a conversation can move from a phone to the car, and every request with something playing begins with a line saying what plays, where in it (`1:02:05 of 1:30:00`), its status, and whether it plays here or on another screen named. A request without one, from a control plane before conversations, continues the same screen's last session within `memoryMinutes` (10), so "the next one" works; each screen has its own, since a session keeps the system prompt it began with, which names its screen. A session the CLI says it no longer has ("No conversation found") starts anew, and the answer carries the new id; any other failure keeps the session and fails, since a new one would replace the conversation's for good, and a request that failed after a tool ran is not asked again, since it may have played or queued already.
- **Its environment.** The child gets the node's environment without names that look like secrets (`SECRET`, `TOKEN`, `PASSWORD`, `API_KEY`, `CREDENTIAL`, `COOKIE`), so `NODE_SECRET` and source credentials stay with the node; `CLAUDE_CODE_OAUTH_TOKEN`, a login of Claude Code's own, stays. `CLAUDE_CODE_DISABLE_CLAUDE_MDS` and `CLAUDE_CODE_DISABLE_AUTO_MEMORY` keep out CLAUDE.md files and auto-memory, since the cache directory sits inside Yolo's checkout, whose coding instructions are not for a screen.
- **Finding the CLI.** `command` (`CLAUDE_CODE_COMMAND`, default `claude`) is looked up on `PATH`, then where its installers put it (`~/.local/bin`, `~/.claude/local`, Homebrew, `/usr/local/bin`), since a launchd or systemd service reads no login profile. Without it the agent reports itself unavailable and screens show no button. `model` (`CLAUDE_CODE_MODEL`) picks a model; `timeoutSeconds` (180) ends a request that runs too long, with SIGTERM and, 5 seconds later, SIGKILL, sent to the CLI's own process group so a wrapper script's children stop too.

`agent-codex` ([`plugins/agent-codex`](../../../../plugins/agent-codex/)) does the same with the owner's Codex CLI: `codex exec --json` once per request, `codex exec resume <session> --json` for a follow-up, with the request on stdin (`-`):

- **Its own login and Yolo connection.** It reads Yolo's server from Codex's user config, `[mcp_servers.yolo]` in `$CODEX_HOME/config.toml` (`~/.codex` by default) as `codex mcp add yolo --url …` writes it, and passes only its URL back with `-c mcp_servers.yolo.url=…`, under `--ignore-user-config` and `--ignore-rules`: none of the owner's other servers, profiles, or rules load, while Codex still signs in from `CODEX_HOME` and finds the token `codex mcp login yolo` stored. Every resume repeats these options, since they hold for one invocation. Without the entry, or with it turned off, the agent reports itself unavailable; an error about the server while it runs fails the request with what to do.
- **Narrow tools, no prompts.** It runs read-only (`sandbox_mode`), never asks (`approval_policy = "never"`), searches the web live (`web_search = "live"`), removes Yolo's deleting tools with `mcp_servers.yolo.disabled_tools`, and turns off the features that run commands, edit files, drive a browser or the computer, or reach the owner's other apps and plugins (`shell_tool`, `unified_exec`, `code_mode_host`, `apps`, `plugins`, `browser_use`, `computer_use`, and others); asked on the home machine to run a command, it says it cannot. Its instructions are Claude Code's, as `developer_instructions`.
- **Events.** `thread.started` gives the session, each `mcp_tool_call` and `web_search` item a step (shown once, though Codex reports a call starting and completing), each `agent_message` text, and the last of them is the answer; `turn.completed` ends it and `turn.failed` fails it. A session Codex no longer has starts anew, as with Claude Code.
- **The rest mirrors Claude Code's plugin**: the same environment without secrets, where `CODEX_API_KEY` is the one kept; `command` (`CODEX_COMMAND`, default `codex` on `PATH`, Homebrew, or `/usr/local/bin`), `server` (`CODEX_YOLO_SERVER`), `model` (`CODEX_MODEL`), `timeoutSeconds`, and `memoryMinutes`.

Both plugins are in [`plugins/official.json`](../../../../plugins/official.json), Claude Code first; on a machine without its CLI each loads and answers `available: false`.

### Voice input

Where the media node has a transcriber, the plugin type [AI subtitles](2026-10-18-ai-subtitles.md) use, a screen can say its request instead of typing it, and `GET /v1/agent` adds `speech: true` (the node's `GET /internal/v1/agent` says so when a transcriber is registered). The screen records with the browser's microphone through Web Audio, not MediaRecorder, and sends what the transcriber takes: 16 kHz mono 16-bit WAV, at most 30 seconds ([`clients/player/src/voice.js`](../../../../clients/player/src/voice.js)).

- **`POST /v1/agent/transcriptions`** (`control` scope) takes the recording as the body (`audio/wav`, at most 1,000,000 bytes) and the screen's language as `?language=` (the one chosen in Settings, else the browser's; [the player's language](2026-10-26-player-language.md)), and answers `{ text, language }`. The control plane passes it on as base64 in `POST /internal/v1/speech/transcribe` `{ audio, language, device }`, waiting at most 40 seconds.
- **On the node** ([`service/node/src/voice.js`](../../../../service/node/src/voice.js)) the WAV is checked, under 0.3 seconds is empty text, and the first transcriber is called directly, not behind AI subtitles' lane, for at most 30 seconds. A screen in Chinese is transcribed as Chinese, with the prompt "以下是普通话的句子。": a Whisper-style model then skips detecting the language, about a third faster, keeps its Mandarin in simplified characters, and still returns English said to it in English; other screens' languages are detected. Segments join without a space between Chinese characters and with one otherwise, up to 1,000 characters. Each screen has one request in flight and a newer one, whether the words so far or the whole recording, stops the older (`superseded`); at most two run on the node (`rate_limited`).
- **Nothing is kept.** The sound passes through the Worker and the node to the transcriber and is never written to disk, logged, or stored in D1, which keeps only the question the screen then asks with the words. A node from before voice input answers 404, and the screen is told to upgrade it; both endpoints are new, so neither `NODE_PROTOCOL` nor `CLIENT_PROTOCOL` changes.

On the screen, while `speech` is true and the browser can record (a secure page with `getUserMedia` and Web Audio), a microphone sits beside Ask in the home header, on the left within the driver's reach in the car, and another before the field in the panel. A tap on the header's opens the panel already listening, without the keyboard; the panel's starts as it is pressed: the browser asks for the microphone the first time, the button turns red with a ring that follows the voice, and a player kept behind the home screen plays at a tenth of its volume. A tap records until a second tap, 0.8 seconds of quiet after speech, 8 seconds without speech, or 30 seconds. Speech is told from the room's noise rather than a fixed level: the quietest moment of the first quarter second sets the noise, which then falls at once with quieter sound and rises slowly, and a block is speech at three times it (between 0.01 and 0.12 RMS), so a car's road noise does not hold the recording open; under 0.12 seconds of speech in all is no speech. Held for 0.35 seconds or more, as in messaging apps, the microphone records through pauses until it is let go, and a finger slid away from it before letting go cancels. While it records, what was said so far is sent again about once a second, one request at a time, and the words show greyed in the field as they come. When it ends the microphone is released, and the words are asked at once, with no countdown: the last of those requests is the answer when it heard 0.3 seconds or more past the last speech, and otherwise the whole recording is sent. A tap on a question puts it back in the field to edit, stopping its answer if it is the one running. A line under the field says what is happening or what went wrong (access refused, no microphone, nothing heard, the speech service's error, with the words seen so far left in the field). Each attempt records a `voice_input` device event with how it ended, its seconds, how long the words took, and how many words-so-far answers it showed, never the words or the sound ([device telemetry](2026-10-11-device-telemetry.md)).

**In the car.** Tesla's 2026.26 release notes let the browser use the cabin microphone on AMD cars once the owner taps to allow it; Intel cars are not listed, and the notes limit only the camera to Park. The `env` event's `microphone` field says, without a prompt, whether a car's browser offers a microphone, and **Settings → This screen → Microphone → Test** records three seconds and tries the browser's own speech recognition, reporting both as a `mic_test` event, so a car is checked rather than assumed. A car without a microphone shows no button, and the owner asks from a phone instead.

### On the screen

The home screen's header has an **Ask** button (the agent's title, such as "Ask Claude Code", is its label) while `GET /v1/agent` says an agent is available; the player checks on every welcome ([`clients/player/src/ask.js`](../../../../clients/player/src/ask.js)). It opens a panel near the top, clear of the on-screen keyboard: the conversation's title between a History button and a New button, its messages (questions on the right, answers on the left), and the field under them. An answer running shows the step the agent is on ("Searching the web…", "Starting it…"), then its sentence or its error. History lists the owner's recent conversations with their time; New starts one. The panel reopens on the screen's last conversation unless it is more than six hours old (`localStorage`). After a tool that changes what plays here, the panel closes on its own 1.5 seconds after the answer. Closing it leaves the answer running; while it runs the send button is Stop, and asking again stops it too. A phone's keyboard dictation also works in the field, and [voice input](#voice-input) adds a microphone of Yolo's own. **Settings › This screen › Ask with** lists the node's agents after Automatic, says why any cannot answer, and keeps this screen's choice in `localStorage` ([`clients/player/src/agent-choice.js`](../../../../clients/player/src/agent-choice.js)); Ask's label names the agent the screen asks, so the car can ask Codex while a phone asks Claude Code.

## Alternatives considered

**An agent loop inside the control plane, calling a model API.** Fastest to answer, since Yolo's tools run in the Worker, but every owner would need an API key paid by use, and Yolo would hold it. The owner's own agent costs nothing more and needs no credential in Yolo.

**The model API's remote MCP connector pointed at Yolo's `/mcp`.** The same key, plus a token Yolo would have to issue itself, for a detour back into the same Worker.

**A long-lived Claude Code process per conversation (`--input-format stream-json`).** Saves the CLI's start on each request, but needs process supervision and memory limits on the node; one run per request with `--resume` is simpler and keeps the conversation.

**`--dangerously-skip-permissions` with a strict MCP config, as some gateways do.** It would let the CLI run any tool it has; narrowing the tools and refusing the rest keeps the agent to searching and playing.

**The browser's own speech recognition (Web Speech API) for voice input.** It streams the words as they are said, where Yolo asks again each second, but Chrome sends the sound to Google and Safari to Apple, Firefox has none, and a Chromium build without Google's speech service, as the car's likely is, lacks it or fails; on a phone the keyboard's dictation already does the same. Recording and the owner's transcriber work wherever the microphone does and keep the sound at home. The microphone check reports what the car's recognition does, in case it turns out to work.

**MediaRecorder for the recording.** Its formats differ by browser, the car's are unknown, and the node would need ffmpeg to decode them; Web Audio gives the transcriber's own WAV in every browser, at 32 KB a second.

## Consequences

The owner asks for something to watch from the screen they are watching on, with the agent and plan they already have; Yolo stores no model credential and pays for no model. Each request starts the CLI, which takes a few seconds before the first step shows, and nothing answers while the node or its machine is off. What the agent can do is what its Yolo connection and the two web tools allow, minus deleting; a request someone says in the car reaches an agent that can search the web and play on any screen. The screen sees only Yolo's events and the agent's last sentence, never its reasoning. Voice input needs a transcriber the owner runs, and none is loaded by default; the words so far cost the transcriber a request about each second while someone speaks, and a misheard request goes out at once, to be stopped and edited by tapping it.
