# Agent Note: 分享链接

Status: implemented

[English](2026-10-20-share-links.md) | 中文

## 问题

在 Yolo 上播放的一切，都在用户本人用 passkey 配对过的屏幕上播放；每条流都经过用户本人的 Hub，而 Hub 只掌管一份播放状态：一次播放会切换用户本人的当前设备、停掉那里的流、写入观看记录，并从用户本人看到的位置续播。用户本人想给一位朋友看一个视频，朋友却没有配对过的屏幕；给朋友配对一块屏幕，又会把用户本人的片库、队列、观看记录、设备和 agent（智能体）都交给这位朋友。Yolo 是一个人自己的服务（[D1 数据模型](../architecture/2026-10-07-d1-data-model.zh.md)）；给其他人的账号仍不在范围之内（[Yolo 1.0](../../proposed/feature/2026-10-11-yolo-1-0.zh.md)）。

## 决策

分享链接是一个 URL，`https://<Yolo 的源>/s/<token>`，它在任何浏览器里播放一个条目，有效期 7 天，不需要配对，也不需要登录。朋友看到的是这个条目和播放器，看不到用户本人的 Yolo 里的其他任何东西；朋友做的任何事都不会影响用户本人的播放状态、观看记录、队列、音轨偏好，也不会影响片源自己的观看进度。

### 生成和撤销链接

配对过的屏幕用播放器的分享按钮生成链接（`POST /v1/shares`，`control` scope，[v1 HTTP API](../architecture/2026-10-07-v1-http-api.zh.md)），有 `control` scope 的 agent 用 MCP 工具 `share` 生成（[远程 MCP 服务](2026-10-07-remote-mcp-server.zh.md)）；两者都分享给定的条目，没给定时分享正在播放的条目。节点先认领并描述这个条目，所以生成链接需要节点在线。回答里只带一次 URL：D1 的 `share_links` 表只保存 token 的 SHA-256（迁移 `0010_share_links.sql`），和设备凭据一样，所以链接可以撤销，但再也无法显示。链接记下是谁生成的（`device:<id>` 或 `client:<id>`）；每生成一个新链接，就删掉用户本人已结束超过 30 天的链接，并只保留最新的 200 个。token 是 16 个随机字节，即 22 个 base64url 字符。播放器有浏览器的系统分享面板时把 URL 交给它，没有就复制到剪贴板，再不行就显示出来让人手动复制，因为分享面板和剪贴板都要求那次点按刚刚发生，而 Yolo 的回答可能来得更晚。

设置里的「Share links」列出还开着的链接，以及朋友播放过每个链接多少次，这些都在用户本人的 passkey 会话之后（`GET /v1/owner/shares`）。撤销一个链接（`POST /v1/owner/shares/:id/revoke`）会立即拒绝它的下一个请求，并让节点停掉这个链接正在播放的流（`DELETE /internal/v1/shares/:id`）；撤销时会写一行 `kind: "security"` 日志，生成链接时也一样。

### 朋友的页面

`/s/<token>` 就是播放器自己的页面：静态资源用 `index.html` 回答它，所以它保留 COOP 和 COEP，用哪个引擎都能播放，特斯拉和在那里打开的任何页面一样用 canvas 引擎（[两个引擎](../architecture/2026-10-12-two-playback-engines.zh.md)）。`main.js` 识别这个路由，启动 `share.js`，而不是配对和实时通道。页面请求两个不需要凭据就会回答的路由（[`service/control/src/share-links.js`](../../../../service/control/src/share-links.js)）：

- `GET /v1/share/<token>`：条目（标题、封面和时长，用一个替身 Source `{ plugin: "share", id }` 代替用户本人的 Source）、链接的到期时间，以及朋友可以尝试的媒体路径。
- `POST /v1/share/<token>/stream`：`{ startTime?, reason?, autoplay?, sessionId?, maxVideoKbps?, network?, capabilities, viewport? }` → `{ stream, item, startTime, autoplay, reason }`，字段和配对屏幕经实时通道收到的 `load` 消息相同。

`playback.js` 在这个页面上把每个流请求都发给这个链接（`setShareStreams()`），并把每个回答交给 `onLoad`，所以播放器播放、恢复、跳到流之外和切换清晰度都和在配对屏幕上一样；`sessionId` 指明一次重建要替换的那条流。文字字幕在页面上切换；需要新流的音轨无法切换。播放器的路由从不把页面切到 `/play` 或首页，所以重新加载打开的还是同一个链接；朋友看到哪里保存在浏览器的 `localStorage` 里，不在 Yolo 里。`:root[data-share]` 下的 CSS 隐藏返回、分享按钮、设置、上一个和下一个、正在播放栏，以及设备选择器。

控制面检查链接，为用户本人的用户 id 签一个媒体 token，它随链接到期，或者在通常的 12 小时后到期，以先到者为准；然后控制面自己调用节点的 `/internal/v1/prepare`，把 `share` 设为链接的 id。Hub 从不知道这条流，所以朋友的流不属于任何设备，不播放队列，也没有上报：节点只根据 Hub 的上报写入片源的观看进度。一次播放（不是重建）给链接的 `plays` 加一。封面以 Yolo 源上的图片链接给出（[封面图片](2026-10-07-remote-mcp-server.zh.md#cover-images)），流自带的缩略图走的是用户本人的路由，会被换成这个图片链接。

已过期的链接回答 410「This share link has expired」，已撤销的回答 410「This video is no longer shared」，未知的 token 回答 404；页面在播放器的位置显示这条消息。两个路由都按地址计入 `PUBLIC_LIMIT`，用的是它们自己的键，所以朋友的页面从不消耗用户本人的登录额度。

### 媒体路径

在 Yolo 看来，朋友从不在用户本人的家庭网络里：提供给朋友的路径先是远程直连播放（用户本人打开了它时），再是中转（在用户本人的中转模式允许时）（[媒体流离开 Worker](../architecture/2026-10-13-media-off-the-worker.zh.md)）。局域网监听端口从不提供给朋友，因为它的名称和地址都是家里的。中转关闭且没有远程路径时，这条流以 `media_unreachable` 被拒绝。

### 朋友在节点上的会话

朋友的流从不挤掉用户本人的流：节点（[`service/node/src/media/pipeline.js`](../../../../service/node/src/media/pipeline.js)）把带 `share` 的会话分开管理，8 个会话的上限（超出时淘汰最旧的会话）只计用户本人的会话。所有链接合起来，同时最多播放 2 个朋友的会话。只有在这两个里有一个已经 2 分钟没有媒体请求时，第三个才会在它的片源解析任何东西之前被接纳，那个空闲的会话随之被淘汰；否则它以 `rate_limited` 被拒绝，消息是「Two friends are already watching from share links; try again in a few minutes」。一次重建的 `replaces` 会先腾出它自己的位置，但只对同一个链接的会话有效。朋友的会话 15 分钟没有媒体请求就会被释放，用户本人的会话则是 2 小时（[节点内部 API](../architecture/2026-10-07-node-internal-api.zh.md)）。

## 曾考虑的替代方案

**一起看。** 朋友加入用户本人的播放，跟着它暂停和跳转。这等于让 Hub 的播放状态和第二种、未配对的屏幕共享，工作量是只分享一个条目的两到三倍，而且仍然要先有链接所做的一切。

**访客设备。** 把朋友的浏览器配对成一个 scope 更少的设备，可以复用实时通道；但每个设备都参与用户本人唯一的那份播放状态：一次播放会切换用户本人的当前设备并写入观看记录，而且设备凭据从不过期。

**链接到播放列表或整部剧。** 这需要一个供挑选的页面，还要决定朋友能浏览什么；给朋友发一个视频，一个条目就够了，以后可以再加别的链接类型。

**可选的有效期，或者不设有效期。** 不提供选择、固定 7 天，足够看完一个视频，被继续转发的链接也会自己失效。其余情况交给撤销。

**保存 token，以便再次显示链接。** 那样数据库的导出或备份里就会有每个还开着的链接。重新生成一个链接只需点一下。

**给链接加密码。** 密码得和链接一起送到同一位朋友手里；链接本身就是秘密。

**提供局域网路径。** 它暴露家里的地址，而且只服务家庭网络上的设备，拿着链接的朋友很少在那里。

## 后果

任何持有链接的人都能看那一个条目，直到链接过期或被撤销，用户本人的 agent 也一样；转发链接就是转发访问权，它受 7 天有效期、撤销和节点上 2 个朋友的流这三者约束。不走远程直连播放时，朋友的每条流都经过中转，受它 4.8 Mbps 上限的约束，并消耗用户本人的 Workers 请求；朋友打开的 AI 字幕在用户本人的语音服务上运行。在设置里重置图片链接，也会替换还开着的分享链接页面上的封面。朋友的流不出现在观看记录、播放健康和媒体路径的流计数里。上一个发布的节点会忽略 `share` 和 `replaces`，所以那时朋友的流会计入用户本人的 8 个会话；升级时先重启节点再部署 Worker，不需要改动 `NODE_PROTOCOL`。

## 测试

`service/control/test/unit/auth.test.js` 不带凭据播放一个链接，检查它发出的 prepare、用户本人的播放状态和观看记录保持为空、中转关闭时的情况、重建的 `replaces`，以及未知的链接得到 404、方法不对得到 405、已过期和已撤销的链接得到 410。`service/node/test/media-pipeline.test.js` 检查朋友的上限与用户本人的分开计算、在片源解析之前接纳、`replaces` 只在同一个链接内生效，以及停掉一个链接的会话。`test/e2e/web-playback.test.js` 用 MCP 工具生成一个链接，在一个从未配对过的浏览器里播放它，检查用户本人的播放和观看记录没有变化，通过设置所用的路由撤销它，并看到页面显示链接已撤销。
