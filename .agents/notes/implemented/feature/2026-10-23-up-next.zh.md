# Agent Note: 接下来播什么

Status: implemented

[English](2026-10-23-up-next.md) | 中文

## 问题

一个条目播完时，Hub 只会播队列的第一项，否则就停下。一部剧的各集、一个多 P 视频的各个分 P 从来不会一个接一个地播：主人在 B 站看一部剧八个分 P 中的第一个，这个分 P 播了四遍。屏幕上没有任何地方说接下来播什么；后面什么都没有时，播放器停在最后一帧，暂停着，"下一个"是灰的。agent 一次调用只能加一个条目进队列，所以"接下来十集"要调十次；一个 B 站视频的其他分 P，只能当作播放列表导入才拿得到。

## 决策

### 顺序

`next` 和播完的条目，先沿着历史往前走（[Hub](../architecture/2026-10-07-hub-and-realtime-channel.zh.md#previous-and-next)），再取队列的第一项，最后取刚才在播的条目所在那一串的下一项。队列是主人点名要的，所以排在前面；那一串是主人正在看的，所以等队列空了再接着播，就像音乐播放器播完插进来的歌，再回到原来的专辑。

### 一串

源用 `sequence(source)` 告诉 Yolo 一个条目属于哪一串（[源插件 API](../architecture/2026-10-11-source-plugin-api.zh.md#methods)）：按播放顺序排列的所有条目，以及这个条目在其中的位置。

- **Plex：** 一集所在的那一串，是它所属剧集跨季的所有集，取自一次 `allLeaves` 列表；电影不属于任何一串。
- **yt-dlp：** 一个 B 站视频所在的那一串，是它的各个分 P，取自去掉 `?p=` 的页面的平铺列表；带 `list=` 的 URL 属于那个播放列表。同一串里的每个视频在 10 分钟内共用这一份列表，其他 URL 不运行 yt-dlp（[`sequence.js`](../../../../plugins/source-ytdlp/src/sequence.js)）。

节点从这个条目开始传出这一串，之后最多 50 项（`GET /internal/v1/sequence`，[节点内部 API](../architecture/2026-10-07-node-internal-api.zh.md)）。屏幕用 `GET /v1/library/items/:id/sequence` 读它：`{ title, items }`，每项带 `sourceKey`、Source、标题、缩略图和时长，第一项就是所问的条目；不属于任何一串的条目，或较老的节点，没有条目。iPhone 播放器把它列在画面旁边。

Hub 把这一串存在自己的存储里（`run`：它的标题，和当前所在条目之后的各项）。直接播放的条目（一次点按、agent 的 `play`、上一个）会替换它：Hub 丢掉旧的那一串，在后台向节点要新条目的那一串，所以流从不等它。队列里的条目保留这一串。从这一串里播放一项，会让它往前移；剩下不到 10 项时再问节点一次，如果回答里没有条目，就保留原有的。列表里没有名字的条目（比如 B 站的分 P），在作为下一项显示之前先查一次信息。这次改动之前的节点没有这个路由，读作没有这一串。

### 状态里写什么

`PlaybackState` 写明 `next` 会播什么：`upNext: { from, title?, item }`，其中 `from` 是 `history`、`queue` 或 `sequence`，`title` 是那一串的名字。Hub 在一次播放、队列改动和节点回答之后刷新它。只要有 `upNext`，屏幕就显示"下一个"；只有面对不发 `upNext` 的 Hub，屏幕才像以前一样根据历史和队列来判断。

### 屏幕上

一个条目的最后 20 秒（只限至少 90 秒长的条目），一张卡片写明接下来播什么，带"立即播放"（就是播放器的"下一个"）和一个关闭按钮（[`up-next.js`](../../../../clients/player/src/up-next.js)）。"立即播放"随着条目快播完从左往右填满，不用读数字也能看出还剩多久。关闭之后，屏幕发的 `ended` 带 `advance: false`，Hub 就在这里停下这个条目，和后面什么都没有时一样。一个在屏幕上播完、后面什么都没有的条目，在中间按钮下方显示"Finished"，按中间按钮会重播，而不是停在暂停的最后一帧。

车机模式下，卡片和所有面板都放在左边，也就是驾驶员一侧，从方向盘伸手就够得着；网页模式下仍在右边。

### Agent

`queue_add` 和 `POST /v1/queue` 接受 `count`：这个条目和它所在那一串里在它之后的条目，合计最多 `count` 个，上限 30。列表里没有名字的条目会先查信息，回答里的 `items` 说明实际有几个。

## 曾考虑的替代方案

**先播那一串，再播队列。** 流媒体服务不管还有什么待播，都会播下一集，但它们没有队列。Yolo 的队列是主人或 agent 点名要的，所以排在前面，那一串在它之后接上。

**`ended` 之后在 Hub 上倒计时。** 这需要 Hub 有自己的计时器，并在休眠前后保持状态，倒计时期间屏幕还停在最后一帧。在结束前显示卡片，把选择放在主人正看着的地方，下一项也能立刻开始。

**把那一串复制进队列。** 每次播放都会往队列里放最多 50 项，主人换看别的东西时还得清空队列。

**让主人把卡片和面板拖到想要的位置。** 拖动会和点按、滚动抢手势，面板也没有更好的地方可放，而左舵车的驾驶员一侧不需要任何设置。右舵车需要一个切换左右的开关。

**给一串里的每一项都查名字。** 那样每个分 P 都要运行一次 yt-dlp；屏幕上只显示下一项，所以只给它查。

## 后果

一部剧或一个多 P 视频不用主人操作就能一路播完，队列播完时"下一个"也能用，agent 一次调用就能把一季加进队列。每个直接播放的条目多一次节点请求（Plex 是两次媒体库请求，yt-dlp 是同一串共用的一次平铺列表），没有名字的下一个分 P 再多一次 `describe()`。每个 B 站分 P 在历史里是独立的条目（`?p=2`），第一个分 P 带不带 `?p=1` 仍然是两个条目，和以前一样。从 YouTube 播放列表打开的视频最多接着播后面 50 个，因为这些视频自己的 URL 不带列表，没法再问。Apple TV 会沿着这一串接着播，因为是 Hub 在播，但它不显示卡片。

## 推迟

播放器里的"接下来"面板、每张卡片菜单里的"下一个播"和"最后播"、每一串只占一张卡的"继续观看"、历史页，以及 Apple TV 上的卡片，都已设计但还没做。
