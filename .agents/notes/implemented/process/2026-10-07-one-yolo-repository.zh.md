# Agent Note: 一个仓库，一次性重写

Status: implemented

[English](2026-10-07-one-yolo-repository.md) | 中文

## 问题

Yolo 由一个家用服务进程、它的 CLI 和一个只给特斯拉用的浏览器播放器，发展成服务、插件和客户端。播放引擎的历史很重要：很多特斯拉相关的细节只因为过去的某次故障才存在，原因只记录在旧提交里。整个过程中还不能让车上没有能用的播放器。

## 决策

- **一个仓库放下整个 Yolo。** npm workspaces 把服务放在 `service/`（`core`、`plugin-api`、`control`、`node`），官方插件放在 `plugins/`，播放器放在 `clients/`（`clients/tesla`）。播放器是 Yolo 的一部分，不是单独的产品或仓库。
- **保留完整历史。** Yolo 起源于 Drive-In，一个只给特斯拉用、自带家用服务的播放器；公开仓库 [`HaitianLiu5/yolo`](https://github.com/HaitianLiu5/yolo) 保留了那个项目完整的 Git 历史，所以 `git log --follow` 能追溯到引擎各种特斯拉专属行为的来由。
- **先拆成服务和客户端，一次性重写。** 协议在任何 MCP 工作落地之前就按多台设备、多个客户端设计，代码按模块一次性重写。之前的服务（`server/`）、它的 CLI（`cli/`）以及节点到它的桥接（`node:legacy` 渲染器），是在新架构通过 `npm run check`、四种流类型（`hls`、`direct`、`dash_split`、`plex`）都在车上检查过之后才删除的。

## 曾考虑的替代方案

**先给之前的服务加上 MCP，以后再拆服务。** 那样到拆分时还要再重写一遍。

**渐进替换（strangler 模式）。** 没有采用：Yolo 一次性重写完成，删除之前的服务之前在车上逐一检查各种流类型，取代了新旧长期并存。

**等到 1.0 改名时再拆仓库，或让新仓库从干净的初始提交开始。** 从零开始会丢掉 Git 历史里记录的、引擎各种特斯拉专属行为的来由。

**按运行时分目录，或让播放器留在自己的仓库里作为独立客户端。** 服务、插件和客户端一起演进，放在一个仓库里，一个提交就能同时改好协议的两端。

## 后果

协议改动、它的服务端、客户端和测试可以在一个提交、一次 `npm run check` 里完成。对任何引擎文件，`git log --follow` 都能追溯到之前那个项目的历史。仓库是公开的，所以配置示例和记录里绝不能出现密钥。一次性重写把风险集中在一次切换上，车上检查降低了这个风险。
