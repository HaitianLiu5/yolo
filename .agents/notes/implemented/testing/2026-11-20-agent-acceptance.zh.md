# Agent Note: 由 agent 亲自走一遍来验收改动

Status: implemented

[English](2026-11-20-agent-acceptance.md) | 中文

## 问题

Yolo 原有约 480 条单元和集成测试、145 条 Swift 单元测试、30 条脚本化的端到端流程、一套给原生客户端用的一致性套件、一条 tvOS UI 测试，以及四个 GitHub Actions 工作流。从 2026-10-21 到 2026-11-07（Actions 额度用完、工作流停掉，#138），447 次运行失败了 10 次，没有一次是用户会碰到的 bug：两次是语音测试的时序竞争，两次是供应商名规则抓到了注释里的一个词，一次是某个插件少了屏幕要显示的描述，五次是 e2e 运行环境本身（ffmpeg 安装超时、ffmpeg 崩溃、端口被占用）。Apple 工作流 51 次全部通过。同一时期有三个提交只是在修测试（#96、#143、#82），#98 因 Chrome 升级重写了一条 e2e 流程，测试代码占全部代码改动的 16%。本地完整跑一次 `npm run check` 约 14.5 分钟，其中 13.6 分钟是 e2e 流程。单元测试钉住的是代码的写法，每次重构都要跟着改；脚本化流程与屏幕的实际行为渐渐脱节；一致性套件找不到任何运行记录。而用户真正碰到的问题，车上的卡顿、Bilibili 的地区限制、屏幕配对成功却什么都不显示，都出在没有任何测试建模过的路径上。

## 决策

谁做改动，谁就把 Yolo 跑起来亲自用一遍来证明它，实际中就是做改动的 agent：走改动涉及的路径，覆盖它影响到的每一种屏幕，像用户一样使用 Chrome 里真实的播放器（车机模式和网页模式）以及模拟器里的 iOS 和 tvOS App。[`yolo-acceptance`](../../../skills/yolo-acceptance/SKILL.md) skill 就是这份清单：怎么启动、有哪些路径、每条怎么走、怎样算通过、本地服务覆盖不到什么，以及汇报里要附什么（截图、命令输出、MCP 返回，以及哪些没有走）。不会新增单元测试、脚本化端到端测试或 CI 门禁来代替这一步，合入和发布也从不等某个检查，只等用户确认。

**仍然自动运行的**只有不需要编写和维护用例的部分：`npm run check` 运行文档门禁，构建播放器和 Worker，并运行规则检查（[`scripts/run-gates.js`](../../../../scripts/run-gates.js) 的 `rules`），约 15 秒：`service/` 下任何文件都不出现供应商名（[插件架构](../architecture/2026-10-11-plugin-architecture.zh.md)）；播放器、用户本人的页面和 Apple App 显示的每段文字都有中文（[播放器语言](../feature/2026-10-26-player-language.zh.md)）；Worker 提供的内容不引用其他主机，用户本人的页面保持 Yolo Web 的深色 token（[两个引擎](../architecture/2026-10-12-two-playback-engines.zh.md)）；各处只有一个版本号且 CHANGELOG 有对应条目（[版本与发布](../process/2026-10-13-versions-and-releases.zh.md)）；目录里的每个插件都为屏幕描述了自己；每个 skill 都为 Claude Code 链接好。这些检查从 `service/control/src` 导入的模块不导入 `cloudflare:workers`，所以能在普通 Node 里加载。改到 `clients/apple/` 的改动还要以 Release 配置构建两个 App。GitHub Actions 不运行任何检查，唯一的工作流只响应 `@claude` 提及。

**本地服务。** `npm run stack`（[`scripts/stack/`](../../../../scripts/stack/)）在本机启动整个 Yolo：媒体节点和 `wrangler dev --local` 下的控制面，端口随机空闲，使用本地 D1 和 KV、没有路由和 Workers VPC 绑定的生成配置、一个用户及其会话、一个通过真实 OAuth 流程拿到的 agent 令牌，以及 Yolo 之外一切的替身：ffmpeg 生成的每种流类型的媒体、在本地应答的 yt-dlp 和 Plex、一个文件夹媒体库和一个赛事库。它保留了原来测试的隔离：节点在临时目录下有自己的 `YOLO_RUNTIME_DIR` 和 socket，`YOLO_ENV_FILE=""`，不开 Bonjour；不访问 Cloudflare、YouTube、Plex 或 Let's Encrypt；不碰线上节点的运行目录或 9191 端口。它的命令可以以用户身份批准屏幕的配对码、发起 agent 的 MCP 和 `/v1` 调用，以及打印创建通行密钥用的用户码。`npm run stack:walk` 在一块屏幕上走一遍主路径（配对、agent 播放、暂停、跳转、继续），每一步留下截图以及屏幕和 Yolo 各自报告的状态，本身不做断言，由 agent 判断看到的结果。Apple App 的调试构建以 `-YoloServer <地址>` 启动时会直接与该地址配对，跳过会先找到用户本人实例的 Bonjour。

原先测试分层里有两条规则独立保留：页面的模式和引擎取决于设备类型和特斯拉指纹，所以改动要在车机模式和网页模式下都走一遍；在最老的受支持 Node（22）下行为可能不同的改动要在它下面运行（`npx -y node@22 …`），因为事件循环排空时 Node 22 会取消仍未完成的 promise。

### 车上检查

路由和播放相关的改动还要在车上用受影响的流类型检查一遍：`hls`、`direct`、`dash_split` 或 `plex`，确认播放器能加载和配对、跳转正常、音画保持同步。播放或网络相关的改动之后，再做一次故障检查，覆盖本地服务无法复现的部分：真实的特斯拉渲染器、移动网络、Cloudflare 路径和家里的节点一起工作。先播放一个固定 720p60 的 YouTube 或 Bilibili 视频，然后逐个制造故障，每次等播放稳定后再做下一个：

| 故障 | 预期 |
|---|---|
| 让车断网 30 秒 | 已缓冲的视频尽量继续播放；恢复后在原位置附近接着播，不刷新页面 |
| 断网 60 秒 | 卡顿持续 8 秒后，设备的事件上报 `bandwidth_insufficient`（可用与所需的 kbps）或 `network_unstable`；重试间隔上限保持在 60 秒 |
| 断网 180 秒 | 页面保持响应，内存保持有界；网络恢复后重新解析片源 |
| 从 Wi-Fi 切换到 LTE 或另一个热点 | 丢弃旧的 CDN 和会话 URL，新的流从保存的位置续播 |
| 播放时重启媒体节点 | 过期的会话返回 `410`，播放器建立新的流，而不是对过期 URL 一直重试 |
| 用 `?decodeErrorAt=<秒>` 打开播放器，时间略超前于要播到的位置，再加上 `&decodeErrorCount=4` 打开一次 | 一次：`decoder_recovery` 停在第 1 步，`outcome: "recovered"`，没有新的流，声音一直在播。四次：第 1 到 3 步 `failed`，第 4 步 `requested`，然后在当前位置有一条新的流 |

通过标准：没有任何状态无限循环（缓冲、断开、重连）；恢复按 1、3、10、30、之后 60 秒的退避进行，没有重试风暴；恢复后 HLS 预取的待处理工作清空，同时只有一个下载；只有至少两个吞吐样本支持时，才会上报 `bandwidth_insufficient`；清晰度变化遵循[自适应策略](../feature/2026-10-11-adaptive-quality.zh.md)；设备的事件里能看到 `stall_start`、恢复、一次新的流请求和 `playback_recovery_stable`（[设备埋点](../feature/2026-10-11-device-telemetry.zh.md)）。

## 考虑过的替代方案

**保留精简后的测试集，在本地跑。** 测试集在 2026-10-18 已经精简了 80%，每个契约只留一条测试。剩下的部分因自身运行环境失败的次数仍多于因产品 bug 失败，每次要跑 14 分钟，最后一个月里三分之一的修复是在修测试。测试集再小，也还是要跟着每天都在变的代码同步维护。

**保留脚本化流程，只删单元测试。** 这些流程证明了各部分的衔接，但每条都是一串选择器和时序，一次布局调整或 Chrome 升级就会打断；它们全绿也没能挡住用户遇到的卡顿和地区问题。其中有价值的部分，也就是带假供应商的完整本地 Yolo，以 `npm run stack` 的形式保留；断言去掉，改由 agent 亲眼看结果。

**只为静态检查恢复 CI。** 这些检查在本地只要 15 秒，已经包含在 `npm run check` 里；一个跑不了的必需检查（比如额度用完时）只会挡住合入。

**保留 D1 迁移测试和一致性套件。** 两者在有记录的运行里都没有拦住过任何问题，一致性套件甚至没有运行记录。迁移的验收方式是启动本地服务，它会把所有迁移应用到一个新的 D1 上；迁移遇到真实数据是在用户升级时，升级会先备份 D1 并且可以回滚。

## 后果

`npm run check` 从约 14.5 分钟缩短到约 15 秒，没有任何改动需要等机器才能合入。代码改动不再附带测试重写，agent 的汇报里展示的是屏幕本身。

代价是：改动看起来没碰到的路径上出现的回归，不再会被恰好覆盖它的测试抓到；只有 agent 走了那条路径才能发现，所以 skill 要求 Hub、`/v1`、实时通道、MCP 或某个片源有改动时走遍每种屏幕，拿不准时在全部五种屏幕上走主路径。单元测试钉住的细节规则（退避时间、清晰度阈值、协议边界情况）现在只能靠亲自验收、车上检查和代码评审来证明。验收依赖 agent 如实看待所见、如实说明哪些没有走。真实的特斯拉、真实的供应商、真实的证书、Cloudflare 路径、Safari 和真实的 Apple 硬件仍在本地服务之外，和原来在测试集之外一样。
