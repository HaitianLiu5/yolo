# Agent Note: Three test layers and in-car checks

Status: implemented

English | [中文](2026-07-21-test-layers.zh.md)

## Problem

Yolo's behavior spans pure policy (the Hub, pairing, quality decisions), real boundaries (HTTP bodies, the D1 schema, WebCodecs), and a full journey through a Worker, a media node, ffmpeg, and a browser. A test suite that proves everything end to end is slow and flaky; one that proves only units misses the joins. Tests also run on the owner's home machine, next to the live media node, and must never touch its state, its port, Cloudflare, YouTube, or Plex. Some conditions — the real Tesla renderer, a mobile connection, the Cloudflare path — cannot be reproduced locally at all.

## Decision

Yolo has three test layers, each with its own job:

- **Unit** (`*/test/unit`, the `test/*.test.js` of the service and plugin workspaces, and `ops/test` and `scripts/provider-names.test.js`): contracts whose break would be silent — authentication, pairing, media tokens and signing, migrations, the source plugins' `prepare()`, the node's listeners, and the AGENTS.md rules such as single-flight HLS prefetch. They need no ffmpeg, browser, or network.
- **Integration** (`clients/player/test/integration`, `service/control/test/integration`): one real boundary each, such as HTTP bodies, WebCodecs orchestration, or the `/v1` API over the real service layer and D1 schema, with external dependencies injected.
- **End to end** (`test/e2e`): the real stack — the media node, and the control plane under `wrangler dev --local` with a generated config, local D1 and KV, and no fixed ports, nothing sent to Cloudflare — with the player served as the Worker's static assets. Starting the stack costs seconds, so each file that needs it starts one and runs its journeys on it in order. `car-playback.test.js` pairs Chromium as the car through the device code flow and plays the four stream types (`direct`, `hls`, `dash_split`, `plex`) through `/m/*` with the canvas engine, started by an agent over MCP; it also checks the car's default layout, controls, a quality change, recovery, the queue, revocation, Plex's subtitles and transcript, a Tesla paired as a browser that still plays with the canvas engine and wakes onto the loading screen of the item it kept, before its welcome, then plays on muted until a tap, and a decoder that fails mid-item and recovers in place without a stream request, and one that keeps failing and climbs to a new stream ([canvas engine](../architecture/2026-04-04-canvas-playback-engine.md)). `web-playback.test.js` plays the same four stream types through the browser's `<video>` element ([two engines](../architecture/2026-10-12-two-playback-engines.md)), leaves an item with Back, reloads onto the home screen and the bar it kept, before the welcome and Yolo's history, and plays the item on from the bar, pairs with the owner's passkey, and puts owner settings behind it. `media-paths.test.js` plays from the node's LAN listener and then its remote listener on loopback, under names Chromium maps there and certificates openssl signs for the node's own requests, and falls back from one to the next and then to the relay at the same position ([media off the Worker](../architecture/2026-10-13-media-off-the-worker.md)). `ai-subtitles.test.js` plays an item whose AI subtitle the official speech plugin makes through a stand-in for the owner's speech server, and holds the node's AI subtitle checks that read sound with ffmpeg ([AI subtitles](../feature/2026-10-18-ai-subtitles.md)). `ask-voice.test.js` asks by voice: a microphone made with Web Audio stands in for the browser's, since Chrome's own fake one waits on macOS's microphone permission, and the recording goes through the official speech plugin to a stand-in speech server and on to an agent plugin that repeats what it was asked ([voice input](../feature/2026-10-18-agent-from-the-screen.md#voice-input)); the car's microphone is checked in the car. Media is made with ffmpeg; yt-dlp and Plex are local fixtures (`test/e2e/fixtures.js`).

An assertion belongs at the lowest layer that can prove the behavior. The end-to-end layer keeps only the journeys no lower layer can prove: each stream type with each engine, the car's layout, the canvas engine for a Tesla whatever its type, LAN direct play and its fallback, pairing, the passkey, MCP, and resume after Back. A rule that a unit test covers gets no end-to-end copy.

**Size.** The suite is small on purpose: on 2026-10-18 it was cut by more than 80%, to one owner test per contract at its strongest boundary, chosen with [`yolo-test-audit`](../../../skills/yolo-test-audit/SKILL.md); [`yolo-testing`](../../../skills/yolo-testing/SKILL.md) picks the proof for a change. A new test extends a keeper before it adds a file, and a stronger test replaces a weaker one. Narrow regressions that a keeper or the in-car check already covers — realtime races, layout geometry, the node's ffmpeg fallbacks — have no tests of their own. A journey waits for the event it needs, not for a fixed time, and a seek that must reach the network goes past what the browser has already buffered.

**Isolation.** Tests never use the repository's runtime state: the node gets `YOLO_RUNTIME_DIR` and its own socket under a temporary directory, and `YOLO_ENV_FILE=""` so it loads no `.env`. Network tests use local origins or injected transports. No test shares a port, calls YouTube, Plex, Let's Encrypt, or the Cloudflare API, or depends on a running Yolo node, and nothing runs against the live node's runtime directory or its port 9191. Modules under `service/control/src` that tests import do not import `cloudflare:workers` (only `index.js` and `hub/hub.js` may), so they stay testable in plain Node.

**Commands.** `npm run test:unit`, `npm run test:integration`, and `npm run test:e2e` (which builds `clients/player` first if `dist/` is missing) run the layers independently; `npm run check` runs the documentation gates, builds the client and the Worker, and runs all three. The e2e tests need ffmpeg and a Chrome that decodes H.264: Google Chrome or Chrome for Testing, since Playwright's own Chromium cannot play the car's streams. `YOLO_E2E_WEBKIT=1` also runs the `<video>` engine's journeys in Playwright's WebKit, Safari's engine; `PLAYWRIGHT_WEBKIT_EXECUTABLE` names a WebKit build other than Playwright's own. `PLAYWRIGHT_CHROMIUM_EXECUTABLE` names the Chromium or Chrome binary to launch (by default Google Chrome where a Mac has it installed, otherwise Playwright's own Chromium), and `YOLO_E2E_LOG` sets the media node's log level during the e2e tests (default `warn`).

**CI** runs `npm run check:core` on Node 22 and 24 for every push to `main` and every pull request. The e2e tests run in their own workflow, each test file on a runner of its own at once, with the runner's Google Chrome and Ubuntu's ffmpeg, whose packages are cached per runner image so that only the first run on a new image waits on apt's mirror; a change that touches only what cannot reach the stack (Markdown, translation records, Agent Notes, skills, the documentation gates, the Apple clients, the conformance kit, or the other workflows) skips them. When the event loop drains while a test's promise is still pending, the test runner of the oldest supported Node (22) cancels that test and the rest of its file, so a test must not depend on an unref'd timer to settle; to reproduce CI's oldest job locally, run the file under Node 22 (for example `npx -y node@22 --test <file>`).

### In-car checks

Route and playback changes are also checked in the car with the stream type they affect: `hls`, `direct`, `dash_split`, or `plex`, confirming that the player loads and pairs, seeking works, and picture and sound stay in sync. After changes to playback or networking, a fault check covers what local automation cannot reproduce: the real Tesla renderer, the mobile connection, the Cloudflare path, and the home node together. Start a fixed 720p60 YouTube or Bilibili video, then run each fault separately and let playback settle before the next:

| Fault | Expected |
|---|---|
| Disconnect the car for 30 seconds | Buffered video continues where possible; recovery resumes near the prior position without a page reload |
| Disconnect for 60 seconds | Once a stall lasts 8 seconds, the device's events report `bandwidth_insufficient` (available versus needed kbps) or `network_unstable`; retry delays stay capped at 60 seconds |
| Disconnect for 180 seconds | The page stays responsive and memory stays bounded; playback re-resolves the source when connectivity returns |
| Switch Wi-Fi to LTE or another hotspot | Old CDN and session URLs are dropped, and a fresh stream resumes at the saved position |
| Restart the media node while playing | The stale session answers `410`, and the player builds a fresh stream instead of retrying the stale URL |
| Open the player with `?decodeErrorAt=<seconds>` a little ahead of where it will play, then again with `&decodeErrorCount=4` | Once: a `decoder_recovery` at step 1 with `outcome: "recovered"`, no new stream, and the sound playing on. Four times: steps 1 to 3 `failed`, step 4 `requested`, then one new stream at the position |

It passes when no state loops forever (buffering, disconnect, reconnect); recovery follows the 1, 3, 10, 30, then 60-second backoff without a retry storm; HLS prefetch drains after recovery with one download active; `bandwidth_insufficient` is reported only when at least two throughput samples support it; quality changes follow the [adaptive policy](../feature/2026-10-11-adaptive-quality.md); and the device's events show `stall_start`, the recovery, a fresh stream request, and `playback_recovery_stable` ([device telemetry](../feature/2026-10-11-device-telemetry.md)).

## Consequences

Most behavior is proven quickly and deterministically, and the end-to-end layer proves the joins with real media, a real Worker runtime, and a real browser, without credentials or a network. Browser end-to-end tests remain the slowest and least stable layer under load. A cut suite catches fewer narrow regressions; review and the in-car check carry more of that load. Hardware, moving-vehicle networks, and real YouTube, Bilibili, and Plex accounts still need the in-car check; a green suite does not prove them.
