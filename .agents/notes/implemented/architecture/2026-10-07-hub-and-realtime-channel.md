# Agent Note: The Hub, one queue, and the realtime channel

Status: implemented

English | [中文](2026-10-07-hub-and-realtime-channel.zh.md)

## Problem

Something has to own "what is playing now" across an agent, a car, and other screens, push commands to whichever screen plays, and hear back where playback is. The original Tesla-only player had one window connected to one server, and a second player window kicked out the first. Yolo has several devices per user, an always-on control plane billed by Durable Object wall time, and clients that may be buggy or asleep in a parked car.

## Decision

### One queue, one active device

Each user has one **Hub**, a Durable Object ([`service/control/src/hub/hub-core.js`](../../../../service/control/src/hub/hub-core.js), wrapped by `hub.js`). It owns the user's single `PlaybackState`, a single Spotify-style queue, and which device is **active**: at most one device plays at a time. Moving playback to another device (`PUT /v1/playback/device`, the `transfer` tool) carries the position along, and the old device receives `deactivate` and becomes a remote control. If the same device connects from another window, only the newest connection plays; the old window receives `deactivate` with `reason: "replaced"` and offers a take-over button that reconnects. A window replaced while its own `hello` was being answered gets no `welcome`, so it never acts on one; a `hello` that fails once its connection was the device's closes that connection (`1011`), and the page reconnects with its backoff. A play that names no device goes to the active device, or else to the only online device that can play; a remote ([capabilities](2026-10-07-capability-negotiation.md) with `renderer: "remote"`) is never picked and cannot be named.

### The realtime channel

Devices connect to `wss://…/v1/realtime` after trading their token for a ticket ([OAuth](2026-10-07-oauth-authorization-server.md)). Every message shares one envelope, `{ v: 1, type, id?, ... }`; a command with an `id` expects an `ack`.

**Heartbeat from the device.** The device sends `{"v":1,"type":"ping"}` every 25 seconds, because Cloudflare closes a WebSocket idle for 100 seconds. The string must match exactly (`HEARTBEAT_PING` in `@useyolo/core`): the Durable Object's WebSocket auto-response answers `{"v":1,"type":"pong"}` without waking the Hub, so heartbeats cost no Hub wall time. The server sets no timer and sends no heartbeat of its own.

**Limits**, so that a buggy client cannot keep the Hub awake and billing:

- At most 16 connections per user and 20 new connections per minute; beyond that, `429 rate_limited`.
- At most 30 messages per connection per 10 seconds, heartbeats excluded; beyond that, the server closes the connection with `1008 rate_limited`.
- Clients reconnect with exponential backoff and wait at least 30 seconds after a `1008` or `429`.
- Clients never answer a broadcast (`state`, `queue`, `playlists`, `devices`) with a `report` or any other message, which would loop with the Hub. A `media` message makes a screen probe its paths again, and it sends `network` only when its path changes; the Hub answers `network` with no broadcast.

**From the device:**

| type | Fields | Meaning |
|---|---|---|
| `hello` | `protocol?, deviceId?, name, kind, capabilities` | `protocol` is the [client protocol](2026-10-19-client-protocol.md) the device speaks; one the Hub no longer serves gets a welcome with only `upgrade: true` and `clientProtocols`, then the connection closes, and a hello without it counts as the first number. Without `deviceId` the server assigns one. A paired device (whose ticket came from a device credential) can only be itself, and `deviceId` is ignored; a removed device is closed with 4003 |
| `report` | `sessionId, status, position, duration, playing, viewport?, health?, keep?` | Only from the active device, at least every 5 seconds and at once on a status change. A report for a session other than the current one is ignored. `health` comes about every 15 seconds while playing, and at once for a new stream, a new stall, or a change of buffering: `{ engine, bufferSeconds, throughputKbps, buffering, stalls, stallSeconds, recentStalls: [{ ago, seconds }], width, height, videoCodec, droppedFrames }`, the player's own measurements; the Hub keeps the latest per device, with the last stream it loaded and its recent rebuilds, for playback health ([`playback-health.js`](../../../../service/control/src/hub/playback-health.js)). `status: "idle"` means the device left the video itself (Back): the Hub records the position and keeps the item paused on that device, marked `leftAt`, for its now-playing bar to play again. With `keep: true` the device keeps its paused player behind its home screen: the Hub also marks the item `kept` and leaves the node's session running until the device either reports from that player again (it was shown) or reports `idle` without `keep` (it let the player go); without `keep`, the Hub stops the node's session ([progress and resume](../feature/2026-10-11-yolo-owns-progress-and-resume.md)). A plain `idle` that a dead connection took goes again after the next welcome (below) |
| `ended` | `sessionId` | Playback finished; the Hub takes the next queue item, once per stream: an `ended` that arrives while the Hub is still taking the next item for the same stream is ignored |
| `error` | `sessionId, code, message` | Playback failed; the Hub decides whether to rebuild the session or stop |
| `ack` | `id` | Acknowledges a command; for an agent's danmaku change, the Hub then stops keeping it (below) |
| `network` | `path, reason?, probes?, hairpin?` | The media path the device takes (`lan`, `wan`, `relay`, or null for none) and each probe's outcome, with `hairpin` (`ok` or `failed`) from a device the welcome marked as at home: whether the router loops back to the home's public address, sent when its choice changes, once after each welcome, and when a stream fails on its path. The Hub keeps the latest value per device and passes the path to the node with the next `prepare`, gives a device that found none the relay unless the owner turned it off, and otherwise refuses with `media_unreachable`; the device's own play requests carry it too, and win. A path the Hub does not know counts as none, as does a report without `path`, such as one from a player before 0.5 that carries only `lan` ([media off the Worker](2026-10-13-media-off-the-worker.md)) |
| `ping` | none | The heartbeat string |

**From the server:**

| type | To | Meaning |
|---|---|---|
| `welcome` | The device that just connected | `deviceId`, the current `state`, `queue`, and `playlists`, `commands` (the last `pause` or `resume` and the last `seek` sent to this device for the stream `state` names, when there are any; below), `media`: `{ paths: [{ path, origin, notAfter, home? }], relayMode, domain? }`, the node's listeners that serve with a valid certificate (`wan` only while it was reached from outside), `home: true` on `wan` when the device connected from the home's public address, the relay's mode (`auto`, `on`, or `off`), and `domain: false` on an instance without a domain. If `state` shows this device still playing (a page reload, the car waking up), the device asks for a new stream with `reason: "recovery"`. The Hub sends each `load` once, over the connections the device has then, and sets `state` as soon as the `load` has gone out. A connection becomes the device's before its welcome is read: what the Hub sends from then on reaches it, a `load` possibly just before the welcome, and the welcome's `state`, read last, names any stream whose `load` went out before. So when `state` names this device with another stream than the one it plays (a seek's, a quality change's, a recovery's, an agent's play), that `load` went with the old connection, and the stream it plays is one the Hub stopped when it built the new one. The device asks for the Hub's stream first, in its place, and the `load` that answers switches the screen over: for the same item at a pending seek's target (`reason: "seek"`), else where the device is (`reason: "recovery"`), even when the lost `load` was an agent's play of that item from another position; for another item where and whether `state` says, as a page that just opened would. Refused as `superseded` (the welcome was older than the stream on screen, or the Hub moved on), the stream on screen plays on; failing otherwise, the device leaves it with the error. A seek's stream that has not arrived 10 seconds after the Hub built it makes the device ping its connection and replace it if no answer comes; one still missing 10 seconds later over a connection that answers ends the seek as failed. When the answer to the device's request named the stream the Hub built, the device then asks for a new stream where it was in place of that one; when the request was refused as `superseded`, it knows no such stream and plays on the stream it had. Any stream request of the device's own refused as `superseded` makes it ping its connection too |
| `load` | The active device | The stream descriptor (`stream`), the item with its Source (needed to rebuild the stream), `startTime`, `autoplay`, and `reason` (`play`, `recovery`, `seek`, `quality`, `transfer`, `tracks`). The Hub's state is `loading` until the screen reports, or `paused` from the start for a `load` with `autoplay: false`. `tracks` means a track change needed a new session, such as a Plex image subtitle or another audio track. A device asks for one seek's stream at a time: a seek while that request or its `load` is on its way moves the target, and the stream starts at the last one. A last target before where that stream starts is a seek once the stream has loaded, inside it when it can go there and with a stream of its own when it cannot, unless the owner or an agent seeks again while it loads. While a seek's stream loads, the device cannot tell yet where that stream can go, so a seek then gets a stream of its own wherever it goes: the first such seek asks for one, and the seeks after it move its target, so the last seek asked for is where playback goes on. The stream that was loading waits paused, and plays on if the newer stream never comes (that seek ends as failed) |
| `pause`, `resume`, `stop`, `seek` | The active device | Control commands. `pause`, `resume`, and `seek` carry the `id` the screen acknowledges and the `sessionId` of the stream they are for (below). A `resume` or `seek` that comes ahead of its connection's welcome and names another stream than the one the screen has, is starting, or keeps is not applied there: that stream's `load` went with the connection before, the welcome switches the screen to it, and the new stream starts where a seek so left went. Over a welcomed connection a stream's `load` comes ahead of its commands, so they apply. A `pause` always goes |
| `tracks` | The active device | Change subtitles or audio, with the subtitles' VTT URLs |
| `danmaku` | The device an agent named, or the active one | `settings`: the danmaku settings to change on that screen (`enabled`, `density`, `opacity`, `area`, `fontSize`), which the screen keeps itself ([danmaku](../feature/2026-10-13-danmaku.md)). The Hub keeps a change's settings until the screen acknowledges it, and sends them again right after the screen's next welcome, with `again: true` (below) |
| `deactivate` | The previously active device | Playback moved elsewhere; this device stops and becomes a remote. `reason: "replaced"` is the same device connected from another window |
| `state`, `queue`, `playlists`, `devices` | Every device | Broadcasts of changes |
| `media` | Every connected device | The welcome's `media` for that device, sent when the remote origin a welcome lists changes, such as the home's new address without a domain ([media off the Worker](2026-10-13-media-off-the-worker.md)) |
| `pong` | The device that sent `ping` | Sent by the runtime's auto-response |

The Hub writes the active device's reports to Yolo's history ([progress and resume](../feature/2026-10-11-yolo-owns-progress-and-resume.md)), and the order of requests from a waking device is covered in [wake request ordering](../bug-fix/2026-10-11-wake-request-ordering.md). A play whose history write fails still plays, and the Hub logs `history_write_failed`: that viewing is not in history, so an item with no earlier entry keeps no progress from it, and a later play of it without `startTime` starts where the source says.

### What a dead connection takes

The Hub sends each message once, over the connections the device has then, and counts a command as delivered when a socket of the device took it. A connection that died without either side noticing takes the command, and the agent was told it worked; a report the screen sends into it is lost the same way. The screen's next report would then overwrite what the command set, or the Hub would go on as if the screen had never ended or left its stream. After the reconnect, the welcome and the screen make up for each kind, as they do for a lost `load` (the `welcome` row):

- **Pause, resume, and seek.** The Hub keeps, per device, the last `pause` or `resume` and the last `seek` it sent for the device's stream, with their command ids, and the welcome names them while its `state` names that stream: `commands: { sessionId, playback?: { id, action }, seek?: { id, position } }`. A new stream starts with none. The screen keeps the ids of the last pause or resume and the last seek it dealt with, recorded against the stream each command names (`sessionId`), so one that arrives while the screen swaps streams counts for the new one; from a Hub that names none, against the stream the screen has or is starting. One the welcome names, for the stream the screen plays or keeps behind its home screen, that the screen never dealt with, it does now, then reports once: the pause or the resume first, then the seek. A missed resume shows a kept player again; a kept player that stays kept takes a missed seek before it tells the Hub again that it is kept, so the Hub keeps that position. Done or left out, what the welcome names is settled: a later welcome naming the same commands changes nothing ([`missed-commands.js`](../../../../clients/player/src/missed-commands.js)).
- **What the owner did meanwhile.** A pause on the screen (in Yolo's controls, the system's media controls, Picture-in-Picture or the system's player, or by a call), Back, a seek on the screen, and a change to a danmaku setting each count as unheard by Yolo until Yolo answers a ping the page sends right after it over its welcomed connection. That connection delivers in order, so whatever Yolo sends after that answer, or sent and the page never received, was sent after the owner's action; no clock is read. This holds only for the connection the Hub has welcomed: until a new connection's hello binds it, the Hub still sends to the old one, so an answer over the new one proves nothing about what the old one lost. The page therefore pings only over a welcomed connection, and what the owner does while it has none stays unheard until the next welcome. One ping is in flight at a time; its answer covers what the owner did before it was sent, and what came after waits for the next. The rule also takes the runtime to answer a ping only after it delivered what the Hub sent before on that connection. Cloudflare does not document how the runtime's automatic answer orders against the Durable Object's output gate, which holds what the Hub sends while a storage write is still unconfirmed. An answer that passed such a command could make the page take it for newer than the owner's action, but only if the connection died in those few milliseconds as well. At a welcome, a missed resume is left out while the owner's pause or Back is unheard, since that pause may be the newer, and nothing starts playing on that doubt. A missed seek is left out while the owner's seek is unheard. A missed pause always goes, since it starts nothing. What the owner did before a welcome counts as heard after it, since everything Yolo sends over the new connection is newer.
- **Subtitles.** The welcome's `state.tracks` are the Hub's choice for the stream. When its subtitles differ from the text subtitles the screen shows, and the switch needs no new stream, as with a `tracks` message, the screen shows the Hub's. A switch to or from a burned-in track, and an audio change, needs a new stream.
- **Danmaku.** The Hub keeps, per setting, the value an agent's change set last and that change's id, until the screen acknowledges that change. Right after the screen's next welcome it sends them again, each change under its own id with the settings no later change set, marked `again: true`. Of such a message, the screen skips a setting it applied from that change already, which the owner may have changed since, and one the owner changed unheard, and applies the rest. A page loaded since knows neither, and applies the whole message.
- **`ended`.** The screen remembers a stream it played to its end and told Yolo `ended`, until anything plays, pauses, or seeks it or another stream starts, and counts the `ended` as heard once Yolo answers a ping sent after it over the welcomed connection (an `ended` sent before the Hub binds a new connection is dropped there). When the welcome still names that stream and the `ended` is unheard, the screen sends `ended` again, unless a missed pause or seek from the same welcome pauses or moves it. The Hub takes the next item for a stream once: an `ended` that arrives while the next item for the same stream is still being taken is ignored.
- **`idle` without `keep`.** A screen that left a stream without keeping its player remembers that stream until a `state` marks it `leftAt` or names another stream, in the browser tab's `sessionStorage` too, so a page loaded again in the tab (a reload, a car's wake) remembers it. When the welcome still names that stream on this device without `leftAt`, the screen says `idle` again with the position it left at, and does not resume it.

A page that does not know `commands` ignores it, and a welcome without it leaves the screen's playing or paused state and position as they were. A page that does not know `again` applies such a danmaku message whole. A Hub that takes every `ended` it gets could take two items only when the first `ended` reached it and the answer to the ping after it was lost, since the screen sends `ended` again only while it is unheard.

### The channel stays in core

The realtime channel is part of Yolo's core, not a device plugin. The player, in both profiles, is the channel's device and negotiates playback through its [capabilities](2026-10-07-capability-negotiation.md). In the car profile a tap plays on the car itself; in the web profile, in a computer's or phone's browser, the player plays (through `<video>` where the browser can) and also acts as a remote: a tap plays on another device that is playing or paused, and otherwise in this browser ([where a tap plays](../feature/2026-10-11-yolo-web-client.md)). The device-plugin interface will be designed when the first third-party device arrives (a Jellyfin session or an Apple TV), from that device's real needs.

## Alternatives considered

**A queue per device, as Plex does.** One person has one pair of eyes and never watches on two screens at once, so one queue and one active device match how Yolo is used.

**A device plugin for the realtime channel from the start.** Both profiles of the one player, car and web, are Yolo's own and speak the same protocol; an interface with one implementation could not be designed well.

**Server-initiated heartbeats.** A server timer would wake the Hub every interval and bill its wall time for every connected device; device-sent pings answered by the auto-response cost nothing.

**Sending every unacknowledged command again after the welcome.** That fits danmaku settings, which belong to the screen and apply on any page. A pause, resume, or seek belongs to a stream: a page that reloaded has no player for it and already plays what `state` says, and a resume sent to a kept player, or to a screen whose owner paused it while the connection was dead, would start playback without asking the screen. Only the screen knows which stream it plays and which commands it heard, so the welcome names the commands and the screen decides.

## Consequences

Every device sees one consistent playback state, and moving playback between screens is one call. A command or report that a dead connection took takes effect at the reconnect, for the cost of one stored entry per device for its last commands and one for its unacknowledged danmaku settings. Heartbeats and idle connections cost no Durable Object time, and the limits bound what a misbehaving client can cost. Two people cannot watch different things on one account, which suits the single-owner model and would need revisiting for households. Third-party players need a device-plugin interface that does not exist yet.
