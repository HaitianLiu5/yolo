# Agent Note: 媒体节点按规则走代理的出口层

Status: implemented

[English](2026-10-13-node-egress-proxy.md) | 中文

## 问题

片源播放的每个字节都由节点经家里的网络下载（[媒体管线](2026-10-11-node-media-pipeline.zh.md)），每个网页也都从这条网络经 yt-dlp 解析。有些内容只对节点不在的某个地区开放：某个网站只给本国观众看的体育回放或番剧，付费账号也一样，而它随后给出的媒体服务器从哪里都能访问。节点需要把受地区限制的那几个请求经该地区的代理发出，其他一概不动。

从家里的网络访问片源 CDN 的质量也随时间变化很大。2026-10-12 和 2026-10-13 从家里的节点测量，同一个 Bilibili 镜像前一天只有 172 kbps，第二天最高 70 Mbps；其他镜像只有 2–5 Mbps，并且会卡顿。对冲的分片读取和节点对每个主机的记忆会实时选出最好的镜像（[分片读取](2026-10-11-node-media-pipeline.zh.md#segment-reads)），但从节点的网络看所有镜像都慢时，它们帮不上忙。

## 决策

节点核心里有一个出口层，把用户规则选中的上游请求经有名字的代理发出；代理由一种插件类型提供（[`service/node/src/egress/`](../../../../service/node/src/egress/)）。

### 规则

用户的 `yolo.config.json` 可以在 `plugins` 旁边有一个 `egress` 段。它给代理命名，每个代理写明由哪个提供者提供以及给提供者的选项，再列出按主机名匹配的规则：

```json
{
  "plugins": ["./plugins/source-ytdlp", "./plugins/proxy-url"],
  "egress": {
    "proxies": { "abroad": { "provider": "url", "options": { "env": "EGRESS_ABROAD_PROXY_URL" } } },
    "rules": [
      { "hosts": ["api.video.example", "*.api.video.example"], "via": ["abroad"] },
      { "hosts": ["*.cdn.example"], "via": ["direct", "abroad"] }
    ]
  }
}
```

- **第一条主机匹配的规则生效，** 它的 `via` 按尝试顺序列出线路，`direct` 是其中一条。模式 `*.example.com` 匹配 `example.com` 的子域名，不匹配 `example.com` 本身。
- **没有匹配任何规则的主机直连。** 出口层从来不是全局代理：通往控制面的 cloudflared 隧道、媒体监听端口和这台机器的其他所有连接都碰不到它；没有 `egress` 段时，节点的请求和以前完全一样。
- **不含 `direct` 的规则让这些主机只经代理访问，** 有地区限制的内容需要的正是这样：它列出的代理都失败时，请求就失败，而不会改为直连。同时列出 `direct` 的规则，在某条线路还没拿到响应就失败时换下一条。
- **格式错误的 `egress` 段会让节点启动失败**（[`rules.js`](../../../../service/node/src/egress/rules.js)）：线路指向不存在的代理、代理叫 `direct`、主机模式里带了协议或路径。写错一个字不能让流量换一条路走。

### 代理提供者

代理提供者是一种插件类型。节点入口用 `yolo.registerProxyProvider(id, { endpoint(options, { refused, failed }) })` 注册一个，`egress.proxies` 里的代理把它写成 `provider`。`endpoint` 返回代理当前的位置 `{ url, username?, password?, expiresAt? }`，`url` 是 `http://` 或 `https://` 地址（凭据也可以写在地址里），提供者自己的登录也由它处理。提供者永远不知道哪些请求、哪些主机在用它。

- **节点会再次询问：** 在 `expiresAt` 之前不久（60 秒），在代理对它给的凭据回答 407 之后（带 `refused: true`），在代理本身失败之后（带 `failed: true`），以及提供者没给出地址 30 秒之后；每个代理同时只问一次。启动失败的插件会带走它注册的提供者。
- **代理失败**指连不上它（连接被拒绝、被重置或超时，或者它的域名解析不了），或者它对 `CONNECT` 回答 502、503 或 504。这时节点带 `failed: true` 询问，每个代理每 10 秒最多一次，免得代理到不了的网站让提供者每个请求都去找新服务器；有多台服务器的提供者先检查自己给出的那台，坏了就换一台。代理拒绝或失败的请求会再试一次，前提是提供者给出了不同的地址；在这之前，代理一坏，只走代理的规则下每个请求都失败，直到节点重启。
- **Yolo 只带一个通用的官方提供者 [`plugins/proxy-url`](../../../../plugins/proxy-url/src/node.js)，** 它注册 `url`：一个固定的代理，地址连同凭据放在代理的 `options.env` 指定的环境变量里。它不在 `plugins/official.json` 里，用户要在 `yolo.config.json` 里列出它。它的目录名不对应任何服务商，所以 `scripts/provider-names.js` 把它和模板一起列为不给出服务商名字的插件。
- **Yolo 还带一个商业加速服务的提供者 [`plugins/proxy-transocks`](../../../../plugins/proxy-transocks/src/node.js)，** 它注册 `transocks`：只凭用户的账号就能登录、选出能建隧道的最快中国线路、续期，并在线路失败时换掉它（[Transocks 代理提供者](../feature/2026-10-28-transocks-proxy-provider.zh.md)）。它同样默认不加载。这类服务只通过私有接口给出代理地址，接口会不打招呼地改变；它的设备数限制可能让节点一登录就把用户的另一个会话挤下线。2026-10-28 用户选择把这些放进仓库，而不是从该服务自己的客户端手工把线路抄进 `proxy-url` 的环境变量，那样做在那条线路坏掉的当天就不能用了。其他服务的提供者仍是通过 `yolo.config.json` 加载的本地插件（[插件架构](2026-10-11-plugin-architecture.zh.md)）。
- **暂不支持 SOCKS 代理：** 地址是 `socks5://` 的会被拒绝，并给出这个说明。

### 每条出口路径都遵循规则

- **节点自己的请求** 经出口层的 `fetch()`：媒体管线的上游读取（`upstream.js`、`hedge.js` 和按字节范围的读取）、画面和故事板（`frames.js`），以及 AI 字幕读取的声音（`audio.js`）。走代理的线路用 undici 的 `ProxyAgent`，把地址的凭据作为 `Proxy-Authorization`。
- **插件** 拿到同一个函数 `yolo.fetch`，用于它自己对片源的请求；yt-dlp 插件用它读取 Bilibili 的分 P 列表、弹幕、字幕、镜像测速和 DRM 检查。
- **子进程拿到的是回环地址上的代理，而不是代理本身。** 用户有规则时，节点在 `127.0.0.1` 的一个空闲端口上启动一个 HTTP 代理（[`listener.js`](../../../../service/node/src/egress/listener.js)），对自己打开的每个连接套用规则：HTTPS 以 `CONNECT` 到达，直连或经代理自己的 `CONNECT` 建立隧道；普通 HTTP 请求经同样方式打开的连接发出。它只接受回环地址的对端。插件从 `yolo.egressProxy()` 拿到它的地址，没有规则时为 null；yt-dlp 插件每次运行都把它作为 `--proxy` 传入，所以 yt-dlp 对没有规则匹配的主机的请求仍然直连。ffmpeg 读取的输入，主机所在的规则不只有 `direct` 时，以 `-http_proxy` 拿到它。凭据不会出现在命令行里，而 Node 的 `execFile` 会把命令行复制进它的错误信息。

### 凭据和状态

- 凭据放在 `.env.example` 记录的环境变量里，`yolo.config.json` 最多写出变量名。日志和错误信息里都没有代理的凭据或地址：代理用配置里的名字称呼，经代理线路出的错会删去地址的用户名、密码和认证头。
- 某条线路失败时记一条警告，带主机和线路；回环代理打开的隧道以 debug 级别记下主机和线路。提供者给出的第一个地址、续期和失败都会记录，带代理名和提供者。
- `/internal/v1/health` 里有 `egress`：规则条数、回环代理是否在监听，以及每个代理的提供者和状态（`ready`；第一次使用之前是 `idle`；`unavailable` 并附提供者的错误；没有已加载的插件注册它时是 `no_provider`），从不包含它的地址。`npm run yolo -- doctor` 对没有提供者的代理报失败，对不可用的代理报警告。

### 范围

只有节点到片源这一段改变。设备的路径，无论经控制面的隧道还是经[局域网直连播放](../feature/2026-10-12-lan-direct-play.zh.md)，都不变，Plex 也不变。

## 暂缓

**对冲和主机健康度里的线路。** 直连和经代理是拿到同一批字节的两条线路，所以以后的改动会把每一对网址和线路当作一个候选：节点对主机的记忆（`hosts.js`）按主机和线路分别记录故障和吞吐量，对冲的分片读取在现有的阈值和上限内让这些候选赛跑，不设任何按时段的规则。现在规则里的线路按列出的顺序尝试，某条线路失败就换下一条。开始这项工作的条件是遥测显示剩下的卡顿发生在所有镜像都慢的时候：Workers Logs 里设备的 `stall_start` 事件（[设备遥测](../feature/2026-10-11-device-telemetry.zh.md)），按节点每行日志的 UTC 时间戳，与节点发现某个分片所有镜像都慢的对冲对得上。那时经代理的线路要在 1.5 秒的对冲阈值下多付首字节的延迟，跨两条线路的对冲可能把同一段字节读两次，计入付费流量。

## 曾考虑的替代方案

**系统级 VPN 或 TUN 客户端的全局模式。** 它不需要改 Yolo，但会把通往控制面的 cloudflared 隧道和机器发出的其他一切都经代理所在的地区转发，于是每台设备的媒体和控制面到节点的每个请求也都要绕这一圈。

**网站回答地区错误时，只让 yt-dlp 经代理重试。** 它只覆盖一个片源，而且只覆盖解析；它依赖每个网站对错误的措辞；节点自己的请求和 ffmpeg 的读取仍然没有办法访问受地区限制的主机。

**整个出口层做成插件。** 规则决定的是管线自己的上游读取（包括对冲）以及节点启动的子进程走哪条线路，所以无论由谁实现，挂钩都得在核心里；各个服务之间真正不同的只是代理在哪里、怎么登录，这正是提供者插件装的东西。规则只写用户配置里的主机和代理，从不写服务商，所以核心仍然不认识任何服务商。

**把代理地址直接交给 yt-dlp 和 ffmpeg。** 这会把凭据放进命令行和 `execFile` 的错误信息里，还会让子进程的每个请求都经代理，包括没有规则匹配的主机。

## 后果

用户只要加一个提供者插件和一条只列出受地区限制主机的规则（通常是网站的播放接口），就能访问受地区限制的内容，而它的媒体服务器保持直连、全速；没有规则的用户什么都不变。任何服务的提供者都只是一个给出地址的小插件，通用的 `proxy-url` 覆盖任何固定代理。

代价：

- 提供者在插件信任模型下以节点的全部权限运行，包括 `.env` 和 `NODE_SECRET`，而且它所用服务的私有接口一变就会坏。代理没有地址时，规则里也列了 `direct` 的主机改为直连，只走代理的规则后面的内容无法播放。
- 这台机器上的任何进程都能经回环代理发请求；插件调用全局 `fetch` 而不是 `yolo.fetch` 就绕过了规则。
- 用户有规则时，yt-dlp 的每个请求都经回环代理，直连的主机也多走一跳本机转发。
- 请求体是流的请求只尝试第一条线路。
- 经代理的流量可能计入付费额度；经代理播放受地区限制的内容可能与片源的条款冲突。
- 网站可能对经代理的页面给出只有本地区能访问的媒体主机，而节点直连下载媒体，读不到它们；这时片源的插件要选出从任何地方都能访问的主机，就像 yt-dlp 插件对 B 站做的那样（[B 站页面走出口规则](../feature/2026-10-27-bilibili-through-the-egress-rule.zh.md)）。

[`service/node/test/egress.test.js`](../../../../service/node/test/egress.test.js) 里的测试固定了这些行为：规则；提供者地址的生命周期（问一次后复用，过期前续期，407 之后再问一次，代理连不上或对 `CONNECT` 回答 502 之后也再问，但每 10 秒最多一次，同一个地址不重试）；只走代理的主机从不直连；回环代理把匹配的主机经代理转发、其他主机直连；日志里没有密码；插件能注册提供者并经出口层发请求。
