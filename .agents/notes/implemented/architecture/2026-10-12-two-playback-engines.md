# Agent Note: One player over two engines: canvas in the car, `<video>` on the web

Status: implemented

English | [中文](2026-10-12-two-playback-engines.zh.md)

## Problem

The canvas engine (Mediabunny and WebCodecs drawing to `<canvas>`, with a `SharedArrayBuffer` audio clock) exists because Tesla can freeze a `<video>` element while the car moves ([canvas engine](2026-04-04-canvas-playback-engine.md)). Yolo Web used it in every browser too ([Yolo Web](../feature/2026-10-11-yolo-web-client.md)). Computer and phone browsers do not freeze `<video>`, so there the canvas engine is pure cost: demuxing in JavaScript, a decoded-frame queue, canvas painting, and an audio pipeline of its own, where the browser has a native media pipeline with hardware decoding. It also needs cross-origin isolation, which Safari does not give the page (it ignores `Cross-Origin-Embedder-Policy: credentialless`), so an iPhone or iPad could only be a remote. And what comes with `<video>` — Picture-in-Picture, the lock screen's media controls, AirPlay — was out of reach.

## Decision

The client has one player and two engines with one interface. [`player.js`](../../../../clients/player/src/player.js), with the modules it draws through, owns everything above the engine: the player's controls, progress, menus, and loading screen and error panel ([`player-screens.js`](../../../../clients/player/src/player-screens.js)); reports and progress to the Hub; recovery with new streams, after the canvas engine recovered a failed decoder in place as far as it could ([canvas engine](2026-04-04-canvas-playback-engine.md)); telemetry ([`telemetry/`](../../../../clients/player/src/telemetry), which reads both engines' `getStats()` in [`engine-stats.js`](../../../../clients/player/src/telemetry/engine-stats.js)); adaptive quality; resume; and the Hub's commands (load, pause, resume, seek, tracks, stop). It drives either engine through the interface of [`engine/mediabunny-player.js`](../../../../clients/player/src/engine/mediabunny-player.js): `load`, `play`, `pause`, `seek`, `stop`, `destroy`, the states `loading`, `paused`, `playing`, `buffering`, `seeking`, `ended`, and `error`, `getCurrentTime`, `getStats`, `getSeekableRange`, `getLiveTimeline`, `setVolume`, `setPlaybackRate`, `enableAudioOutput`, and `audioOutputState`.

### Which engine plays

The device's [profile](../feature/2026-10-11-yolo-web-client.md) chooses ([`engine/native-support.js`](../../../../clients/player/src/engine/native-support.js)):

| Profile | Engine | Otherwise |
|---|---|---|
| `car` | The canvas engine, unchanged | A remote, when the browser cannot run it |
| `web` | The browser's `<video>` element ([`engine/native-video-player.js`](../../../../clients/player/src/engine/native-video-player.js)), when it plays Yolo's streams | The canvas engine when only that runs; a remote when neither does |

**A Tesla never plays through `<video>`.** A page the Tesla fingerprint recognizes ([device code pairing](../feature/2026-10-07-device-code-pairing.md)) plays with the canvas engine and announces `CAR_CANVAS_CAPABILITIES` in `hello`, whatever type the owner gave the device. A car paired as a browser keeps the web profile's layout and its rule for where a tap plays, but not the `<video>` engine; a Tesla that cannot run the canvas engine is a remote.

A `<video>` element plays Yolo's streams when it plays HLS by one path or the other, and H.264 with AAC. Apple's WebKit (Safari, and every browser on iPhone and iPad) plays HLS natively, which keeps AirPlay and the system's media pipeline. Elsewhere (Chrome, Edge, Firefox, Android) [hls.js](https://github.com/video-dev/hls.js) feeds Media Source Extensions. Progressive files play directly. hls.js is its own chunk, which a page that plays HLS through it fetches once its home screen shows, so the first tap does not wait for it; the car never downloads it. Outside a Tesla, a change of the device's type changes the engine from the next stream on.

### What the `<video>` engine does

- **Capabilities.** The page announces `renderer: "html5-video"` with the codecs its HLS path plays (`MediaSource.isTypeSupported` for hls.js, `canPlayType` for native HLS), avc1 and mp4a first, and a `maxHeight` from the display ([capability negotiation](2026-10-07-capability-negotiation.md)).
- **Positions are the item's.** A `<video>` element counts from the stream's first segment. With hls.js the engine adds the media's own first timestamp (`INIT_PTS_FOUND`), which is the timeline the canvas engine reads. Native HLS does not expose it: for a stream the node may have trimmed to its start position (the descriptor's `trimToStart`, a transcode resumed part way), the part of the item's duration that the stream lacks stands in for it, accurate to the source's rounding of the duration (Plex's is whole seconds). A seek before such a stream's start asks Yolo for a new stream, as with the canvas engine.
- **Waiting is the time standing still.** The element's events alone do not tell: WebKit's native HLS fires `waiting`, or ends a seek below `HAVE_FUTURE_DATA`, and then plays on without `playing` or `canplay`. So the time moving ends a wait, whatever the events said, and a `waiting` becomes buffering only once the time has stood still for 750 milliseconds; playing with the time still for 5 seconds is a stall the browser did not report. A `pause` that Yolo did not make, arriving while the element has nothing ahead to play (below `HAVE_FUTURE_DATA`, or during a wait already seen), is the browser pausing for a stall, not the owner's pause: it shows the spinner, and the engine plays on, with the sound as it was, once data is back.
- **Failures.** A 410 from the node is `SESSION_EXPIRED` and a 403 is `UPSTREAM_ACCESS_DENIED`, also where hls.js would keep asking again for a single variant's fragment. A `<video>` element never reports the status that failed, so after an element error, and after 8 seconds of waiting, the engine asks the node itself: a `HEAD` of the stream and, for native HLS, of its first variant playlist, which the node fetches from the source. A network error, a decode error, or 30 seconds without new data (`MEDIA_NETWORK_ERROR`, `MEDIA_DECODE_ERROR`, `MEDIA_STALLED`) rebuild the stream through the player's recovery; a stream the browser does not play (`MEDIA_UNSUPPORTED`) shows the error panel.
- **Subtitles stay Yolo's.** [`subtitles.js`](../../../../clients/player/src/subtitles.js) draws them over the picture, laid out from the element's picture size and timed by the engine's position. The engine keeps the browser's own captions off: hls.js renders no subtitles or captions, and a text track the browser shows is disabled. The exception is the system's fullscreen player on iPhone (below), where Yolo's overlay cannot show. The selected subtitles are also text tracks of the element, made from the cues Yolo already parsed and moved onto the stream's timeline (a `<track>` loading the WebVTT file would miss the offset of a stream resumed part way), and hidden inline. While that player has the picture, the first selected subtitle shows, or, when Yolo has no cues for it, the stream's own subtitle track in the same language; a choice in that player's caption menu holds until it closes.
- **Audio tracks.** Audio tracks a source lists (Plex's) switch through Yolo, which rebuilds the stream, as before. Audio renditions inside an HLS playlist that the source does not list switch in the engine (hls.js's audio tracks, the element's `audioTracks`), without a new stream.
- **Sound.** Playback starts with sound when the browser allows it; otherwise it plays muted with "Tap for sound" (a stream without video waits for a tap), and the first tap unmutes it while the gesture is active ([progress and resume](../feature/2026-10-11-yolo-owns-progress-and-resume.md)). Every stream plays in the element the last stream played in: WebKit lets an element play sound without a gesture only once a gesture has started it, so with a new element for each stream, a quality change or a recovery on an iPad played muted until another tap. Yolo's subtitle tracks stay with the element, disabled, and the next stream takes them up again. The element plays at the system's volume; the canvas engine's gain boost does not apply.
- **What comes with `<video>`.** Hardware decoding. A fullscreen button where the browser offers it ([`picture-controls.js`](../../../../clients/player/src/picture-controls.js)); Picture-in-Picture has no button of Yolo's, which the owner found clutter, and stays in the browser's own menu and the system's player; fullscreen takes the whole player, so Yolo's controls and subtitles stay. Every browser on iPhone lacks element fullscreen and can only put the `<video>` element itself in fullscreen, in the system's own player (`webkitEnterFullscreen`): there the button opens that player, as YouTube's mobile site does, while iPad and computers keep the player's fullscreen. Danmaku cannot show in the system's player and goes on after it closes. On the way back the engine takes over what that player did (a pause, a play, a seek, the sound turned off or on), whether or not each event reached the page, and the controls, the Hub, and progress follow at once. A new stream closes that player, so while it is open only a stall steps quality down, and a step up makes no new stream anyway; the queue's next item and a recovery close it too. Turning the phone sideways does not open it: iOS opens it only from a tap, and a rotation is not one. The system's media controls (the lock screen, a phone's notification) through Media Session, with the item's artwork and seeking. AirPlay on Safari. A pause or a play from Picture-in-Picture or the system's controls becomes the owner's intent and reaches the Hub.
- **Live streams** play at the edge of the window the browser can seek in, and seeks stay inside it. The node gives a `<video>` element a live playlist that ends at the newest published segment and reaches 5 minutes back, without the canvas engine's runway of segments not yet published ([media pipeline](2026-10-11-node-media-pipeline.md)).

### Playback speed

The player's speed panel, on both engines, holds a slider from 0.5× to the engine's fastest in steps of 0.1 and the presets 0.5, 1, 1.5, 2, and 3; Shift+. and Shift+, (`>` and `<`) step a quarter within the same range ([`playback-speed.js`](../../../../clients/player/src/playback-speed.js), [in-car design](2026-07-13-in-car-design-principles.md)). The slider lays speeds out on a logarithmic scale of the speed plus one, which gives 0.5× to 2× half of the web's track and 2× to 5× the rest, and a slider let go within 0.05 of a preset lands on it. Dragging plays the speed as it goes, at most every 150 milliseconds, so the engines are not set at every pointer move. The fastest is 5× on the `<video>` engine and 3× on the canvas engine, which decodes the speed's multiple of frames and was not measured past 3× in the car. The owner's speed holds for every stream the page plays: `player.js` gives it to each engine it makes, so it survives a recovery, a seek's or a quality change's new stream, a kept player shown again, and the next item. It is not stored: a new page starts at 1×, as YouTube does, so a speed chosen for a lecture does not carry into the next drive's film. A press and hold below 2× plays at 2× and lets go back to the owner's speed; at 2× or faster it does nothing. A live stream plays at the speed it is made, so it offers neither.

- **The `<video>` engine** sets the element's `playbackRate` with `preservesPitch` (`webkitPreservesPitch` in older Safari), and its `defaultPlaybackRate`, to which loading a new source resets the element. A speed chosen in the system's fullscreen player on iPhone becomes the owner's speed. Chrome and WebKit keep the sound to 5×: the element's output, read through Web Audio, held its level at 4.5× and 5× in Chrome 155 on macOS and in Playwright's WebKit (2026-10-21). Firefox mutes it outside 0.25× to 4× (Gecko's `THRESHOLD_HIGH_PLAYBACKRATE_AUDIO`), so there, above 4×, the panel says "No sound above 4× in this browser" instead of seeming to play it ([`engine/native-support.js`](../../../../clients/player/src/engine/native-support.js)).
- **The canvas engine** stretches the sound in time in its audio output, keeps its pitch, and keeps its clock in media time ([canvas engine](2026-04-04-canvas-playback-engine.md)).
- **Positions stay the media's own.** Progress, resume, subtitles, and danmaku follow the engine's position and need nothing of their own. The system's media controls get the speed with the position, and above normal speed adaptive quality asks for that much more throughput ([adaptive quality](../feature/2026-10-11-adaptive-quality.md)).
- **The Hub hears no speed, and agents cannot set it.** The Hub counts a playing item's position on between the screen's reports at the normal speed, so until the next report (at most 5 seconds) another screen's now-playing bar, an agent's `get_status`, and the place the Hub keeps when the screen's connection drops are off by the time since the last report times the speed's distance from 1: up to 5 seconds at 2×, 20 at 5×. Both would add to the [client protocol](2026-10-19-client-protocol.md): a `rate` in `report` and in the playback state for the Hub to count with, and a `speed` action of the `control` tool that the Hub sends to the active screen as a command it acknowledges, as it does `pause`. They wait until an agent needs them.

### Cross-origin isolation stays on every page

COOP and COEP stay on every page of the app ([canvas engine](2026-04-04-canvas-playback-engine.md)). One page serves both profiles, and it learns its profile only after it loads (the owner's type for the device, or the Tesla fingerprint), while the headers must come with the document itself; a car served the page without them could not play at all. The `<video>` engine neither needs isolation nor suffers from it: its media is same-origin, or from the node's LAN origin, which answers CORS (the element then loads with `crossorigin="anonymous"`). The subtitle fonts come from the page's own origin under `/lib/fonts/`, so no font host sees a screen's address, and [`third-party-origins.test.js`](../../../../service/control/test/integration/third-party-origins.test.js) fails when the player's build or an owner page references another host. Images come from the same origin: a thumbnail on another host, such as a web video's, goes through `/v1/thumbnail`, which the node fetches ([node's internal API](2026-10-07-node-internal-api.md)). Both engines resolve every media URL of a stream against the stream's origin ([LAN direct play](../feature/2026-10-12-lan-direct-play.md)). Safari ignores `credentialless` and plays through `<video>` regardless. The web app manifest and the home-screen icons are the page's own files too, which the headers let through: Add to Home Screen opens Yolo by itself, without the browser's bars, and needs no service worker, which Yolo does not have. iOS keeps a home-screen app's storage apart from Safari's, so it pairs as a screen of its own.

### Adaptive quality with the browser's ABR

Yolo's cap stays the ceiling, and the browser adapts below it ([adaptive quality](../feature/2026-10-11-adaptive-quality.md)). For every device the node keeps only the variants of a multi-variant playlist that fit the device's `maxVideoKbps`; hls.js and native HLS switch among those by themselves. Yolo's quality controller still rebuilds the stream at a lower cap, and that is what adapts a stream with one variant (Plex's transcode, joined split files, a file); a step up waits for the next stream, as on the canvas engine. It measures with hls.js's bandwidth estimate or, without hls.js, by how fast the buffer grows while the browser fetches. Where hls.js switches variants itself, the variant is its choice: Yolo never rebuilds such a stream for quality and only keeps a step up for the next stream.

### Testing

[`test/e2e/web-playback.test.js`](../../../../test/e2e/web-playback.test.js) plays `direct`, `hls`, `dash_split`, and the Plex fixture through the `<video>` engine in desktop Chromium: seeks, pause and resume, a speed preset with the voice's pitch kept and the speed carried to the next item, subtitles over the picture, an audio switch, recovery after a 410, and fullscreen; the same file leaves an item with Back and plays it on from the now-playing bar, and on a computer changes the speed with its keys, a press and hold, and the panel's slider to 5×, which opens above its button. The car's end-to-end tests check the slider ends at 3×. With `YOLO_E2E_WEBKIT=1` the stream types and Plex also run in Playwright's WebKit, Safari's engine, where HLS plays natively and the page is not cross-origin isolated. The car's end-to-end tests pair as the car and keep testing the canvas engine, at twice the speed too and across a recovery, and a Tesla paired as a browser still plays with it. Unit tests cover the engine choice per profile, and the slider's scale, steps, and presets, each engine's fastest, and where Firefox's sound stops ([`playback-speed.test.js`](../../../../clients/player/test/unit/playback-speed.test.js)); the `<video>` engine itself is proven only end to end.

## Alternatives considered

**The canvas engine everywhere**, as before. It plays in Chrome, but costs CPU that the browser's own pipeline does not, cannot run in Safari (iPhone and iPad stay remotes), and gives up Picture-in-Picture, AirPlay, and the system's media controls.

**`<video>` everywhere, the car included.** Tesla can freeze `<video>` while the car moves, which is why the canvas engine exists.

**The owner's type alone chooses the engine.** The type is a label picked on the approval page, and a car can carry the type of a browser; it would then play through `<video>`. The fingerprint measures the browser itself, so in a Tesla it decides the engine and the capabilities, and the type keeps deciding the layout.

**A separate web player.** It would duplicate the controls, reports, recovery, telemetry, quality, and resume, and the two would drift apart; behind one interface the engines share all of them.

**hls.js in Safari too** (Safari has Media Source Extensions, and the iPhone has ManagedMediaSource). Native HLS keeps AirPlay, uses the system's power-efficient pipeline, and works in every browser on iOS; hls.js there would add a download and give AirPlay up.

**COOP and COEP only for the car's pages.** The page decides its profile after it loads, but the headers come with the document. Sending them per profile needs a signal the server trusts before the page runs, and a wrong guess leaves the car unable to play.

**A multi-variant playlist for every stream, all adaptation left to the browser.** Yolo's joined split files and transcodes have one variant: the node would have to join and probe every format the source offers, or the source would have to transcode several at once, which Plex does not. With Yolo's cap as the ceiling, every source works as it is, and the browser adapts wherever a playlist has variants.

**The browser's captions for subtitles.** Yolo's renderer lays out bilingual subtitles in its own fonts and shows several tracks at once; the browser's captions do neither the same way in every browser.

## Consequences

Computers and phones play with the browser's own media pipeline. In desktop Chrome on an Apple-silicon Mac, the same H.264 and AAC HLS stream costs about half the CPU of the canvas engine, summed over Chrome's processes: about 9% of one core against 17%, at 720p30 and at 1080p30 alike, with both engines showing 30 frames a second and almost none dropped (measured on 2026-10-12 in a visible window; headless Chrome does not pace frames like a real display and is no measure). Safari on iPhone and iPad plays instead of only controlling other screens, and Yolo Web gains Picture-in-Picture, fullscreen (of the player, or on iPhone the system's own player), the system's media controls, and AirPlay. The system's player on iPhone shows no danmaku, counts a stream resumed part way from where that stream begins, and closes for every new stream. The car's behavior is unchanged, also where its type says browser. The fingerprint is the guard: a Tesla whose user agent and window measurements both stop matching it would play as its type says. The player keeps two engines behind one interface, and some failures surface differently: a `<video>` element never reports the status that failed, so the engine asks the node, and a stall the browser does not report is found by watching time and buffer. Under native HLS, the position in a stream resumed part way is as accurate as the source's duration. The runway live playlist, the split-file delivery, and the gain boost remain the canvas engine's. hls.js is a 180 kB (gzip) chunk that only a page playing HLS through Media Source Extensions loads, on its home screen.
