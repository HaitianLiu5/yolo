# Agent Note: The /v1 HTTP API

Status: implemented

English | [中文](2026-10-07-v1-http-api.zh.md)

## Problem

Agents and the player, in its car and web profiles, all need the same operations — play, control, queue, playlists, history, the library, devices — with the same errors and scopes. The earlier server's routes were shaped around one player and one server, named Plex in their paths, and had no authentication. An API defined per client would drift from the MCP tools that do the same things.

## Decision

The control plane serves one JSON API under `/v1` ([`service/control/src/api/v1.js`](../../../../service/control/src/api/v1.js)). It and the MCP tools share one service layer (`service/control/src/services.js`), so a tool and its route cannot diverge. Every route outside `/v1/owner` requires one [OAuth scope](2026-10-07-oauth-authorization-server.md); the [owner routes](#owner-routes) take the owner's passkey session instead.

### Resources

```js
// Device
{
  id: "dev_…", name: "Model Y", kind: "car" | "browser" | "phone" | "tv" | "other",
  online: true, active: false, lastSeenAt: 1730000000000,
  capabilities: Capabilities,
}

// Item: a queue or playlist entry
{ id: "itm_…", source: Source, title, thumbnail, duration, addedAt }

// PlaybackState: the one playback state the Hub broadcasts
{
  status: "idle" | "loading" | "playing" | "paused" | "buffering",
  deviceId: "dev_…" | null,
  item: { source, title, thumbnail, duration, isLive } | null,
  position: 123.4, positionAt: 1730000000000,  // clients extrapolate progress from these two
  tracks: { subtitles: ["en", "zh"], audio: "a_2" | null },
  sessionId: "ses_…" | null,
  walk?: { back: 2, forward: 1 },  // while previous and next walk through history: the items each way
  upNext?: { from: "sequence", title: "…", item: { source, title, thumbnail, duration } },  // what next plays: from "history", "queue", or "sequence"
}

// Track: a subtitle or audio track
{ id: "s_en" | "plex:123", kind: "subtitle" | "audio", language: "en",
  name: "English", auto: false, format: "text" | "image", default: false }
```

A `Source` belongs to a source plugin, and its stable key `sourceKey` (`<plugin>:<id>`) keys history, resume positions, and track preferences ([source plugin API](2026-10-11-source-plugin-api.md)). `Capabilities` is described in [capability negotiation](2026-10-07-capability-negotiation.md). An item's `thumbnail` is a path on Yolo that needs the device credential, or the http(s) URL of an image on another host, which screens load through `/v1/thumbnail`; an item's details carry their other pictures (`poster`, `backdrop`, `still`, and a person's `photo`) in the same two forms. MCP gives agents image links instead ([cover images](../feature/2026-10-07-remote-mcp-server.md#cover-images)).

### Errors

Every error has one shape: `{ "error": { "code": "device_offline", "message": "…", "retryable": true } }`, and a refusal a client can act on adds `details`. The codes are `invalid_request`, `unauthorized`, `forbidden`, `not_found`, `device_offline`, `node_offline`, `resolve_failed`, `superseded`, `media_unreachable` (no media path reaches the device and the owner turned the relay off; the message names each path and each fix, and `details` is `{ relayMode, reason, fixes: [{ action, text }] }` with the actions `relay`, `remote`, and `forward`, the last with `port`, `address`, and `gateway`), and `rate_limited`.

| POST | `/v1/playback/play` | control | `{ source \| itemId \| url \| queueItemId, deviceId?, startTime?, reason?, autoplay?, sessionId?, maxVideoKbps?, network? }`. A device rebuilding its own stream passes `reason` (`recovery`, `seek`, `quality`) and the `sessionId` it replaces; if that session was already replaced, the answer is `superseded`. `maxVideoKbps` is the device's adaptive cap ([adaptive quality](../feature/2026-10-11-adaptive-quality.md)), `null` for none, which the Hub keeps for the media path the stream takes; without it the stream starts at the rate kept for that path. `network` (`lan`, `wan`, `relay`, or null for none; any other value counts as none) is the media path a device playing on itself takes now; the Hub keeps it for that device ([media off the Worker](2026-10-13-media-off-the-worker.md)) |
| POST | `/v1/playback/warm` | control | `{ sources, network? }`: the first items a device's home screen offers (the player sends its first three history items once it knows its media path), which the Hub has the node resolve ahead for that device, with its capabilities, its path, and its remembered cap, so a tap on one starts sooner ([node's internal API](2026-10-07-node-internal-api.md)). | PUT | `/v1/playback/device` | control | `{ deviceId, play: true }`: move playback to another device at the same position |
| PUT | `/v1/playback/tracks` | control | `{ subtitles?: [id…], audio?: id }`; an empty array turns subtitles off |
| GET | `/v1/tracks?source=…` | read | A source's tracks; without `source`, the current item's |
| GET | `/v1/queue` | read | The queue |

| GET | `/v1/storyboard?source=&from=&to=&count=&width=` | read | One JPEG grid of `count` evenly spaced, labelled frames of an item, by default the one playing now ([storyboards](../feature/2026-10-13-video-frames.md#storyboards)); `x-yolo-storyboard-times` lists the tiles' times in seconds, comma-separated, and `x-yolo-storyboard-origin` says `storyboard` or `frames` |
| GET | `/v1/thumbnail?url=` | read | An image on another host, such as a web video's thumbnail, fetched by the node ([node's internal API](2026-10-07-node-internal-api.md)), so a screen loads every image from Yolo's own origin; `url` is an http(s) URL of at most 2048 characters |

| POST | `/v1/agent` | control | `{ text, language?, agent? }` → the agent's NDJSON stream from the node; `agent` is the screen's choice, and a paired screen's credential makes that screen its default target |
| GET | `/v1/agent/conversations?limit=` | read | `{ conversations }`: the owner's conversations with the agent, newest first, each `{ id, title, agentId, deviceId, createdAt, updatedAt }` |
| GET | `/v1/agent/conversations/:id` | read | One conversation with its `messages`: `{ id, role, text, createdAt }`, and for an answer `steps` and `status` (null until it ends) |
| POST | `/v1/agent/conversations/:id/messages` | control | `{ text, language?, agent? }` → a first line `{ type: "conversation", id, title }`, then the agent's stream as for `POST /v1/agent`; `new` as the id starts a conversation, and the question and answer are kept; without `agent` the agent that answered the conversation answers again |
| DELETE | `/v1/agent/conversations/:id` | control | Delete a conversation and its messages |
| GET | `/v1/canvas` | read | This screen's agent canvas, `{ rev, objects }`, for a paired screen's own credential that declared one; a screen reads it again when a `canvas_ops` rev is out of step ([agent canvas](../../proposed/architecture/2026-10-21-agent-canvas.md)) |
| POST | `/v1/canvas/events` | control | `{ objectId, gesture, payload? }`: what the person did to an object on this screen (`press`, `pick` with `{ option, after? }`, or `dismiss`) → `{ event }`. The Hub plays or queues a picked choice itself and logs the event for agents |
| POST | `/v1/realtime/ticket` | read | A one-time ticket for `/v1/realtime` ([OAuth](2026-10-07-oauth-authorization-server.md)) |
| POST | `/v1/shares` | control | `{ source? \| itemId? \| url? }` → 201 `{ id, url, title, expiresAt }`: a share link that plays the item, else what plays now, in a friend's browser for 7 days ([share links](../feature/2026-10-20-share-links.md)); `url` is the only time the link is shown. What plays now is named from the Hub's state, without asking the node |

The library routes forward to the node, so no route names a provider such as Plex, and a future audiobook or music library needs no new route. Listings come back with Yolo's history laid over them: an item's `resumeAt` and `watched`, and a show's or season's `watchedEpisodes`, count what the owner played in Yolo as well as what the source knows ([progress and resume](../feature/2026-10-11-yolo-owns-progress-and-resume.md)).

A share link's two routes, `GET /v1/share/<token>` and `POST /v1/share/<token>/stream`, answer without a credential: the Worker routes them before the OAuth provider, and the token in the path is their only authority ([share links](../feature/2026-10-20-share-links.md)).

### Owner routes

The owner's settings use routes under `/v1/owner` ([`service/control/src/api/owner.js`](../../../../service/control/src/api/owner.js)). They are not OAuth resources: they authenticate only with the owner's passkey session cookie ([passkey owner sign-in](2026-10-08-passkey-owner-sign-in.md)), and a bearer token, a device credential included, never reaches them (`401 unauthorized`). Every request carries the header `X-Yolo-Owner: 1`; a request without it, one whose `Sec-Fetch-Site` is not `same-origin`, or one that changes something without an `Origin` equal to Yolo's own gets `403 forbidden`. Responses are `no-store`.

| Method | Path | Purpose |
|---|---|---|
| GET | `/v1/owner/session` | `{ signedIn }`; the one owner route that answers without a session |
| POST | `/v1/owner/session/sign-out` | End this browser's owner session |
| GET | `/v1/owner/devices` | Devices, as `GET /v1/devices` returns them |
| PATCH | `/v1/owner/devices/:id` | `{ name?, kind? }`: rename a device or change its type |
| DELETE | `/v1/owner/devices/:id` | Remove a device, revoke its credential, and close its realtime connection |
| POST | `/v1/owner/pairing/approve` | `{ userCode, name?, kind? }`: approve a pending pairing code, as the approval page does ([device code pairing](../feature/2026-10-07-device-code-pairing.md)) |
| GET | `/v1/owner/agents` | Connected agents, one per OAuth client: `{ id, name, site, redirectHosts, scope, connections, createdAt }` |
| DELETE | `/v1/owner/agents/:id` | Revoke every grant that client holds, with its access and refresh tokens |
| GET | `/v1/owner/passkeys` | Passkeys: `{ id, name, synced, createdAt, lastUsedAt }`, never the public key |
| DELETE | `/v1/owner/passkeys/:id` | Remove a passkey other than the last; every other owner session is signed out |
| GET | `/v1/owner/media` | The media paths ([media off the Worker](2026-10-13-media-off-the-worker.md)): `{ relay: { mode, on, note }, lan, remote, screens, streams }`, where `mode` is `auto`, `on`, or `off`, `on` whether the relay may carry media, `note` the one line settings show about it, `lan` LAN direct play's state as the last check left it, `{ configured, status, zone, name, origin, address, notAfter, renewAt, checkedAt, error, retryAt }`, never the ACME account key ([LAN direct play](../feature/2026-10-12-lan-direct-play.md)), `remote` remote direct play's `{ configured, on, status, reason, zone, name, origin, address, ipv6, mapping, notAfter, renewAt, reachedAt, checkedAt, error, retryAt }`, `screens` each screen's `{ id, name, kind, online, path, at }` from its last stream, and `streams` the streams each path carried over 7 days, `{ days, lan, wan, relay }` |
| PATCH | `/v1/owner/media` | `{ relay?, remote? }`: `relay` sets the relay's mode (`auto`, `on`, or `off`; any other value, `true` and `false` from a page before the modes included, is refused with `invalid_request`), with no confirmation; each change writes a `kind: "security"` log line and sends the connected screens the media paths again. `remote` turns remote access on or off and runs the remote check at once. Answers the same shape |
| POST | `/v1/owner/media/check` | Run the LAN and remote checks now; answers the same shape |
| GET | `/v1/owner/voice` | `{ languages }`: the languages the owner speaks to Yolo, BCP 47 tags first first, `[]` when they chose none ([voice input](../feature/2026-10-18-agent-from-the-screen.md#voice-input)) |
| PUT | `/v1/owner/voice` | `{ languages }`: replaces them, at most four, repeats dropped; `[]` forgets them; anything but a list of tags is refused with `invalid_request` |
| GET | `/v1/owner/image-links` | `{ version, resetAt }`: the key version of the image links agents get for covers, and when they were last reset ([cover images](../feature/2026-10-07-remote-mcp-server.md#cover-images)) |
| POST | `/v1/owner/image-links/reset` | Move to the next key version, so every image link agents were given stops working, and write a `kind: "security"` log line; answers the same shape |
| GET | `/v1/owner/shares` | `{ links }`: the share links screens and agents made, newest first, each `{ id, title, thumbnail, status, createdBy, createdAt, expiresAt, revokedAt, plays, lastPlayedAt }`, where `status` is `active`, `expired`, or `revoked`; never the link itself ([share links](../feature/2026-10-20-share-links.md)) |
| POST | `/v1/owner/shares/:id/revoke` | Revoke a link: its next request is refused, the node stops its streams, and a `kind: "security"` log line is written; answers `{ id, revokedAt, stopped }` |

Adding a passkey uses the sign-in endpoints (`/auth/passkey/register/*`) with the session, which then need no pairing code.

## Consequences

Agents, the player, and any future client see the same operations, errors, and scopes, and a route and its MCP tool cannot drift apart. Provider-neutral library routes keep the API stable as source plugins come and go. The API is pre-1.0: the control plane, the player, and the MCP tools ship together, so a breaking change updates all three in one commit.
